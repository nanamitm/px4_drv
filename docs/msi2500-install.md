# RSP1 互換機 (MSi2500) フルセグ・J.83B BonDriver の導入

対象は Mirics MSi2500 と MSi001 を使う SDRplay RSP1 の互換機（USB ID `1DF7:2500`）です。
UHF 13〜52ch の地上デジタル放送を受信し、A 階層（ワンセグ）と B 階層（HD）を多重フレームの位置に従って
1 本へ戻した TS を返します。スカパー！プレミアムサービス光の ITU-T J.83 Annex B（256QAM、5.6 Msps）も、
同じ BonDriver の別のチューニング空間で受信できます（[J.83B の受信](#j83b-の受信)）。
復調と誤り訂正はすべてソフトウェアで行うため、PX 系チューナーのような
ハードウェアの復調器は使いません。この対応は実験的なものです。

検証できた範囲は、64 ビット版での受信、13ch と 15ch の選局の切り替え、TVTest での視聴です。
32 ビット版の実機での受信、USB の抜き差し、数時間の連続受信は未確認です。
純正の SDRplay RSP1 は検証に使っていません。互換機とはフロントエンドの GPIO の配線が異なる可能性があります
（[技術資料](../winusb/docs/msi2500-fullseg-design.md)の 2.5 節）。

## 既知の制約

USB の等時転送の一部が間に合わない失敗が、数分〜十数分に 1 回起きることがあります。
そのたびに復調をやり直すため、約 2 秒分の TS が欠けます。
欠落の頻度は USB の接続先で変わり、検証環境では PX-MLT8PE と同じ USB コントローラーにつないだ場合に多く、
別のコントローラーのポートへ移すと減りました。他の USB チューナーと別のコントローラーへ接続することを勧めます。
長時間の録画は、この欠落が許容できるかを確認してから使ってください。

受信中の CPU 使用率は検証環境で平均約 1.3 コア、メモリーは約 80 MB でした。
選局から最初の TS が届くまで約 2 秒かかります。

## ドライバーの登録

この配布物には USB ドライバーを同梱していません。SDRplay が配布する API（ドライバーを含む）を導入し、
デバイスマネージャーで機器が `SDRplay RSP1` として認識されていることを確認してください。
`DriverHost_PX4.ini` の定義は、SDRplay のドライバーが登録するデバイスインターフェースの GUID
（`{2d93e8f2-bc67-4f7d-8891-574830aa637d}`）で機器を探します。

SDRplay のアプリケーションなど、他のソフトウェアがこの機器を使っている間は受信できません。

## 配布フォルダーの選択

TVTest・EDCB など、使用するアプリケーションと同じビット数のフォルダーを選んでください。

- 32bit アプリケーション: `BonDriver_MSI2500_32bit`
- 64bit アプリケーション: `BonDriver_MSI2500_64bit`

フォルダーには `BonDriver_MSI2500.dll`、`DriverHost_PX4.exe`、設定・チャンネル定義と、`msi2500` サブフォルダーが入っています。
`msi2500/msi2500_frontend.exe` が復調を行うため、受信に必須です。DLL だけを取り出さず、フォルダーの内容をまとめて配置してください。

## TVTest・EDCB への配置

1. 使用中の TVTest・EDCB・録画処理を終了し、既存の `DriverHost_PX4.exe` も終了したことを確認します。
   古い `DriverHost_PX4.exe` が動作したままだと、同じ通信名のため新しい定義の機器を利用できません。
2. 選んだ配布フォルダーの内容を、アプリケーションの BonDriver 配置先へコピーします。`msi2500` サブフォルダーもそのままコピーします。
3. アプリケーションで `BonDriver_MSI2500.dll` を選び、チャンネルスキャンを実行します。
   最初の TS まで約 2 秒かかるため、スキャンの受信待ち時間は 5 秒以上に設定してください。

フルセグ（B 階層）の映像はスクランブルされたまま届きます。PX 系チューナーと同じく、アプリケーション側でカードによる解除の設定が必要です。

## 設定

`DriverHost_PX4.ini` の MSi2500 の定義（`Type="MSI2500"`）の `Config` 節で、次の値を変更できます。

| 項目 | 既定値 | 内容 |
|---|---|---|
| `GainDb` | 40 | MSi001 の利得 (0〜102 dB)。検証環境の受信点では 40 で MER 約 27 dB |
| `AsyncTune` | true | 選局要求の受付で選局を完了とし、復調は非同期で進める |
| `ViterbiThreads` | 自動 (最大 4) | B 階層のビタビ復号のスレッド数 |
| `HelperPath` | `msi2500\msi2500_frontend.exe` | helper の場所 |

| `GainDbJ83B` | 46 | J.83B を受信するときの MSi001 の利得 (0〜102 dB)。[J.83B の受信](#j83b-の受信)を参照 |

信号レベルの表示は、RS 復号の成功割合（0〜100）です。地上デジタル放送では B 階層、J.83B では全ブロックの割合で、
RF の C/N（dB）ではありません。

helper のログは `DriverHost_PX4.exe` と同じフォルダーの `msi2500_frontend-<番号>.log` に残ります。
欠落の調査には、このログの `[usb]` と `discontinuity` の行を使います。

## J.83B の受信

スカパー！プレミアムサービス光の RF 出力を機器のアンテナ入力へつなぐと、`BonDriver_MSI2500.dll` の 2 つ目の
チューニング空間「スカパー！プレミアムサービス光(J.83B)」で受信できます。チャンネル定義は PX-MLT 系と共通の
`BonDriver_PX4-J83B.ChSet.txt`（H001〜H105）です。TS は受信したまま返し、スクランブルの解除は扱いません。

検証環境で受信を確かめた範囲は次のとおりです。

| 搬送波 | 結果 |
|---|---|
| H007 (132.25 MHz)、H008 (138.75 MHz) | 64 ビット版の helper で各 600 秒、RS の訂正不能 0。BonDriver 経由で H007 と H008 を交互に選局する試験も誤りなし |
| H004 (112.75 MHz)、H005 (119.25 MHz) | MER が約 23 dB で、256QAM の復号に要る約 28 dB に届かず受信できない |
| H073、H075〜H077 (561〜587 MHz) | H075 は MER 約 28 dB で、0.03% の RS ブロックが訂正できない。受信できる帯域としては扱っていない |

64 ビット版の TVTest でも、J.83B の空間を選局して視聴できることを確かめました。
受信できる搬送波と MER は、地域の搬送波の配置と分配後の入力レベルで変わります。
32 ビット版の実機での受信、数時間の連続受信は未確認です。

### 利得

利得が大きすぎると ADC が飽和し、MER はほとんど下がらないまま RS の訂正が急に増えます。検証環境では
`GainDbJ83B` が 58 で H008 の RS ブロックの約 26% が訂正を要し、46〜52 ではほぼ 0 でした。既定値の 46 で
信号レベルが 100 を下回り続ける場合は、helper のログ（`msi2500_frontend-<番号>.log`）の `done:` の行の `clip` を確認します。
`clip` が 0 でなければ利得を下げ、0 のまま MER が低い場合は 52 前後まで上げてください。

### チャンネルスキャン

J.83B の選局は、ロックまでを 1 秒で打ち切ります。検証環境では helper の起動を含めて約 0.44 秒でロックしました。
H001〜H105 の行のうち搬送波のない行は、それぞれ約 1 秒で失敗として次の行へ進みます。

### 既知の制約

地上デジタル放送と同じく、USB の等時転送の遅れによる欠落が起きることがあります。欠落のたびに復調をやり直すため、
その前後で TS が途切れます。検証環境の 600 秒の受信では、10 回の欠落で合計約 0.25 秒分の TS が欠けました。
受信中の CPU 使用率は約 1.0 コアです。

復調の仕組みと検証の記録は [J.83B の技術資料](../winusb/docs/msi2500-j83b-design.md)を参照してください。
配布フォルダー内では `TECHNICAL-J83B.md` に収録しています。

## ソースからビルドする場合

Visual Studio 2022 の C++ 開発ツール・v143・Windows SDK、Python 3、Rust/Cargo を用意します。リポジトリのルートから次を実行してください。

```powershell
rustup target add i686-pc-windows-msvc x86_64-pc-windows-msvc
.\winusb\build.ps1
```

通常ビルドで両ビット数の MSi2500 配布物も生成し、helper の自動試験と、必要ファイル・対応ソースの検査を実行します。
配布物は `winusb/dist/` に生成されます。helper は C ランタイムを静的リンクした単一の実行ファイルのため、
利用者が Rust や Visual C++ 再頒布ランタイムを追加する必要はありません。

復調の仕組み、検証の記録、未解決の事項は[技術資料](../winusb/docs/msi2500-fullseg-design.md)を参照してください。配布フォルダー内では `TECHNICAL.md` に収録しています。
