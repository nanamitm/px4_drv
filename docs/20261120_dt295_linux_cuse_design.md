# PIX-DT295 の Linux 対応の設計 (ユーザー空間デーモンと CUSE)

この文書は、PIXELA PIX-DT295 (USB ID `06b8:103b`) を Linux で使うための構成案です。  
維持する契約、再利用するコード、試験の範囲、未確認の条件を整理します。  
本実装は [`cuse/`](../cuse/README.md) にあり、「本実装の確認」に実機で確かめた範囲を記載します。  
「試作の結果」と「本実装の確認」に記載した実機の測定を除き、記載した動作は設計上の想定です。

この文書の「検証環境」は、Raspberry Pi 4 Model B に 64 ビット版の Raspberry Pi OS Lite を入れ、PIX-DT295 を本体の USB ポートへ直接接続した構成を指します。  
仮想マシンの USB パススルーでは制御転送に遅延が加わり、受信中に続く SERVICE の間隔とカード通信の成功数が実機と変わる可能性があるため、USB コントローラーを OS が直接扱う実機を検証環境に選びました。

## 目的と範囲

recpt1、BonDriverProxy_Linux、Mirakurun などは、既存の機種と同じく `/dev/*video*` のデバイスファイルを開き、PTX の ioctl で選局します。  
PIX-DT295 でも同じ使い方ができるよう、ユーザー空間のデーモンが CUSE (Character device in Userspace) でデバイスファイルを作り、カーネルモジュールの `ptx_chrdev` と同じ契約で応答する構成を採ります。

対象は地デジ・BS・110度CS の受信と、内蔵カードリーダーの pcscd からの利用です。  
PIX-DT295 はアンテナ給電に対応していないため、LNB 電源の制御は対象外です。  
PIX-DT295 W など別の PID の機器は、WinUSB 版と同じく対象外です。

## カーネルモジュールを採用しなかった理由

WinUSB 版の PIX-DT295 の制御は、すべてユーザー空間の `DriverHost_PX4.exe` で動いています。  
ファームウェアの書き込み、受信中に待機なしで続ける SERVICE の制御転送、Bulk IN 8 KiB × 64 本の読み出し、カードの UART を含め、カーネルの機能を必要とする処理はありません。

制御の中心は、プラットフォームに依存しない形ですでに分かれています。

| ファイル | 内容 | Windows への依存 |
|---|---|---|
| `winusb/src/DriverHost_PX4/dt295/runtime.c`、`upstream/` | 起動、選局、TS 入力の C 実装。USB 転送は `struct dt295_io` のコールバックで受け取る | なし |
| `dt295/source_firmware.cpp` | 組み込みファームウェアの検証と配置、`Tune`、`Service`、`ReadCn` など | SHA-256 の計算 (`BCryptHash`) と、EXE のリソースからの読み出しだけ |
| `dt295/frontend_init.cpp`、`dt295/card_uart.cpp`、`card_response.hpp` | 復調器の初期化列、カード UART | なし |
| `dt295/winusb_transport.cpp` | `dt295_io` を WinUSB の制御転送で実装 | あり (94 行) |
| `dt295/device.cpp` | Bulk IN の読み出し、SERVICE のループ、受信機の公開 | あり (WinUSB、`OVERLAPPED`、DriverHost の受信機の API) |

カーネルへ置くと、上の C++ を C へ書き直し、カーネルの待機とメモリー確保の制約へ合わせる必要があります。  
ユーザー空間なら上の表の上 3 行をそのまま使え、新たに書くのは転送層、受信ループ、デバイスファイルの公開だけで済みます。  
カーネルモジュールの px4_drv は `06b8:103b` を USB ID の一覧 (`driver/px4_usb.c`) に持たないため、デーモンが機器を開いても既存の機種と衝突しません。

## 構成

デーモン (仮称 `px4-dt295d`) が、接続された PIX-DT295 ごとに次のものを持ちます。

```
PIX-DT295 ──USB── libusb の転送層 ── SourceFirmware (共有コード)
                                        │
                     制御ロック (1台につき1つ)
                  ┌─────────┼──────────┐
           SERVICE のループ   CUSE: /dev/dt295videoN   CUSE: /dev/px4card/<ID> 相当
           Bulk IN の読み出し  (PTX の ioctl、read、poll)   (PX4_CARD_* の ioctl)
                                        │                       │
                               recpt1 / Mirakurun        px4-drv-pcsc (pcscd)
```

制御ロックの扱いは WinUSB 版の `device.cpp` と同じにします。  
SERVICE のループは待機者がいれば 1 回分を先に通すため、C/N の読み出しやカードの操作の遅れは SERVICE 1 回分程度に収まります。  
CUSE の要求を処理するスレッドがこのロックを持ったまま、FUSE への応答や利用者の読み出しを待つと SERVICE が止まるため、ロックの範囲を機器の操作だけに限ります。

### 再利用と新規作成の分担

`device.cpp` の SERVICE のループと受信の停止手順には、送出の詰まりへの対処や統計の記録など、実機の測定から決めた処理が含まれます。  
`device.cpp` には PIX-DT295 の追加以降 24 件の変更があり、C/N の読み出し間隔、T=1 の CRC の待ち合わせ、バッファのあふれの扱いなど、実機で見つかった不具合の修正が多く含まれます。  
試作のデーモンはこのうち SERVICE のループとカードの操作を書き直して持っており、本実装でも複製すると、片方だけが修正される状態を招きます。

このため、次の部分を WinUSB と DriverHost に依存しないクラスへ移し、Windows 版と Linux 版の双方から使います。

| 共有するもの | 内容 |
|---|---|
| 制御ロックと待機者の数 | SERVICE が待機中の要求を 1 回分先に通す処理を含む |
| SERVICE のループ | 停止の判定を呼び出し側から受け取り、統計と滞留の記録を共有する |
| カードの操作 | `card_response.hpp` による応答の完成判定、FIFO へ区切って積み込む送信、抜去とリセットでの状態の破棄 |
| TS の受け渡し | `Feed()` から `TsContinuityMonitor`、出力先への書き込みまで |

Bulk IN の読み出しは、Windows の `OVERLAPPED` と libusb の非同期転送で待ち方が異なるため、OS ごとに持ちます。  
読み出した USB のデータを共有のクラスへ渡す境界を 1 つにして、TS の処理を 2 か所に書かない形にします。

ファイルは `winusb/src/DriverHost_PX4/dt295/` に残し、Linux 版のビルドから参照します。  
`pcsc/Makefile` と `macos/CMakeLists.txt` もこのディレクトリの共有コードを参照しており、ファイルを移すと Windows 版の履歴を `git log --follow` なしでは追えなくなるためです。  
この切り出しは Windows 版の動作に触れるため、Windows 版の回帰試験 (`build.ps1` の試験、`channel_switch_stress`、`card_stream_stress`) を同じ変更の完了条件に含めます。

`source_firmware.cpp` の Windows への依存は、ブート ROM の内容を確かめる SHA-256 の計算 (`BCryptHash`) と、EXE のリソースからの組み込みファームウェアの読み出しの 2 点です。  
この 2 点を OS ごとに実装する小さな関数へ分け、Windows 版は現在の `BCryptHash` とリソースの読み出しをそのまま使います。  
Linux 版の SHA-256 は、試作で使った約 60 行の実装を置き、公開されている試験ベクターで自動試験します。  
SHA-256 の用途はブート ROM の 1 回の確認だけのため、libcrypto への依存を加える案は採用しませんでした。  
組み込みファームウェアは、Windows の EXE と同じく Linux 版でもデーモンの実行ファイルへ埋め込み、利用者がファイルを別に配置する手順を不要にします。

### 配置とビルド

Linux 版のデーモンは、リポジトリ直下の新しいディレクトリ `cuse/` に置きます。  
`driver/` はカーネルモジュール、`pcsc/` は IFD ハンドラーで、ユーザー空間のデーモンはどちらとも実行の形と配布の単位が異なるためです。  
`cuse/` には、デーモンのソース、`Makefile`、systemd のユニット、udev の規則、自動試験を置きます。  
共有コードは `pcsc/Makefile` と同じく相対パスで `winusb/src/DriverHost_PX4` を参照します。  
Debian パッケージは、`build_pcsc_deb.sh` と同じ形の別のスクリプトで作ります。

## デバイスファイルの契約 (受信)

デバイスファイル名は既存の命名に合わせて `/dev/dt295video0` からの連番とします。  
番号は、カーネルモジュールと同じく空いている最小の番号を割り当てます。

| ioctl・操作 | 応答 | 備考 |
|---|---|---|
| `open` | 2つ目の open には `-EALREADY` | `ptx_chrdev_open()` と同じ |
| `PTX_SET_CHANNEL` | 既存の周波数の換算式で選局 | 地デジは UHF 13〜62ch と CATV、衛星は `freq_no` 0〜23 |
| `PTX_START_STREAMING`、`PTX_STOP_STREAMING` | 二重の開始・停止は `-EALREADY` | |
| `PTX_GET_CNR` | 選局時と受信中に 1 秒ごとに読んだ値を返す | 換算式は WinUSB 版と同じ |
| `PTX_ENABLE_LNB_POWER` | `arg` が 0 なら成功、0 以外なら `-ENOSYS` | `set_lnb_voltage` を持たない機種へのカーネルの応答と同じ |
| `PTX_SET_SYSTEM_MODE`、`PTX_GET_LOCK_STATUS` | 既存の意味で応答 | |
| `PTX_GET_TMCC_*`、`PTXT_*` | 対応しない機能は既存機種と同じ `-EOPNOTSUPP` か `-ENOSYS` | 必要な利用者の有無を確認してから追加 |
| `read` | 受信中は 0 を返さずに待ち、`O_NONBLOCK` では `-EAGAIN`。停止後は EOF | 利用側は 0 を EOF と解釈して受信を終えるため |
| `poll` | 読み出せる量がしきい値に達したときに起床 | |
| USB 切断後 | すべての操作に `-EIO` を返し、待機中の `read` と `poll` を起こす | 切断後にノードを消すかどうかは下記 |

`PTX_SET_CHANNEL` の換算式は `driver/ptx_chrdev.c` に書かれています。  
Linux 版と同じ式を別に書くと食い違う余地が生まれるため、`driver/isdbc_channel.h` の例と同じく、ユーザー空間からも読める共有ヘッダーへ移すことを検討します。

### 衛星の相対 TS 番号

recpt1 や Mirakurun のチャンネル指定 (`BS15_0` など) は、`slot` に相対 TS 番号を渡します。  
カーネルモジュールは `slot` が相対 TS 番号の範囲内なら TMCC から TSID を読み、範囲外なら `slot` を TSID として扱います (`driver/px4_device.c` の `px4_chrdev_set_stream_id_s()`)。

PIX-DT295 の共有コード (`dt295/source_firmware.cpp` の `SourceFirmware::Tune()`) も同じ契約にそろえ、衛星の `tsid` が 0〜7 なら相対 TS 番号として TMCC から TSID を求めます。  
WinUSB 版の PX4 系と ISDB2056 系の受信機も `stream_id` が 8 未満なら相対 TS 番号として扱うため、PIX-DT295 だけが異なる意味を持つと、BonDriver のチャンネル定義を機種ごとに書き分ける必要が生じます。  
実在する TSID は 8 以上のため、TSID を直接渡す既存のチャンネル定義の選局は変わりません。

復調器 TC90532XBG の TMCC の配置は、カーネルモジュールがすでに TC90532XBG を載せた ISDB2056 系 (`driver/isdb2056_device.c`) で TC90522 の関数を使っていることから同じと推定し、PIX-DT295 の実機で確かめました。  
手順はカーネルモジュールと同じで、TSID を 0 にしたまま周波数を合わせ、0xc3 の bit4 で搬送波のロックを待ち、0xce から 2 バイトずつ並ぶ TSID の一覧を読み、0x8f/0x90 へ書いてから 0xe6 で一致を確かめます。  
`Tune()` の通常のロック判定は 0xe6 と指定した TSID の一致を条件に含むため、TSID が決まるまでは 0xc3 だけで搬送波のロックを判定します。

PIX-DT295 の実機では、使われていない番号が 0 ではなく 0xffff と読めました (BS15 で `40f1 40f2 48f3 ffff ffff ffff ffff ffff`)。  
0xffff を TSID として書くと 0xe6 も 0xffff を返し、存在しない番号の選局が成功してしまうため、0 と同じく存在しない番号として扱い `-EAGAIN` を返します。  
WinUSB 版の PIX-DT295 の受信機は、`-EAGAIN` を無信号の `-ENOLINK` と同じく機器の異常として扱わず、次の選局を受け付けます。  
TC90522 を載せた機種の既存の判定 (0 だけを不在とする) で 0xffff が読めるかは、それらの機種の実機で確かめていません。

### 32 ビットのプロセス

`PTX_GET_CNR` は `_IOR` の型の位置にポインタを指定しているため、32 ビットと 64 ビットのプロセスでコマンド番号が異なります。  
カーネルモジュールは `compat_ioctl` を実装していませんが、CUSE ではデーモンが両方の番号を受け付けられます。  
既存の機種と挙動を揃えるか、両方を受け付けるかは未決です。

### CUSE の ioctl の制約

CUSE の ioctl は、コマンド番号の方向と大きさからカーネルがデータを複写します。  
`PTX_GET_CNR` の番号が示す大きさ (64 ビットでは 8 バイト) と、実際に書き戻す `int` (4 バイト) が異なります。  
下記の試作で、カーネルが利用者へ複写するのはデーモンが応答した長さだけであることを確かめました。  
デーモンが 8 バイトを応答すると `int` の直後の 4 バイトが上書きされるため、`PTX_GET_CNR` の応答は必ず `sizeof(int)` にします。  
ポインタを含む `PTXT_GET_INFO` などに対応する場合は、CUSE の制限なしの ioctl (`CUSE_UNRESTRICTED_IOCTL`) が必要です。

`PTX_ENABLE_LNB_POWER` と `PTX_SET_SYSTEM_MODE` は `_IOW` で定義されていますが、カーネルモジュールは `arg` をアドレスではなく値として読みます。  
recpt1 も `LNB_ENABLE` の電圧を値で渡すため、制限付きの ioctl ではカーネルがその値をアドレスとして複写しようとして失敗します。  
このため、デーモンは制限なしの ioctl で動かし、`PTX_SET_CHANNEL`・`PTX_GET_CNR`・`PTX_GET_LOCK_STATUS` のようにアドレスを渡す ioctl だけを `fuse_reply_ioctl_retry()` で読み書きします。  
`PTX_GET_CNR` の再要求ではカーネルと同じ 4 バイトだけを指定するため、利用者のメモリーの `int` の直後は変わりません。

`include/ptx_ioctl.h` は `<linux/ioctl.h>` を読み込まないため、ユーザー空間で使う場合は先に `<sys/ioctl.h>` を読み込みます。

### CUSE の試作の結果

PIX-DT295 を使わずに、PTX の ioctl の一部へ合成した TS で応答する CUSE のデーモンと、recpt1 と同じ読み方をする試験用のクライアントを作り、検証環境で実行しました。  
カーネルは 6.18.50 (`6.18.50+rpt-rpi-v8`)、libfuse3 は 3.17.2 です。  
デーモンは制限付きの ioctl (`cuse_info.flags = 0`) で動かし、デーモンとクライアントは root で実行しました。

| 確認した項目 | 結果 |
|---|---|
| 2つ目の `open` | `EALREADY` |
| `START` より前と `STOP` の後の `read` | 0 (EOF) |
| `PTX_GET_CNR` (コマンド番号 `0x80088d04`、大きさ 8) | デーモンへは `out=8` で届き、4 バイトの応答では直後の 4 バイトが変わらず、8 バイトの応答では上書きされた |
| `PTX_SET_CHANNEL` (`0x40088d01`) | デーモンへ `in=8` で `struct ptx_freq` が届いた |
| 二重の `START` | `EALREADY` |
| 未定義のコマンド番号 | `ENOTTY` |
| ブロッキングの `read`、`poll`、`O_NONBLOCK` | 受信中は TS を返し、`poll` は `POLLIN`、読み尽くした後の `O_NONBLOCK` は `EAGAIN` |
| 約 3 MB/s (BS 相当) で 10 秒間の読み出し | 2.95 MB/s、`read` 2,451 回、`read` の間隔は最大 4.2 ms、同期と CC の異常は 0 件 |
| その間のデーモンの CPU 使用量 | 1 コアの約 2.6% |

デーモンを終了すると、CUSE のデバイスファイルは消えました。  
作られたデバイスファイルの権限は `crw------- root root` で、root 以外から使うには udev の規則が必要です。  
この試作は CUSE の契約と転送量を確かめたもので、PIX-DT295 の SERVICE や Bulk IN と同時に動かしたときの負荷は含みません。

### libusb で PIX-DT295 を動かした試作の結果

WinUSB 版の `SourceFirmware` (`direct-fr`)、`frontend_init.cpp`、上流の `stream_input.c`・`ts_framer.c`・`ts_mux.c` を変更せずに Linux でビルドし、libusb の制御転送と Bulk IN で PIX-DT295 を動かしました。  
Windows に依存する 3 か所は、試作専用の代わりの実装で補いました。

- EXE のリソースからの読み込み: ファイルから読む形に置き換えた
- `BCryptHash`: SHA-256 の小さな実装に置き換えた
- `msg_printf`: 標準エラー出力へ書く形に置き換えた

転送層は WinUSB 版の `Transport` と同じく、操作ごとの絶対期限を持ち、失敗した要求を再送しない作りにしました。  
Bulk IN は WinUSB 版の `direct-fr` と同じく、8 KiB の読み出しを 64 本投入しました。  
SERVICE のループと C/N の読み出しの関係も WinUSB 版と同じで、C/N は 1 秒ごとに、待機者を先に通す制御ロックの下で読みました。  
検証環境の PIX-DT295 は High Speed で接続され、どのカーネルドライバにも割り当てられていない状態で開けました。

| 項目 | 結果 |
|---|---|
| 初期化 (`Start`) | 成功。約 0.37 秒、制御転送 1,252 回、平均 155 µs |
| 選局 | ロックした場合は約 0.47 秒。無信号では `-ENOLINK` を約 4.2 秒で返した |
| 終了時の復元 (`Close`) | 成功。ブート RAM と TS エンジンの復元を検証済み |
| 地デジの UHF 13〜52ch の走査 | 13〜17ch でロックし、C/N は 31.1〜31.8 dB |

13ch を 60 秒受信した結果は次のとおりです。

| 項目 | 結果 |
|---|---|
| 受信量 | 225,009,664 バイト (29.96 Mbps)、1,196,859 パケット |
| 枠の再同期、破棄、同期、CC の飛び、形式不正 | すべて 0 件 |
| TEI | 19 件 (すべて受信開始から 10 秒以内で、以降は増えなかった) |
| Bulk IN の完了の間隔 | 最大 3.3 ms |
| SERVICE | 74,411 回、間隔は平均 0.81 ms・最大 3.0 ms、1 回の所要時間は最大 3.0 ms、未送信量の最大は 526 バイト |
| 受信中の制御転送 | 149,365 回、平均 398 µs、最大 2,873 µs |
| C/N | 30.88〜31.87 dB、読み出しの失敗は 0 件 |

受信開始直後の TEI は、WinUSB 版がロック後 350 ms の待機と BonDriver の Purge で破棄している、復調器 TC90532XBG のロック直後の誤り訂正前の TS と考えられます。  
この試作はロック後の待機を入れていないため、CUSE のデーモンでは WinUSB 版と同じく、ロック後の待機と、それまでの TS の破棄が必要です。  
TEI の発生時刻をパケット単位で記録していないため、ロック直後の区間に限られることは未確認です。

続けて 13ch を 10 分受信した結果は次のとおりです。

| 項目 | 結果 |
|---|---|
| 受信量 | 2,250,006,528 バイト (29.96 Mbps)、11,968,119 パケット |
| 枠の再同期、破棄、同期、TEI、CC の飛び、形式不正 | すべて 0 件 (この回は選局に約 0.68 秒かかった) |
| Bulk IN の完了の間隔 | 最大 3.3 ms |
| SERVICE | 740,045 回、間隔は平均 0.81 ms・最大 3.2 ms、未送信量の最大は 526 バイト |
| 受信中の制御転送 | 1,481,713 回、平均 401 µs、最大 3,075 µs |
| C/N | 30.60〜32.01 dB、読み出しの失敗は 0 件 |
| CPU 時間 | 経過 602 秒に対し user 63.6 秒、sys 93.1 秒 (1 コアの約 26%) |
| CPU 温度 | 受信の前後とも 44.3℃ |

WinUSB 版の記録では、SERVICE の間隔は地上波で平均約 9 ms です。  
検証環境では 1 回の SERVICE が短く終わり、待機なしのループが毎秒約 1,230 回の SERVICE を送るため、CPU 時間の大半はこの制御転送に使われています。  
未送信量は最大 526 バイトで、機器内のリング (6 MiB) にはほとんど溜まっていません。  
SERVICE の間に待機を入れれば CPU 時間を減らせる可能性がありますが、待機の長さは BS・CS の受信量とカード通信の負荷で測ってから決める必要があり、未決の事項として扱います。

### CUSE と PIX-DT295 を結合した試作の結果

上記の 2 つの試作を 1 つのデーモンにまとめ、`/dev/dt295video0` を recpt1 (stz2012 版、rev.72) から `--device` で開いて受信しました。  
デーモンは制限なしの ioctl で動かし、TS は Bulk IN の完了ごとにデーモン内の 188 × 65,536 バイトのリングへ入れ、`read` で渡しました。  
地デジでは、選局がロックした後に 350 ms 待ってから `PTX_SET_CHANNEL` を完了させます。  
TS の取り込みは `PTX_START_STREAMING` から始まるため、ロック直後の TS は利用者へ渡りません。  
デバイスファイルを閉じるたびに `SourceFirmware::Close()` で起動前の状態へ戻し、次の選局で初期化し直します。  
これは WinUSB 版の受信機の `Close` と同じ扱いです。

デーモンは root ではなく、ログインユーザーで動かしました。  
次の udev の規則で、PIX-DT295 の USB 機器と `/dev/cuse` を `plugdev` グループへ、作成したデバイスファイルを `video` グループの 664 にしました。

```
SUBSYSTEM=="usb", ATTR{idVendor}=="06b8", ATTR{idProduct}=="103b", MODE="0660", GROUP="plugdev"
KERNEL=="cuse", MODE="0660", GROUP="plugdev"
KERNEL=="dt295video*", MODE="0664", GROUP="video"
```

## デバイスファイルの契約 (内蔵カードリーダー)

px4-drv-pcsc は `/dev/px4card/<ID>` を開き、`include/px4_card_ioctl.h` の ioctl でカード検出、電源、UART を操作します。  
デーモンが同じ ioctl を CUSE で提供すれば、ATR の解析と T=1 の処理を持つ IFD ハンドラーを変えずに使えます。  
`EHOSTDOWN`、`ENODEV`、`EINTR` の意味も同じヘッダーの定義に従います。

IFD ハンドラーは、pcscd のホットプラグが渡す `usb:06b8/103b:libudev:0:/dev/bus/usb/<bus>/<dev>` から、sysfs の `px4card` クラスをたどってデバイスファイルを探します (`pcsc/linux_card_device.cpp` の `ResolveCardDevice()`)。  
CUSE のデバイスは USB 機器を親に持たないため、この探索では見つかりません。  
デーモンが USB のバス番号とデバイス番号からデバイスファイルへの対応を `/run` の下に書き出し、IFD ハンドラーがそれを読む方式が候補です。  
あわせて `pcsc/Info.plist` へ `0x06b8`/`0x103b` を追加します。

PX4_CARD_MAX_FRAME の 255 バイトは IT930x の UART の上限から決めた値です。  
PIX-DT295 のカード UART の 1 回の送受信の上限がこれと同じかは、`card_uart.cpp` と実機で確認します。  
リーダー名の ID は、WinUSB 版と Linux 版で同じ機器を同じ ID で識別できる既存の規則に合わせます。

### カードリーダーの試作の結果

結合した試作のデーモンへ、2 つ目の CUSE のセッションとしてカードのデバイスファイルを加えました。  
`cuse_lowlevel_main` はシグナルのハンドラーを 1 つのセッションにしか結び付けないため、受信のセッションは従来どおり `cuse_lowlevel_main` で動かし、カードのセッションは `cuse_lowlevel_new`、`/dev/cuse` を開いた fd への `fuse_session_mount("/dev/fd/N")`、`fuse_session_loop` を回すスレッドで動かしました。  
USB の機器は 1 つのプロセスだけが開けるため、受信とカードは同じデーモンが扱います。

カードの操作は WinUSB 版の `Device::Card()` と同じ形にしました。  
受信の制御ロックを待機者として取り、受信中は PIF1 の Bulk 転送、受信していない間はブート ROM への直接アクセスでカードの UART を操作します。  
応答を待つ間はロックを手放すため、SERVICE は止まりません。  
ioctl の応答はカーネルモジュールに合わせ、同時に開けるのは 1 つ (`-EBUSY`)、`PX4_CARD_POWER_ON` の 2 回目以降は何もせず、電源投入前の UART の操作は `-EHOSTDOWN`、`close` で電源を切ります。  
`PX4_CARD_RX_READY` は、WinUSB 版と同じ `card_response.hpp` の応答の完成判定で答えます。

デバイスファイルの名前は、CUSE の `DEVNAME` を `px4card!<ID>` にすると `/dev/px4card/<ID>` になりました (sysfs は `/sys/class/cuse/px4card!<ID>`)。  
ID は WinUSB 版の `HashDevicePath()` とカーネルモジュールの `px4_card_reader_id()` と同じく、USB のシリアル番号を含む機器のパスから求めます。  
作られたデバイスファイルは root の 600 で、カーネルモジュール用の `SUBSYSTEM=="px4card"` の規則は `SUBSYSTEM=cuse` の CUSE のデバイスに当たりません。  
udev は sysfs の名前の `!` を `/` に置き換えてから `KERNEL` と比べるため、`KERNEL=="px4card!*"` では一致せず、次の規則で 660 になりました。

```
SUBSYSTEM=="cuse", KERNEL=="px4card/*", MODE="0660", GROUP="plugdev"
```

IFD ハンドラーの `ResolveCardDevice()` は `/` で始まる名前をそのまま開くため、試作では `/etc/reader.conf.d/` へ `DEVICENAME /dev/px4card/<ID>` を書き、IFD ハンドラーを変更せずに pcscd へ登録しました。  
この方法はホットプラグに対応せず、pcscd より先にデーモンが起動している必要があるため、配布の形には上記の `/run` の対応表などが必要です。  
Debian の pcscd は polkit で、有効なローカルのログインではないクライアント (SSH のセッションなど) を拒否するため、pcscd を経由する試験は root で実行しました。

検証環境の PIX-DT295 と B-CAS カードで、ATR と、B-CAS の初期設定条件の取得コマンド (INT) の APDU を試しました。

| 試験 | 経路 | 結果 |
|---|---|---|
| デバイスファイルを直接開き、IFD ハンドラーと同じ `LinuxCardDevice` と `SmartCard` で 20 回 | ブート ROM への直接アクセス | ATR 13 バイト (317 ms)、応答 61 バイトと SW 9000、20 回すべて成功、平均 72.8 ms・最大 73.1 ms |
| pcscd 経由の `SCardConnect` (T=1) と `SCardTransmit` 50 回 | 同上 | 接続 325 ms、50 回すべて成功、平均 72.8 ms・最大 73.0 ms |
| 13ch の 120 秒の受信中に pcscd 経由で 1,300 回 | PIF1 の Bulk 転送 | 1,300 回すべて成功、平均 66.9 ms・最大 71.5 ms |

受信中にカードを操作した 120 秒の TS は、同期、TEI、CC の飛び、形式不正がすべて 0 件で、29.96 Mbps で一定、`read` の間隔は最大 5 ms でした。  
デーモン側は、リングのあふれ 0 件、1 回の SERVICE の所要時間は最大 6.7 ms (カードなしの 6 時間の受信では 6.2 ms)、未送信量の最大は 527 バイトでした。  
長時間の同時動作は下記の「受信とカードの 6 時間の同時動作」で確かめました。カードの抜き差しと受信中の USB の抜き差しは未確認です。

カードのセッションを加えた後、デーモンが SIGTERM で終了しない問題が起きました。  
カードのループのスレッドは `/dev/cuse` の `read` で待っており、別のスレッドから `fuse_session_unmount()` で fd を閉じても、すでに待っている `read` は戻りません。  
また、`cuse_lowlevel_main` のハンドラーは受信のセッションに終了を記録するだけで、`read` が中断されるのはシグナルを受けたスレッドに限られるため、終了のシグナルが補助のスレッドへ届くと受信のセッションも終わりません。  
試作では、デーモンが作るスレッド (Bulk IN のイベント処理、SERVICE、カードのループ) を SIGTERM・SIGINT・SIGHUP を遮断した状態で作り、カードのセッションの終了時は `fuse_session_exit()` の後に `SA_RESTART` なしのハンドラーを設定した SIGUSR1 を `pthread_kill()` で送って `read` を中断しました。  
`read` に入る直前にシグナルが届く場合に備え、ループが終わるまで 10 ms ごとに最大 2 秒送り直します。  
libusb が内部で作るスレッドは、libusb 自身がすべてのシグナルを遮断しています。  
修正後は、待機中と受信後のどちらも SIGTERM から約 0.1 秒で終了し、両方のデバイスファイルが消え、終了時の復元も成功しました。

地デジ 13ch を 6 時間受信しながら、pcscd 経由で `SCardConnect` と `SCardTransmit` 1,000 回の組を受信の終わりまで繰り返しました。  
TS は保存せず、6 時間の受信と同じ道具で計数しました。

| 項目 | 結果 |

| `read` の間隔 | 最大 8 ms |
| デーモンのリング | あふれ 0 件 |
| SERVICE | 19,281,748 回 (毎秒約 890 回)、1 回の所要時間は最大 16.2 ms、未送信量の最大は 526 バイト |

最後の組は受信の終了をまたぎ、平均 72.3 ms、最大 173.3 ms でした。

SERVICE の最大 16.2 ms は、カードなしの 6 時間 (6.2 ms) と 120 秒の同時動作 (6.7 ms) より長い値です。

CPU 使用量もカードなしの 44〜46% より低く、SERVICE の回数と CPU 使用量は対応しています。  
カードの操作が制御ロックを取る間は SERVICE が待つため回数が減る、という説明が考えられますが、カードなしの 10 分の受信でも毎秒約 1,230 回だったため、カードの操作だけでは回数の違いを説明できません。

## 機器の着脱とデーモンの寿命

デーモンは libusb のホットプラグ通知で接続と切断を受け取ります。  
切断を検出したら、利用可能を示す状態を制御ロックの下で無効にし、カードのセッション、受信中の読み出し、ファームウェアの状態をまとめて破棄します。  
受信スレッドや開いたままのデバイスファイルが参照を持つため、一覧から外すことと、オブジェクトを解放することを分けて扱います。

切断後のデバイスファイルは、カーネルモジュールでは USB 機器とともに消えます。  
CUSE では、開いている利用者がいる間もセッションを残して `-EIO` を返し、全員が閉じてからセッションを終える形が、カーネルの挙動に最も近いと考えます。  
挿し直した機器には、空いている最小の番号で新しいデバイスファイルを作ります。

1 台の PIX-DT295 は、受信とカードの 2 つの CUSE のセッションを持ちます。  
試作は受信のセッションを `cuse_lowlevel_main` で動かしましたが、機器の数が実行中に増減する本実装では、すべてのセッションを `cuse_lowlevel_new` で作り、それぞれ専用のスレッドで `fuse_session_loop` を回します。  
終了のシグナルは main スレッドだけが受け、ほかのスレッドは試作と同じくシグナルを遮断した状態で作ります。  
セッションを終えるときは、`fuse_session_exit()` の後、ループが終わるまで `SA_RESTART` なしの SIGUSR1 をそのスレッドへ送ります。  
`/dev/cuse` の `read` で待つスレッドは、別のスレッドが fd を閉じても起きないためです。

pcscd はカードのデバイスファイルを開いたまま保持するため、機器を抜いた後も、pcscd が閉じるまでカードのセッションは終わりません。  
同じ機器を挿し直すと、リーダーの ID が同じため、古いセッションと同じ `/dev/px4card/<ID>` を作ろうとして名前が衝突します。  
デーモンは、古いセッションが終わるまで新しいカードのセッションの作成を保留し、古いセッションの終了を契機に作成します。  
受信のデバイスファイルは空いている最小の番号を使うため、この保留は不要です。

WinUSB 版では、古いファームウェアが RAM に残った場合に USB の抜き差しが必要です。  
デーモンが異常終了したあとの再起動で同じ状態になるかは未確認で、復旧の手順を実機で確かめます。

## 権限と導入

`/dev/cuse` は既定で root だけが開けます。  
`/dev/cuse` を開けるプロセスは任意の名前でデバイスファイルを作れるため、試作で使った、udev の規則で `/dev/cuse` を plugdev グループへ開く方法は、配布の形には採用しませんでした。  
ログインユーザーへこの権限を広げると、ほかのデバイスの名前を先に取る操作を許すためです。

デーモンは Debian の pcscd と同じく root で動かし、systemd のユニットで権限を絞ります。

| 設定 | 目的 |
|---|---|
| `CapabilityBoundingSet=` (空) | root の特権を持たせず、所有者として `/dev/cuse` と USB 機器を開くだけにする |
| `DeviceAllow=/dev/cuse rw`、`DeviceAllow=char-usb_device rw` | 開けるデバイスを限定する |
| `ProtectSystem=strict`、`ProtectHome=yes`、`PrivateTmp=yes` | ファイルシステムへの書き込みを止める |
| `RuntimeDirectory=` | IFD ハンドラーへ渡す、USB 機器とカードのデバイスファイルの対応表を `/run` の下に置く |

作ったデバイスファイルは、既存の機種と同じ 664 になるよう udev 規則を用意します。  
カードのデバイスファイルには、試作で確かめた `SUBSYSTEM=="cuse", KERNEL=="px4card/*"` の規則で権限を与えます。

配布はカーネルモジュールと別の Debian パッケージとし、libusb-1.0 と libfuse3 に依存します。  
DKMS は不要です。  
CUSE のデバイスファイルを Docker コンテナへ `--device` で渡して使えるかは未確認です。

## 試験

実機試験は、冒頭で定義した検証環境で行います。  
検証環境は arm64 のため、x86_64 でのビルドと動作は別に確認し、試験の記録には CPU アーキテクチャを記載します。  
Raspberry Pi 4 の USB ポートは合計の給電量に上限があるため、公式の 5V 3A の電源を使い、USB ハブを経由しない接続を基準とします。  
ハブを経由した接続や、同じ USB コントローラーへ SSD をつないだ構成で試験する場合は、その構成を記録に明記します。

BS の TS は 1 時間で約 10 GB になり、SD カードへの書き込みは速度と寿命の点で長時間の試験に向きません。  
長時間受信の試験では、TS を保存せずに同期エラー、TEI、連続性の飛び、空受信の時間を計数します。  
受信中は SERVICE が待機なしで続くため、長時間の試験の記録には CPU 温度と、熱による速度の低下の有無も残します。

### 自動試験

- 共有へ移した SERVICE のループと受信の停止手順を、既存の模擬 USB の試験で Windows と Linux の双方から実行する。
- CUSE の受信のデバイスファイルを模擬の機器で動かし、`open`、各 ioctl の戻り値、`read` と `poll` と `O_NONBLOCK`、切断後の `-EIO` を、カーネルモジュールの `ptx_chrdev` と比べる。
- `PTX_GET_CNR` の応答で、利用者のメモリーの `int` の直後が変わらないことを確かめる (試作と同じ確認を、実装の回帰試験として残す)。
- カードのデバイスファイルを、px4-drv-pcsc の既存の試験から開けることを確かめる。

### 実機試験

- recpt1 で地デジ・BS・110度CS を選局し、BS と CS では相対 TS 番号と TSID の双方を試す。
- 長時間受信で、同期エラー、TEI、連続性の飛び、空受信の時間を分けて記録する。
- pcscd で内蔵カードリーダーを使いながら受信し、APDU の失敗数と SERVICE の最大所要時間を記録する。
- 受信中の USB の抜き差し、カードの抜き差し、デーモンの再起動からの復旧を確かめる。
- 他の px4_drv の機種と同時に使い、カーネルモジュールと干渉しないことを確かめる。

### 本実装の確認

本実装のデーモン (`cuse/`) を検証環境でビルドし、利用者として起動したものと、systemd のユニットで導入したものの双方で確かめました。  
カードの抜き差しと、本実装での長時間の受信は、この時点では確かめていません。

| 試験 | 結果 |
|---|---|
| `make -C cuse check` (arm64) | WinUSB 版と共有する制御経路、選局の換算、SHA-256 と組み込みファームウェアの試験がすべて成功 |
| recpt1 で地デジ 13ch を 30 秒 | 29.96 Mbps、同期、TEI、CC の飛び、形式不正がすべて 0 件、`read` の間隔は最大 3 ms、終了時の復元が成功 |
| カードのデバイスファイルを直接開いて 20 回 (受信なし) | ATR 13 バイト (318 ms)、20 回すべて成功、平均 73.5 ms |
| 受信中にカードを 300 回 | 300 回すべて成功、平均 65.8 ms、TS のエラーは 0 件 |
| 2 つ目の `open`、2 回目の `START_STREAMING` | どちらも `EALREADY` |
| `O_NONBLOCK` と `poll`、`STOP_STREAMING` の後の `read` | `poll` で起床し、188 バイト単位で読め、停止後は EOF |
| 受信中に SIGTERM | 0.22 秒で終了し、復元が成功し、両方のデバイスファイルが消えた。再起動後も受信できた |
| systemd のユニットで起動 (特権なし、`DeviceAllow` と `ProtectSystem=strict`) | 両方のデバイスファイルと `/run/px4-dt295/readers` を作り、udev の規則で受信は `root:video 0664` になった。地デジ 13ch の 20 秒の受信はエラー 0 件 |
| reader.conf の登録なしで、pcscd のホットプラグから接続して 50 回 | リーダー名 `PIXELA PIX-DT295 Smart Card Reader`、`SCardConnect` は 328 ms、50 回すべて成功、平均 80.2 ms |
| 受信していない間に USB を抜き差し | 切断の 5 ms 後に両方のデバイスファイルを消し、再接続の 77 ms 後に作り直した。対応表も新しいデバイス番号へ更新され、続く 20 秒の受信はエラー 0 件 |
| 受信中に USB を抜き差し | 切断で SERVICE の制御転送が `-EIO` で失敗して受信を止め、それまでの TS はエラー 0 件。recpt1 が開いたままの `/dev/dt295video0` は閉じられるまで残り、再接続した機器は `/dev/dt295video1` とカードのデバイスファイルを直ちに作った。recpt1 が閉じると古いデバイスファイルが消え、`/dev/dt295video1` の 15 秒の受信はエラー 0 件 |

pcscd のホットプラグ経由の APDU の平均 (80.2 ms) は、試作で reader.conf に登録したときの平均 (72.8 ms) より約 7 ms 長く、原因は調べていません。  
検証環境に `pcscd` グループがないため、カードのデバイスファイルは `root:root 0660` になり、root で動く pcscd が開きました。

systemd のユニットに最初に設定した `PrivateNetwork=yes` では、切断は検出できても再接続した機器を認識しませんでした。  
libusb は接続の通知をカーネルの uevent (netlink) で受け取り、uevent は初期のネットワーク名前空間にしか届かないためで、`RestrictAddressFamilies=AF_UNIX AF_NETLINK` に置き換えました。  
切断は libusb が開いている機器の fd で検出するため、この設定の影響を受けませんでした。  
また、最初の実装では受信のデバイスファイルが開かれている間、使われていないカードのデバイスファイルも残し、再接続した機器のカードの作成が受信の終了まで保留されたため、切断の時点で開かれていないセッションをすぐに止めるよう直しました。

WinUSB 版は、共有のクラスへの切り出しの後に x86 と x64 でビルドし、実機なしの試験 (`run_dt295_tests.py`、追加した `dt295_control_channel_test` を含む) がすべて成功しました。  
Windows で PIX-DT295 を使った回帰試験はまだ行っていません。

## 未決の事項と未確認の条件

- Windows 版の PIX-DT295 の実機での回帰試験 (`channel_switch_stress`、`card_stream_stress`)。共有のクラスへの切り出しは、x86 と x64 のビルドと実機なしの試験だけを確認済み
- 32 ビットのプロセスへの対応 (`PTX_GET_CNR` の応答の大きさは試作で確認済み)
- 機器を抜いてから pcscd が古いカードのセッションを閉じるまでの時間と、挿し直した後にカードを使えるようになるまでの時間 (セッションの終え方と作成の保留は「機器の着脱とデーモンの寿命」で決定済み)
- pcscd のホットプラグ経由の APDU が、reader.conf で登録したときより約 7 ms 長い原因 (ホットプラグでの接続と 50 回の APDU は本実装で確認済み)
- PIX-DT295 のカード UART の 1 回の送受信の上限
- 受信とカードの同時動作で SERVICE の 1 回の所要時間が最大 16.2 ms になった時期 (受信中か停止の手順の中か)。6 時間の同時動作での APDU の失敗は 0 件。本実装は最大値の時刻を記録する
- pcscd がカードを使っている最中に機器を抜き差ししたときの、カードのデバイスファイルの解放と作り直し (受信していない間と受信中の抜き差しは確認済み)
- Docker コンテナからの利用
- Raspberry Pi 4 の USB コントローラー (VL805) で、カード通信と同時に長時間受信したときに制御転送の間隔を保てるか (地デジでは、カードなしの 6 時間の受信と、カード通信と同時の 6 時間の受信を試作で確認済み)
- SERVICE のループへ待機を入れるかどうかと、その長さ (検証環境では 1 コアの約 20〜46% を占め、SERVICE の回数が変わる条件は未確認)
- BS・110度CS の長時間の受信 (各 20 秒の受信は外部からのアンテナ給電で確認済み)
