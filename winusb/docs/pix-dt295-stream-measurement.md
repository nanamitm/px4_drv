# PIX-DT295 SERVICE・Bulk・機器内リングの実測

測定日: 2026-11-07 JST。Windows x64、利用者申告Rev.01 / TC90532XBG、WinUSB、地デジ・BS/CS接続、LNB電源0。ファームウェアはmAgicVISION 0.1.1の未改変バイナリー（SHA256 `0b2147e190afc7626165594fdedbedc6461c0e1f044b17742123b77fc5026fcc`）。独立ソース生成ファームウェアやpix-userlandを起動した測定ではありません。

## 結果

通常条件で、SERVICE間に届くBulk量がほぼ常に32 KiBとなることを実測しました。ホストのTS処理時間に比べ、SERVICEの同期往復が大きな時間を占めています。制御往復と有限の送出枠が転送能力を制限する、という静的解析との対応があります。

ただし、今回のリング位置採取は追加USB要求により測定対象へ負荷を加えます。リング満杯に近い状態を観測できたのはその追加負荷条件であり、通常条件のリング上書き・入力欠落位置まで確定した結果ではありません。

## 通常条件: 各30秒

以下のCCは保存TSの独立解析です。レートはHostのBulk完了時刻・実長から計算し、保存区間とは開始停止境界が異なります。

| 対象 | 保存TSパケット | CC異常 | SERVICE開始間隔平均 | Bulk実効レート |
|---|---:|---:|---:|---:|
| CS ND02 | 462,848 | 23,775 | 11.268 ms | 23.18 Mbps |
| GR13 | 391,168 | 13,688 | 13.304 ms | 19.67 Mbps |
| BS01/TS0 | 346,112 | 0 | 15.034 ms | 17.38 Mbps |

SERVICE終了時点の累積Bulk実長を差し引くと、CSは2669区間中2668区間、GRは2256区間中2255区間、BSは1997区間すべてが32768 bytesでした。その他は開始境界の0 bytesです。FIFO補充関数の「512 bytes×成功64回」と強く対応しますが、FIFO内の成功・待ち回数自体を直接取得した結果ではありません。

Bulk受信完了をHostが観測してから、フレーム化・TS監視・共有バッファー書込を終えるまでの時間は、CS/GR/BSの平均が約42/42/45 us、最大284/283/236 usでした。USB要求再投入の直前までの処理時間で、機器やOSが完了通知を届けるまでの時間は含みません。これに対しSERVICE開始間隔は11～15 msです。

この結果は固定の19.7 Mbps上限を意味しません。呼出し周期が変動するため、今回の実効レートはCS約23.2、GR約19.7 Mbpsとなりました。

## リング位置読出しあり: 各10秒

SERVICE終了後、TSエンジンの `0x01902020..0x0190202F` だけを既存のUSBウィンドウ経由で読みました。対応はring base、ring size、生産位置、消費位置／read limitです。既存の制御ロック内で一時的なマッピングを行い、元のウィンドウ値への復元と読戻しを検証しています。ファームウェアのコードやTSエンジン設定へのパッチはありません。

読出し1回は6回の制御転送となり、平均約18.0 msかかりました。この負荷によりSERVICE開始間隔は約29.5～31.5 ms、Bulkは約8.3～8.9 Mbpsへ低下しています。

| 対象 | 有効リングサンプル | リング容量 | 未読量の範囲（位置の差を容量で剰余） | 保存TSのCC異常 |
|---|---:|---:|---:|---:|
| CS ND02 | 341 | 196,608 bytes | 196,416～196,544 bytes | 3,562 |
| GR13 | 321 | 196,608 bytes | 196,416～196,544 bytes | 2,736 |
| BS01/TS0 | 341 | 196,608 bytes | 196,416 bytes | 1,794 |

ring baseは `0x0138EC00`、容量は192 KiBでした。生産・消費位置の差は容量の99.90～99.97%に相当し、この追加負荷条件ではほぼ満杯です。全サンプルの診断読出しとSERVICEは成功しました。

位置は周回するため、サンプル間の生産量は剰余差の下限しか示しません。実際のRF入力レート、複数周回、リング上書き回数、入力抑止による欠落、FIFO待ち回数をこのデータだけで同定することはできません。追加読出しの前半にも時間がかかるため、通常のSERVICE終了直後のリング占有量として扱うこともできません。

## 読出しを外した再測定: 各15秒

| 対象 | 保存TSパケット | CC異常 | SERVICE開始間隔平均 | Bulk実効レート |
|---|---:|---:|---:|---:|
| CS ND02 | 230,400 | 11,857 | 11.296 ms | 23.03 Mbps |
| GR13 | 230,400 | 5,842 | 11.277 ms | 23.17 Mbps |
| BS01/TS0 | 173,056 | 0 | 14.993 ms | 17.36 Mbps |

追加読出しを外すとレートが回復し、BSの保存区間のCC異常も0へ戻りました。GRのレートは最初の通常試験より高い一方、欠落は残っています。各試験の時間が異なるため、CC件数の大小だけで改善度を比較することはできません。

9本すべての保存TSで同期・TEI・形式・PAT CRC異常は0、要求TSIDとの一致を確認しました。内蔵カードによる復号や視聴成功の試験ではなく、スクランブルされたTSを含みます。BSのHost入力全区間には通常・再測定ともCC異常9件があり、保存区間の0件を開始停止込みの無欠落と表現することはできません。

## 切り分けとして分かったこと

- 32 KiBの送出枠とSERVICE周期に対応する転送能力の制約は、静的解析だけでなく実測でも確認できた。
- 今回の計測範囲では、Bulk完了後のホストTS処理はSERVICE往復より十分短い。
- SERVICEの間にUSB制御要求を追加すると転送速度が落ち、通常は保存区間CC 0のBSにも欠落が発生し、要求を外すと回復した。受信がSERVICEの実行頻度に依存する証拠になる。
- 復調ICのリビジョン差を原因と断定する結果ではない。通常時のリング満杯・上書き・入力抑止のどれが欠落を起こすかは未確定。

次は、追加USB往復を伴わずにSERVICE内の生産・消費位置とFIFO成功・待ち回数を応答へ載せる診断が必要です。現行ファームウェアの公開状態にはこれらのカウンターがないため、今回のホスト側診断ではFIFO成功・待ち回数を個別計測できていません。ファームウェア側で観測点を作る場合も、送出枠や復調器設定を同時に変更しない対照試験が適切です。

## 実装・検証・終了状態

診断は `DT295_STREAM_TRACE_DIR` 指定時だけ有効です。`DT295_STREAM_TRACE_RING` の指定で毎SERVICE後のリング読出しが加わります。SERVICEとBulkは各スレッド専用の上限100000行のメモリーへ追記し、スレッド回収後にCSVへ保存するため、受信中のCSVファイルI/Oはありません。計測時刻は受信開始を基準とするsteady clockのusです。

x86/x64 Hostビルドとbootstrap / loader / session / USB window / stream input / transport / runtime、torne runtimeの模擬試験が通りました。runtime試験では、固定MMIO範囲の読出し、ビッグエンディアン変換、読出し失敗時のウィンドウ復元、停止中・torneでの診断要求拒否を確認しています。

最初の測定用Host起動は通常Hostと同じ排他名を使ったため終了しました。その後、既存の `PX4_ISOLATED_TEST_HOST` により排他・パイプ名を分離したHostへ切り替え、測定が成立しています。測定用Hostは全試験後に通常終了し、既存のTVTest・EDCB・DriverHostのPIDは変化していません。PIX-DT295のPnP problem codeは0でした。開発用TVTestへのデプロイ、コミット、pushは今回の範囲外です。

## SERVICE応答内の計測による追試

[追加USB要求なしの計測](pix-dt295-service-telemetry.md)で、診断版のCS・地デジはSERVICE開始時にリング占有99%以上、BSは中央値約15 KiBと分かりました。安定区間はすべて64成功で終了しており、FIFO待ちによる4096試行上限到達はありませんでした。
