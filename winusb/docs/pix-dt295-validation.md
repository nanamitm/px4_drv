# PIX-DT295実機検証（2026-11-06）

mAgicVISION 0.1.1とpix-userlandの追加試験は[ファームウェア比較](pix-dt295-fw-comparison.md)を参照してください。

Windows 11 Pro x64（10.0.26300）、PIX-DT295 `06b8:103b`、地デジ・BS/CSアンテナ接続済みの構成で検証しました。WinUSBドライバー1.0.0.1の問題コードは0で、専用インターフェースから機器を開けています。アンテナ給電設定は0です。

試験コードの基準は `70301a0`、ファームウェアは [PIX-DT295の説明](pix-dt295.md) に記載した289,424-byteのSBC2コンテナー（SHA-256 `d9f549b29d286c2ff1e7daf4237e2205bb8a5a2affbb98362bce137b8b42a33f`）です。今回の実測はmAgicVISION方式であり、ソースビルドFRファームウェアのDT295用HALを検証した結果ではありません。

既存の受信Hostと衝突しないよう、HostとBonDriverを `RtlSdrIsolatedTest=true` でビルドし、PIX-DT295だけの機器定義を置いた専用フォルダーから実行しました。通常版と試験用版はx86/x64ともビルド成功、bootstrap / loader / session / USB window / stream input / transport / runtimeの模擬試験も両アーキテクチャで合格しています。

## 初回の問題と残した変更

初回の地デジGR13・GR17は各10秒で110,592 / 109,568パケットを受信したものの、CC異常が4,313 / 4,116件あり、試験は失敗しました。同期・TEI・形式エラーは0でしたが、HostのUSB入力直後にもCC異常があり、BonDriverより前で起きていることを確認しました。

SERVICEの `WaitForSingleObject(1ms)` を計測すると、実際の呼出し間隔は平均15,554µsでした。同じ1msを既存の高精度waitable timerで待つように変更すると、地デジのSERVICE間隔は約8.7msとなり、受信量とCC異常が大きく改善しました。呼出し間隔にはUSB要求自体の処理時間も含まれます。失敗・キャンセル・タイムアウトの条件は維持しています。

終了時の診断ログへSERVICEの回数・平均/最大間隔・最大呼出し時間、およびUSB読出しの最大間隔を追加しました。読出しキュー拡大、優先度変更、先行再投入、SERVICE間の待機削除、供給時計の変更も比較しましたが、CSのCC異常を一貫して解決する根拠が得られず、最終差分には含めていません。

## 最小修正版のx86実測

同じOpenでGR13→BS01/TS0→CS ND02を各10秒測定しました。

| 放送方式 | space:index | 選局時間 | 最初のTS | パケット | 同期 / TEI / CC / 形式 |
|---|---|---:|---:|---:|---|
| GR13 | 0:0 | 4,735ms（初回初期化込み） | 72ms | 198,656 | 0 / 0 / 0 / 0 |
| BS01/TS0 | 1:0 | 517ms | 170ms | 114,688 | 0 / 0 / 0 / 0 |
| CS ND02 | 2:0 | 554ms | 73ms | 259,072 | 0 / 0 / 0 / 0 |

測定対象は合計572,416パケット、最大空受信間隔170ms、末尾の無受信は最大90msで、診断は終了コード0でした。Close後のHostはアイドル終了しました。独立した試験プロセスでのClose→Openと、地デジ・衛星の切り替えも繰り返し成立しています。

ただしHostがフレーマーから取り出した全区間には、CSの `cc_jump=29 / same_cc_changed=1` と、各区間の初期同期破棄96 / 40 / 40 bytesが記録されています。BonDriverのPurgeと初期バッファ破棄後の測定が0でも、開始・終了を含む全経路無欠落とは扱えません。

## 追加比較で残った問題

最終的に残した最小修正版のx64でも、CS ND02→GR13→BS01/TS0を各30秒測定しました。

| 放送方式 | パケット | 同期 / TEI / CC / 形式 | 選局時間 | 結果 |
|---|---:|---|---:|---|
| CS ND02 | 628,736 | 0 / 0 / 24,575 / 0 | 3,868ms（初回初期化込み） | 失敗 |
| GR13 | 596,992 | 0 / 0 / 0 / 0 | 1,370ms | 測定区間は合格 |
| BS01/TS0 | 345,088 | 0 / 0 / 0 / 0 | 487ms | 測定区間は合格 |

この試験は全体として終了コード1です。CSのSERVICE間隔は平均8,286µs、HostのCC jumpは24,583件で、後段の保存TSにも異常が残っています。x86の10秒成功とx64の30秒失敗は、測定時間とアーキテクチャが異なり、アーキテクチャだけを原因とする比較ではありません。

比較用のキュー拡大版では、GR13 / GR17 / BS01 / BS03 / CS ND02 / GR13を各30秒受信し、CC異常は0 / 0 / 6 / 17 / 17,668 / 0件でした。独立したTS解析でも同じ件数と、要求したPAT TSIDを確認しています。優先度・時計等を変えたCSの各20秒試験でも約11,000件のCC異常が続きました。これらは最小修正版の合格結果には含めていません。

短時間の成功から長時間・全放送方式の安定性を推定することはできません。残る切り分けは、SERVICEの処理量と実際の入力レート、USB制御転送とBulkの待ち合わせ、開始・停止時のデータ境界です。パケット整列エラーやPAT CRC異常の有無だけでCCの欠落を成功へ読み替える判定はありません。

## 再現方法と範囲

`experimental/torne/bondriver_probe` は `space:channel-index` 形式で放送方式をまたぐ診断が可能です。従来の単一番号はspace=0を表し、`--list` は全spaceを列挙するだけで機器を開きません。

```text
torne_bondriver_probe.exe <absolute-dll-path> --list
torne_bondriver_probe.exe <absolute-dll-path> --receive 0 1:0 2:0 --measure-ms 10000
```

`TORNE_PROBE_CAPTURE_DIR` を指定すると測定TSを保存できます。衛星ファイル名はspaceとインデックスを含みます。188-byteの保存TSは `experimental/dt295-firmware/tools/check_capture.py --ts-only --expected-tsid ...` でPAT CRC・TSIDも検査できます。後段の188-byte TSだけから、初期同期・Purge等で破棄された入力を検証することはできません。

今回の確認対象は初期化、選局、TS受信、放送方式の切り替え、Closeと再Openです。MULTI2復号、映像・音声再生、内蔵カード、CNR、アンテナ給電、物理抜去、スリープ復帰、数時間録画は未検証です。CNR未実装のため診断の `signal=0` は受信品質の測定値ではありません。
