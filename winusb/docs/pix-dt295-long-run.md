# PIX-DT295 長時間受信（2026-11-11〜12）

TVTest で PIX-DT295 を数時間ずつ連続して受信し、TS の欠落、TS リングの滞留、SERVICE の間隔を記録した結果です。

この文書の「検証環境」は次の構成を指します。

- Windows 11 Pro x64（10.0.26300）、USB 2.0 High Speed で接続した PIX-DT295（`06b8:103b`、利用者申告 Rev.01）1台
- 内蔵カードリーダーに B-CAS カード1枚、地デジアンテナと BS/110度CS アンテナ（外部から給電）
- 64ビット版 TVTest と同じフォルダーに x64 版の `BonDriver_DT295.dll`、`DriverHost_PX4.exe`、`WinSCard.dll` を配置
- `DriverHost_PX4.ini` は `Experimental=true`、`FirmwareBackend=direct-fr`、`DebugLog=true`。`BonDriver_DT295.ini` は `DebugLog=true`

DriverHost は受信段（Bulk 受信の直後）で、BonDriver は TVTest へ渡す直前で、それぞれ TS の連続性を数えています。両方の値を比べると、欠落がホストより手前で起きたか、ホスト内で起きたかを区別できます。

## 結果

### 1回目（develop `0c087d6`）

| 受信 | 時間 | BonDriver の出力 | 異常（BonDriver） | 異常（DriverHost） | 未送信量の最大値 |
|---|---|---:|---|---|---:|
| 地デジ 17ch（497.143 MHz） | 05:02〜06:53（1時間51分） | 132,173,824 | 0 | 0 | 2,205,462 |
| 地デジ 13ch（473.143 MHz） | 06:53〜06:57 | 5,568,512 | 0 | TEI 11 | 526 |
| 地デジ 15ch（485.143 MHz） | 06:57〜07:04 | 8,342,528 | 0 | 0 | 526 |
| 110度CS ND06（TSID `0x7060`） | 07:04〜09:00（1時間55分） | 180,468,736 | 0 | 0 | 524 |

「異常」は同期、TEI、CC の飛び、形式不正の合計です。4区間の合計は約3時間58分で、BonDriver の出力に異常はありません。

13ch の TEI 11件は、同じチャンネルで前日にも8〜13件あり、電波の弱さによるものと考えています。DriverHost では TEI を数えた一方、BonDriver の出力では0件だった理由は確認していません。

17ch の区間では、未送信量が最大 2,205,462 バイト（6 MiB のリングの約35%）まで増え、SERVICE 1回の最大が 238,344 µs でした。リングが溢れる前に送り出せたため、欠落はありません。受信終了時の集計値しか残っておらず、いつ、何がきっかけで増えたかは特定していません。この原因を調べるため、未送信量が増えた前後の SERVICE、カード操作、Bulk 受信の時刻を残す記録（`StallTraceDir`）を別の変更で追加しています。

### 2回目（`d63e6de` に滞留の記録を加えたビルド）

`StallTraceDir` を有効にして、110度CS ND06 を 09:55〜12:38（2時間44分）受信しました。

| 項目 | DriverHost | BonDriver の出力 |
|---|---:|---:|
| パケット | 255,761,255 | 255,759,360 |
| CC の飛び | 1 | 1 |
| adaptation field だけのパケットの CC の不一致 | （集計の対象外） | 1 |
| 同期、TEI、形式不正 | 0 | 0 |

- 12:30:00.514 に PID `0x0601` で CC が 15 から 10 へ飛び、12:30:01.660 に PID `0x1201` の adaptation field だけのパケットで CC が 3 から 7 へ変わりました。
- DriverHost の受信段でも数えているため、ホストに届いた時点で欠けていました。
- 未送信量が 1 MiB を超えた記録はなく、リングの3/4を超えた SERVICE も0回でした。
- リングの溢れなら、その区間を流れていた全 PID で CC が飛びます。今回は1つの PID だけで、時刻は30分の番組の切り替わりでした。放送側の不連続の可能性が高いと考えていますが、放送と機器内の欠落を区別できる記録はなく、確定していません。
- 集計の `peak_pending=531,531` と `max_call_us=116,289` は、受信停止時の値です。ログで `reader end` が `service calls` より先に記録されており、Bulk 受信が止まった後に最後の SERVICE が約0.1秒詰まったときの値と一致します。受信中の滞留ではありません。

## SERVICE の間隔

1回目の110度CS では SERVICE の平均間隔が 486 µs、2回目は 3,671 µs でした。同じ110度CS ND06 で3種類のビルドを、カード負荷なしとあり（`card_stream_stress`、基準45秒と並行1秒、または基準5秒と並行45秒）で受信して比べました。

| ビルド | カード | 1回の送出量 | SERVICE の平均間隔 | 送出量 ÷ 間隔 |
|---|---|---:|---:|---:|
| `0c087d6` | なし | 18,493 B | 3,780 µs | 4.89 MB/秒 |
| `0c087d6` | あり | 27,073 B | 5,535 µs | 4.89 MB/秒 |
| `d63e6de` | なし | 2,420 B | 494 µs | 4.90 MB/秒 |
| `d63e6de` | あり | 2,571 B | 525 µs | 4.90 MB/秒 |
| 滞留の記録を加えたビルド | なし | 2,433 B | 496 µs | 4.91 MB/秒 |
| 滞留の記録を加えたビルド | あり | 26,847 B | 5,488 µs | 4.89 MB/秒 |

- どのビルドでも、受信ごとに「約0.5ミリ秒間隔で約2.4 KBずつ」と「約4〜5ミリ秒間隔で約18〜27 KBずつ」のどちらかになり、中間の値は出ませんでした。カード負荷の有無とも対応しません。
- 1回の送出量を間隔で割ると、どの受信も ND06 の流量（約4.9 MB/秒）と一致します。機器側のリングの書き込み位置が進む単位が受信ごとに異なり、SERVICE はその単位を待って戻っていると考えられます。
- 間隔が長い受信では、SERVICE の要求を送る制御転送1回が平均約3.5ミリ秒かかります。
- どちらの受信も TS の異常は0（DriverHost の受信段）で、APDU は1分あたり約510〜520回成功しました。
- どちらになるかを決める条件は調べていません。

試験ツールは、どの受信でも開始直後の区間で CC の不一致を35〜38件数えました。DriverHost の受信段では0件で、[TSリング](pix-dt295.md#tsリング) に記録した試験ツール側の計数と同じ傾向です。

## 内蔵カードリーダー

- 両方の受信で `WinSCard.dll` を配置し、内蔵カードリーダーを使いました。TVTest のスクランブル数は記録していません。
- 受信の前に、TVTest がカードの状態を取得できず `SCARD_E_TIMEOUT` を表示したことがありました。このときカードは挿入ありと検出され、電源投入の手順もレジスターの値どおりに書き込まれていましたが、ATR は1バイトも届かず、受信 FIFO と状態レジスターの受信フラグも変化しませんでした。カードを挿し直すと、選局の前、受信中、再オープンの後のいずれでも13バイトの B-CAS ATR を受信し、APDU が成功しました。検出スイッチだけが押され、接点が当たっていない状態だったと考えています。

## 確認していない条件

- x86 版の実機での受信
- BS の長時間受信（BS01/TS2 での短時間の受信だけを確認）
- USB の抜き差し、無信号、スリープ復帰
- 1回目の17ch で未送信量が増えたきっかけ
- SERVICE の間隔が受信ごとに2通りに分かれる条件
