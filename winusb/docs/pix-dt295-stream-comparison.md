# PIX-DT295: pix-userlandとmAgicVISIONのTS転送経路

## 比較範囲と結論

対象は公式由来D295A1ファームウェアを使うpix-userlandのDT295経路、DT295-TVTest-Kit 1.1同梱版、およびmAgicVISION 0.1.1常駐コードと現在のWindows DriverHost実装です。比較用pix-userlandは42364ad、mAgicVISION公開ホスト側はe1b1280。キットは1d606beを基準とする変更版です。今回の調査は保存済みソース、常駐コード、以前取得した実測ログによる静的比較で、追加の実機試験はありません。

復調器の型番差より具体的な候補として、mAgicVISIONのTS送出がホストのSERVICE往復と、有限回のUSB FIFO補充処理に依存することが確認できました。pix-userlandの受信ループには、各ブロックを出すための同等のSERVICE要求がありません。PID選別の有無と合わせ、両者の受信負荷は大きく異なります。

## 経路の比較

| 段階 | pix-userland / キット | mAgicVISION / DriverHost |
|---|---|---|
| 機器側の受信プログラム | 公式由来TRCをアップロード | 独自常駐コードと機器内TSエンジン |
| 出力対象 | 最大64スロットのPID経路を設定。PATは暗黙スロット | 解析した送出処理はリングを順番に読み、PIDによる分岐がない。現在の経路は全多重TS |
| 開始 | prepare後、command(5,0,2)でstate 2へ | TUNE/STREAM要求後、SERVICEで状態と送出を進める |
| 定常時の機器制御 | 認証更新・経路更新・状態確認等。ブロックごとのSERVICEなし | SERVICEごとに制御OUTと制御INの同期往復 |
| USB受信 | EP81、8本×65536 bytesの非同期Bulk | EP81、4本×16384 bytesの非同期Bulk |
| 受信後の待避 | 32 MiBリングへコピー後、USB要求を再投入 | フレーム化・TS監視・共有バッファー書込後、USB要求を再投入 |
| TS処理 | 188-byte単位で転送用暗号を解除し、番組情報・経路を更新 | 生TSをフレーム化して配信。内蔵カードによる復号経路ではない |

8本・64 KiB・32 MiBは保存した上流とキット双方で確認した値です。USB要求容量とホスト側待避容量は別物で、mAgicVISION側の共有TSバッファーも約12.3 MBあります。ホストバッファーだけを増やしても機器側の送出ペースが上がるとは限りません。

## mAgicVISIONの機器内処理

以下のアドレスは0.1.1の常駐領域です。SHA256は `d3ae3dd104d4f4280ed37e29658e67690c482d3843baf972f1edc3ce3d570743`。

1. 共通SERVICE処理 `0x80381B44` は機種別テーブルのoffset 0x14を呼ぶ。DT295テーブル `0x803ADFE4` の該当値は `0x8039927C`。
2. DT295処理は通常の選局状態機械に加え、capture状態に応じて `0x8039986C` を呼ぶ（呼出し命令 `0x80399432`）。
3. `0x8039986C` は `0x80399668` を反復する。試行予算は4096回。戻り値0の成功を64回数えると終了し、負値でも終了する。成功以外の戻り値では成功数を増やさず、試行予算を消費する。
4. `0x80399668` はTSエンジンの `0x01902028` と保持した読出し位置から残量を調べる。同期獲得時には192-byte間隔の3か所で47を探す。十分な入力があると `0x8038328C` を呼ぶ。
5. `0x8038328C` は `0x00FDBD0C` のbit 04が立っている場合に、`0x00FDBD84` へ32bit値を128回書く。1成功512 bytes。188-byteのTS部分を詰め、入力リングの位置を192 bytesずつ進める。成功後にFIFOコミット操作と読出し位置更新がある。
6. 成功したステップは `0x0190202C` へ更新したリング読出し位置を書き戻す。

従って、この反復関数1回での送出量の上限は64×512 = 32768 bytesです。これは反復関数単体の上限であり、全コールバック・開始停止を含む「SERVICE全体の厳密な上限」と同一視できません。テーブルoffset 0x34の別コールバックから1ステップを呼ぶ経路もあります。

旧版にも同形の反復関数（0x80397CD8）とFIFO詰め込み関数（0x80383284）が存在します。新版だけに導入された処理方式ではありません。公式TRC側の内部DMA・割り込み・FIFO補充実装の全逆解析は今回の範囲外です。

## 以前の実測との整合

同じ新版を使った保存済みCS試験では、SERVICE 1505回、平均呼出し間隔13299 us、raw受信49496064 bytesでした。受信全区間とSERVICE計数区間には開始停止の差があるため概算ですが、約32888 bytes/回で、反復処理の32768 bytesと近い値です。

32768 bytesを13.299 msごとに送るモデルは約2.464 MB/s（19.71 Mbit/s）です。これはUSB High-Speedの理論限界ではなく、この呼出し周期と処理単位から計算した値です。RF側の実際の入力レート・リング上書き発生を計測した結果ではありません。

同じログのcapture-stop集計は制御IN平均約2.99 ms、OUT平均約9.10 msです。OUTには常駐処理の実行待ちを含むため、Windows側スケジューリングと機器内処理へ分離できていません。このログでは入力段階にCC jump 14670があり、framing desyncは0、同期獲得時の破棄は40 bytesでした。下流配信だけの問題では説明できない一方、入力TSの欠落位置を機器内のどこかへ確定する証拠も不足しています。

## 原因候補の優先度

- 最優先: SERVICE往復の待ち時間、512-byte単位の送出、64成功・4096試行という処理予算の組合せ。実測との対応がある。
- 並行確認: PID選別後の公式経路と全多重経路の負荷差。キットの短時間CC 0だけでは全多重受信の余力を比較できない。
- 次点: USB要求の本数と大きさ、完了後の再投入までのホスト処理時間。4本から8本への変更だけで上記の機器内処理制約が解消する根拠はない。
- 残る候補: 復調器初期化の差、入力ポート・クロック・TSエンジン設定。初期化比較は[復調器・RF設定](pix-dt295-demod-comparison.md)を参照。

現時点でリングの上書き、FIFO待ち時間、受信入力レートを同時に観測できていないため、欠落原因の確定や修正完了とは扱えません。ICリビジョン別対応を先に追加する根拠も不足しています。

## 次に必要な対照試験

まず、機器内の生産位置・読出し位置・FIFO成功数・待ち回数をSERVICE単位で集計できる診断手段が必要です。既存ABIで取得可能か確認し、不足する値はソース生成ファームウェアで計測する方法を検討します。ホストのSERVICE開始終了時刻、Bulk完了時刻、入力CCとの対応により、入力速度不足とUSB補充不足を分離できます。

その後、SERVICEを1 ms早めるだけの試験、USB要求容量だけの試験、機器側の処理予算・自律送出の試験を分けると効果を判断できます。処理予算を大きくするだけではUSB制御応答時間が延びる可能性があり、単独の定数置換を修正とする根拠はありません。

今回の変更は比較文書と機器非接続の解析資料のみです。ファームウェアのパッチ、受信プログラムの変更、デプロイは含みません。

## 実機測定による追試

[2026-11-07の測定](pix-dt295-stream-measurement.md)で、SERVICE間の32 KiB送出と、追加制御転送による受信低下・除去後の回復を確認しました。リングがほぼ満杯となったのは診断負荷を加えた条件で、通常時の上書きを確定する結果ではありません。
