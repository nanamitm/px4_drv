# CECH-ZD1JのソースビルドFRファームウェア経路

実験用の `I2cBackend="source-fr"` は、CECH-ZD1Jのcore1へ本リポジトリのCソースから生成したFRプログラムをロードし、PAF2メールボックスで物理I²C要求を転送する経路です。復調器・チューナーの初期化、選局、状態取得はDriverHost内の既存ネイティブ実装が担当します。通常のBonDriver APIとTS配信IPCを使うため、利用アプリ側に専用プロトコルは不要です。

既定値は `native` です。PIX-DT295は別のHAL・フロントエンドを必要とするため、この設定で代用できません。

## ビルドと設定

FRコンパイラー・アセンブラーを指定した [build_auxiliary.py](../experimental/dt295-firmware/build_auxiliary.py) に `--torne-i2c --torne-device-clock` を渡すと `auxiliary.bin` と `manifest.json` が生成されます。手順と時計の実測は [torne-device-clock.md](../experimental/dt295-firmware/torne-device-clock.md) を参照してください。成果物の `deployable=false` は実験段階を表す値です。

通常のx86/x64 DriverHostビルドにはこの経路が含まれます。生成したバイナリーを配置し、`DriverHost_PX4.ini` のCECH-ZD1Jに対応する `.Config` 節へ次を指定します。SHA-256は使用する生成物から取得してください。

```ini
I2cBackend="source-fr"
SourceFirmwarePath="firmware\torne-source-fr.bin"
SourceFirmwareSha256="<生成物の64桁のSHA-256>"
```

相対パスの基準はDriverHost実行ファイルのディレクトリーです。旧INIの `ResidentFirmware=true` は廃止済みのため削除できます。旧Goヘルパーを使うビルドも対象外です。既存DriverHostが起動中の場合は、利用中の録画を終えてから再起動すると設定が反映されます。初期化には時計の2.7秒待機試験が加わるため、初回Openの接続期限には余裕が必要です。通常の選局期限は変更不要です。

## ロードと終了

DriverHostは既存bootstrapで基準状態を作った後、core1を停止し、16KBのRAMを保存します。最大8KBの入力をSHA-256で検査し、書き込み・読み戻しの一致を確認して起動します。PAF2 ABI・機器側時計機能・ホスト更新なしでの時計進行を確認した後にI²Cの所有権を取得します。

I²C要求には絶対期限と転送数の検査があり、NACK・timeout・形式不正・USBエラーの後はセッションが無効になります。途中失敗から既存core1のコマンドへ切り替えるフォールバックはありません。再利用にはセッションの破棄と再初期化が必要です。

NACK・timeoutでSTOPを要求した場合、FR側は応答公開前にバスのbusy解除を最大500ms待ちます。失敗時の完了数は部分転送を表すため、全数一致は成功時だけの条件です。busyが残ったまま期限を越えた場合も成功にはならず、元の失敗とbusy状態を返します。時計停止・所有権喪失時にはこの待機を続けず失敗し、所有権を失った機器への追加I/Oも停止します。

正常Closeと初期化失敗時には別の有限期限でcore1停止、バス停止、保存RAMの書き戻し・一致検査、旧core1のheartbeat確認を行います。保存対象はbootstrap後のcore1 RAMで、電源投入直後の機器全体ではありません。USB抜去後は古いハンドルで復元が成立しないため、ログに復元未確認と記録されます。

プロセス強制終了時はメモリー上の保存像が失われます。次回source-frのbootstrapではcore0/core1とTS入力・出力を先に停止してから既存基準プログラムを再構築します。強制終了時点のRAM像へ戻す機能ではありません。

機器側時計の源はUSB SOFです。アプリケーションからの時刻更新は不要ですが、USBサスペンド中の独立発振時計ではありません。1msの精度と2.048秒以内の定期読み取りが必要で、時計停止時にはループ上限による失敗判定も働きます。

## 確認範囲

CECH-ZD1Jのx64 BonDriver→DriverHost→PAF2経路でGR13→GR17→GR13を各5分受信し、各3,442,688パケット、合計10,328,064パケットの同期・TEI・CC・形式エラーはすべて0でした。保存された188-byte TSのPAT CRCとTSIDも確認しています。Close後のログは `ram_exact=1 / legacy_resumed=1 / restore=1` でした。

この15分試験のFRイメージは4,628 bytes、SHA-256 `7332bc75c6242705d49ff59279428fc6a07072baf55417b518129642acf7ffd1` です。STOP待機追加後のイメージは4,884 bytes、SHA-256 `a832770aec700741b83dda506d913fd3568555ff450eedd6cc2590ee3f7ca138` で、同じ順序の各10秒受信（各113,664パケット）とClose復元を再確認しました。最大空受信間隔は154ms、各区間末尾の無受信時間は89msでした。

x86のBonDriver・DriverHostでも4,884-byte版を使ってGR13・GR17を各5秒、各56,320パケット受信し、同期・TEI・CC・形式エラーは0、最大空受信間隔155ms、終了時のRAM一致と旧core1再開を確認しています。x86/x64とも通常ビルドと既存アプリからIPCを分離した試験用ビルドを生成し、実機試験には後者を使いました。

| 異常条件 | 結果 |
|---|---|
| 設定SHA-256を全0へ変更 | Open失敗、ログは `image SHA256`。正しい設定へ戻すと再受信成功 |
| 受信中の試験用Host強制終了 | 末尾約17秒の無受信を失敗として検出。USB抜き差しなしの新規HostでGR13・GR17再受信成功 |
| PAF2から0x7fへ1 byte読み取り | address NACK（status=4 / result=9）、I²C能力消去・ホストセッション無効化・再送なし・停止・RAM復元を確認 |
| PAF2の既知vendorレジスター読み取りを1µs期限に指定 | timeout（status=4 / result=5）、部分転送tx=2 / rx=0、再送なし・停止・RAM復元を確認 |
| x86受信中の物理USB抜去・5秒後の再挿入 | USBエラー31で受信停止、古いハンドルによる復元は失敗として記録。新規HostでGR13・GR17を各5秒再受信し、各56,320パケットのエラー0、Close時のRAM一致・旧core1再開を確認 |

NACK・timeoutは診断ローダーによる実機試験です。DriverHostの外部I²Cルートでは模擬NACKがそのまま返り、次の要求が `not_ready` となり、既存core1へのUSB要求が増えないことも検査しています。強制終了試験とハッシュ不一致試験は4,628-byte版によるもので、STOP待機追加後の同条件の長時間試験とは区別しています。

物理抜去試験では、旧BonDriverの120秒観測のうち最終パケットが23,254ms、末尾の無受信が96,758msとなり、期待どおり診断は失敗を返しました。切断前のTSエラーが0でも、途中で止まった受信を合格に扱わない条件です。旧セッションのClose後には同じHostでも機器の再列挙を確認しましたが、再受信試験はアイドル終了後の新規Hostによるものです。同じBonDriverインスタンスの自動復帰を確認した結果ではありません。

DriverHostの生192-byteストリームでは各区間の開始時に166 / 155 / 64 bytesの境界合わせ破棄が記録されています。BonDriver後段の保存TSだけから生ストリームの同期後破棄を証明できないため、全区間無破棄の合格とは区別しています。スクランブル解除・映像復号の検証はこの受信計数に含まれません。

USBサスペンド、数時間以上の連続受信、カード通信を伴う受信、PIX-DT295固有の物理制御は追加検証が必要です。
