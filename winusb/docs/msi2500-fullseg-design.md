# RSP1 互換機 (MSi2500/MSi001) によるフルセグ受信の設計

Mirics MSi2500 と MSi001 を搭載した SDRplay RSP1 互換機で、地上デジタル放送の13セグメントを
リアルタイムに復調し、BonDriver から TS として受信するための設計資料。
2 節の測定値の多くは試作ツールによる取り込みとオフライン復調の結果で、実装した helper
(`winusb/tools/msi2500_frontend`) と DriverHost_PX4 への組み込み (`Type="MSI2500"`) での結果は 11 節にまとめた。
利用者向けの導入手順は [docs/msi2500-install.md](../../docs/msi2500-install.md) にある。

## 検証環境

本文で「検証環境」と書く場合は、次の条件を指す。

| 項目 | 内容 |
|---|---|
| OS | Windows 11 Pro x64 (10.0.26300) |
| CPU | AMD Ryzen 9 5900X (12コア24スレッド、AVX2 対応、AVX-512 非対応) |
| 受信機 | RSP1 互換機 1台。USB ID `1DF7:2500`、シリアル `0000000001`、High-Speed (480 Mbps) |
| 接続 | xHCI ルートハブのポートへ直結 (ハブ経由なし) |
| ドライバー | SDRplay Limited 提供の WinUSB INF。デバイスインターフェース GUID `{2D93E8F2-BC67-4F7D-8891-574830AA637D}` |
| 受信チャンネル | UHF 13〜17ch (中心 473.142857〜497.142857 MHz) |
| アンテナ | 配線条件は未申告 |
| 測定日 | 2026-11-05 |

純正の SDRplay RSP1 は検証していない。
互換機の個体差、ほかのチャンネル、USB ハブ経由の接続は未確認。
他機種との同時使用は、PX 系チューナーの録画と同時に受信した範囲だけを確認した (11.2 節、11.3 節)。

## 1. 位置づけ

RTL2838UHIDIR による既存の受信は中央1セグメントに限られる。
RTL2832U が安定して取り込める標本化レートは約 2.4 MS/s で、6 MHz 幅のフルセグには足りないためである。
MSi2500 は約 10 MS/s まで取り込めるため、ISDB-T の基本標本化レート 512/63 MHz (約 8.126984 MS/s) で
1チャンネル全体を取り込める。

構成は [RTL-SDR ワンセグの BonDriver 統合](rtlsdr-bondriver.md) と同じ方式を基本とする。
DriverHost_PX4 の機種実装が機器の利用権と helper の寿命を管理し、
別実行ファイルの helper が USB の取り込み、OFDM 復調、誤り訂正、TS の生成を担当する。

## 2. 検証環境で確認した事実

### 2.1 USB 記述子

interface 0 に次の alternate setting がある。

| alternate | エンドポイント | 種別 | wMaxPacketSize |
|---|---|---|---|
| 0 | なし | — | — |
| 1 | `0x81` | 等時転送 | 5120 (1マイクロフレームあたり 3×1024 バイト、最大 24.576 MB/s) |
| 2 | `0x81` | 等時転送 | 1024 |
| 3 | `0x81` | バルク転送 | 512 |

### 2.2 制御転送

libmirisdr はレジスター書き込み (`bRequest=0x41`) に bmRequestType `0x42` (宛先=エンドポイント) を使う。
WinUSB は宛先がエンドポイントの要求で wIndex の下位バイトを実在のエンドポイントとして検査するため、
レジスター値の上位ビットを wIndex に詰めた書き込みを `ERROR_INVALID_PARAMETER` で拒否する。
1回の設定で送る53回の書き込みのうち33回が拒否され、デバイスは設定途中の状態のままだった。
Linux の msi2500 ドライバーと同じ宛先=デバイス (`0x40`) で送ると、すべての書き込みが成功した。
ストリーミングの開始 (`0x43`) と停止 (`0x45`) も同じ形式の要求である。

### 2.3 libusb 経由の取り込み

PothosSDR 同梱の libmirisdr と libusb 1.0.24、libusb 1.0.30 への差し替え、
libmirisdr-5 (`ericek111/libmirisdr-5` コミット `6392af06`) のバルク転送と等時転送を試したが、
いずれも IQ を取り込めなかった。等時転送では各パケットの状態が `0xC0020000`
(USBD_STATUS_ISO_NOT_ACCESSED_BY_HW) か不明値になり、バルク転送はタイムアウトした。
これらの試験はすべて `0x42` の制御転送でデバイスの設定が完了していない状態で行ったため、
libusb の等時転送処理そのものの問題と、デバイス側の未設定の影響は切り分けていない。

### 2.4 WinUSB による直接の取り込み

WinUSB の `WinUsb_RegisterIsochBuffer` と `WinUsb_ReadIsochPipeAsap` で alternate 1 を読み、
制御転送を `0x40` で送ると取り込めた。1転送を64パケット (8 ms)、同時投入を32転送とした。

| 条件 | 結果 |
|---|---|
| 8.126984 MS/s、10 bit 形式 (384)、600秒 | 約49億サンプル。欠落は開始直後の 24,728 サンプルのみ。不良パケット・転送エラー 0 |
| 実効レート | 8,127,000 S/s 前後 (PC の時計に対して約 +8 ppm) |
| USB 帯域 | 21.7 MB/s。パケットは約88%が 3072 バイト、約12%が 0 バイト |
| 8.126984 MS/s、12 bit 形式 (336)、20秒 | 帯域の上限を超え、約0.78%のサンプルを欠落 |

各 1024 バイトのブロックは16バイトのヘッダーを持ち、先頭4バイト (little endian) がサンプル番号である。
番号はブロックごとに形式のサンプル数 (252/336/384/504) ずつ増えるため、欠落をサンプル単位で数えられる。
ストリーミング開始直後は、形式切り替え前の252形式のブロックが3個前後混ざり、
続いて約2.5万〜3.4万サンプルの欠落が1回ある。

libmirisdr の形式自動選択の境界は、6.048 MS/s 以下が14 bit (252)、8.064 MS/s 以下が12 bit (336)、
9.216 MS/s 以下が10 bit (384)。8.126984 MS/s は等時転送の上限から10 bit 形式になる。

### 2.5 フロントエンドの GPIO

レジスター `0x08` の GPIO で RF 入力経路を切り替える。libmirisdr には既定の表と SDRplay 用の表がある。
検証環境の互換機は既定の表 (UHF で `0xf380`) で受信でき、SDRplay 用の表 (`0xf580`) では
選局とゲインの変更に出力が反応せず、内部の雑音だけが出た。
純正の RSP1 と互換機は USB ID が同じため、USB ID からは表を選べない。

### 2.6 OFDM 復調

| 項目 | 13〜17ch の結果 |
|---|---|
| ガードインターバル相関 (遅延 8192) | \|ρ\| ≈ 0.111 (理論値 1/9)。Mode 3、GI 1/8 |
| 標本化周波数のずれ (放送波基準) | +0.61〜+0.63 ppm |
| 周波数ずれ | 整数部 0 キャリア、小数部 約 +270 Hz |
| TMCC | A 階層 QPSK 2/3、I=4、1セグメント (部分受信)。B 階層 64QAM 3/4、I=2、12セグメント。C 階層 未使用 |

復調の実装で判明した注意点を次に示す。

- SP の電力パターンは、3キャリアのずらしとシンボル位相1つのずらしで区別できない。
  電力だけで整数部の周波数ずれを決めると12キャリアずれた解を選ぶことがあり、
  その場合は帯域端のキャリアが劣化したように見える。
  SP の PRBS (5617キャリア全体で連続する11段 LFSR) との符号の相関で確定する。
- FFT 窓を CP の中央から始めると、伝送路に `k×π/8` の直線位相が乗り、
  SP 間 (3キャリア) で 67.5° 回る。この位相を補償せずに複素線形補間すると、
  中点の振幅が約17%小さくなり、MER が約6 dB 低く出る。
- 中央セグメントの TMCC・AC キャリア12本は、等化後に BPSK 的な2値となる性質から統計的に検出でき、
  既知の位置 (ローカル 7, 89, 101, 131, 206, 209, 226, 244, 286, 349, 377, 407) と一致した。
  他のセグメントの位置表は未作成であり、実装では ARIB STD-B31 の表を一次資料として使う。

### 2.7 MER と誤り訂正

ゲイン 40 dB、IF 帯域幅 6 MHz、各局 4.5 秒の取り込み (有効区間 約4.2秒) の結果。
MER はパイロットの線形補間で等化した値で、B 階層は全キャリアを含む。

| ch | B 階層 MER | ビタビ前 BER | RS ブロック | 訂正 | 訂正不能 | TEI | CC 不連続 |
|---|---|---|---|---|---|---|---|
| 13 | 27.15 dB | 1.1×10⁻⁵ | 47,025 | 0 | 0 | 0 | 0 |
| 14 | 25.20 dB | 5.3×10⁻⁴ | 47,025 | 0 | 0 | 0 | 0 |
| 15 | 27.00 dB | 1.7×10⁻⁴ | 47,025 | 0 | 0 | 0 | 0 |
| 16 | 27.19 dB | 2×10⁻⁶ | 47,025 | 1 (1バイト) | 0 | 0 | 0 |
| 17 | 27.23 dB | 6×10⁻⁶ | 47,025 | 0 | 0 | 0 | 0 |

- 15ch の A 階層は RS ブロック 1,089 個がすべて誤りなし。
- 15ch の B 階層の TS を TSDuck で解析すると、PCR から推定したビットレートは 16,851,541 b/s で、
  64QAM 3/4・12セグメントの理論値と一致した。同期不正と TEI は 0。
- 中央セグメントの DC 近傍 (±2キャリア) は局部発振器の漏れ込みで劣化し、
  A 階層の MER を全キャリアで 19〜24 dB、除外後で約 27 dB に下げる。
- 14ch の B 階層には劣化したキャリアが数本あり、MER が他局より約 2 dB 低い。
  5局で位置が共通ではないため外来の妨害と推定しているが、原因は未確定。
- ゲイン 25〜40 dB ではクリップがなく、ガードインターバル相関は理論値に張り付いた。
  45 dB では libmirisdr のゲイン配分が LNA の設定を切り替え、SNR が約 20 dB に下がった。

### 2.8 誤り訂正の仕様の細部

記憶だけでは確定できなかった細部は、候補を総当たりし、ビタビ前 BER と RS の成否で確認した。

| 処理 | 確認した仕様 |
|---|---|
| セグメント内ランダマイズ | `isdbt-dsp` の `FREQ_PERM_MODE3` (`out[i] = in[PERM[i]]`) をすべてのセグメントに適用 |
| セグメント内ローテーション | 解除は `out[k] = in[(k − s) mod 384]` (s は論理セグメント番号) |
| セグメント間デインターリーブ | 階層内のセグメントを論理番号順に並べ、層内位置 `c×n + j` に第 j セグメントのキャリア c を置く (n は階層のセグメント数) |
| 時間デインターリーブ | 層内位置 c の遅延 `I×(95 − (5c mod 96))` シンボル |
| 64QAM のビット | (b0, b2, b4) が I 軸、(b1, b3, b5) が Q 軸。b0 は負で1、b2 は \|x\|<4 で1、b4 は \|x\| が 3 と 5 で1 |
| ビットデインターリーブ | 受信側の遅延は b0 が120、以降24ずつ減り b5 が0 (QPSK は b0 が120、b1 が0) |
| エネルギー拡散 | PRBS 初期値 `0xa9`。リセット周期は1フレームの TSP 数 (B 階層 2,592、A 階層 64) |
| バイトデインターリーブ | 同期バイトは204=17×12 バイトごとに同じ分岐を通るため、コミュテータ位相は同期バイトの周期では決まらない。RS の符号語判定と組み合わせて確定する |

64QAM の b2〜b5 の極性4通りはビタビ前 BER では区別できず、RS の成否で確定した。

### 2.9 処理量

`isdbt-dsp` のビタビ (K=7、64状態) を検証環境で測った速度は、一括処理で 2.49 M ステップ/秒、
逐次処理で 1.52 M ステップ/秒。
B 階層のリアルタイム処理には 約881.8 シンボル/秒 (512/63 MHz ÷ 9,216 サンプル) × 18,432 ステップ
≈ 16.3 M ステップ/秒が必要で、現状の 7〜11 倍の高速化を要する。
A 階層は約 0.51 M ステップ/秒で、現状の実装でも足りる。
オフライン試作では 4.2 秒分の B 階層の復号に約73秒を要した。

これに対し、整数メトリックとブロック並列で試作したビタビ (5.1 節) を検証環境で測った結果を次に示す。
軟判定値は8ビットに量子化し、パスメトリックは16ビット整数、出力4,096ステップごとのブロックに
前後96ステップの助走を付けて独立に復号した。

| 条件 | 処理速度 |
|---|---|
| 乱数符号語、ISA 指定なし (SSE2 相当の自動ベクトル化)、1スレッド | 47〜50 M ステップ/秒 |
| 同、AVX2 を有効にした版、1スレッド | 33〜36 M ステップ/秒 |
| 同、ISA 指定なし、4スレッド / 12スレッド | 177〜193 / 405〜407 M ステップ/秒 |
| 15ch の B 階層 4.2 秒分 (7,676万ステップ)、ISA 指定なし、1スレッド | 1.9 秒 (実時間の0.45倍) |
| 同、2スレッド | 1.2 秒 (実時間の0.29倍) |

実データの時間は量子化とビット列の詰め替えを含む。
15ch の B 階層では、逐次版と試作版の TS が SHA-256 で一致した (47,025 パケット、RS 訂正不能 0)。
乱数符号語にビタビ前 BER 5.4% の雑音を加えた条件では、試作版の復号後の誤りは 800万ビット中51、
`isdbt-dsp` の一括版は 200万ビット中19 で、先頭200万ビットの出力の差は13ビットだった。
差は軟判定値の量子化によるもので、ブロック分割による劣化は見られなかった。
AVX2 を有効にした版が遅い原因は自動ベクトル化の生成コードの違いと推定しており、未調査である。
上表は助走96ステップ・ブロック4,096ステップ・量子化の倍率7での値で、以下の評価を経て既定値を変更した。

### 2.10 劣化させた信号での助走と量子化

15ch の B 階層の等化後の星座へ、固定シードの複素ガウス雑音を加えて評価した。
雑音は等化の後に加えたもので、RF の雑音や伝送路推定の劣化は含まず、信頼度の重みも再計算していない。
表の「付加雑音」は加えた雑音だけの MER で、元の約27 dB と合成した実効値を括弧内に示す。

助走の長さ (ブロック4,096ステップ、倍率7)。差は助走1,024ステップの出力とのビット単位の差である。

| 付加雑音 (実効 MER) | 助走 32 | 48 | 64 | 96 | 128 | 192 | 1,024 の RS 結果 |
|---|---|---|---|---|---|---|---|
| 20 dB (約19.2 dB) | 14 | 3 | 0 | 0 | — | — | 訂正 258、訂正不能 0 |
| 18 dB (約17.5 dB) | 746 | 185 | 92 | 20 | 0 | 0 | 訂正 11,683、訂正不能 0 |
| 17 dB (約16.6 dB) | 6,763 | 2,459 | 1,093 | 172 | 12 | 0 | 訂正 39,810、訂正不能 8 |
| 16 dB (約15.7 dB) | 35,105 | 19,119 | 11,084 | 3,154 | — | — | 全ブロック訂正不能 |

助走192ステップは、訂正不能が出始める条件まで助走1,024ステップと一致した。
付加雑音 16 dB では助走1,024ステップでも全ブロックが訂正不能となり、
この試作の受信処理での限界はこの付近にある。ただし、この条件ではエネルギー拡散の位置合わせの探索も
失敗している可能性があり、誤り訂正の限界と同期処理の失敗は切り分けていない。
ブロック長を8,192ステップにすると、助走192ステップでも1スレッドの処理時間は助走96ステップの場合と同等 (1.55秒 対 1.58秒) だった。

### 2.11 前処理、逐次投入、32ビット版

デインターリーブ、デマップ、デパンクチャ、量子化を1回の走査にまとめ、f32 の中間配列を作らずに
8ビットの母符号列を直接生成する形にした。出力ビットは各段を分けた場合と一致した。
逐次投入の復号器は、1ステップずつ、1,000ステップずつ、1シンボル分 (18,432ステップ) ずつの投入で、
一括処理と出力ビットが一致した。いずれも15ch の B 階層の TS は SHA-256 が変更前と一致した。

既定値 (助走192、ブロック8,192、倍率12) での15ch の B 階層 4.2 秒分の処理時間:

| 段 | x64 版 | x86 (32ビット) 版 |
|---|---|---|
| 前処理 (1スレッド) | 0.77〜0.82 秒 (実時間の約0.19倍) | 1.24〜1.30 秒 (約0.31倍) |
| ビタビ 1スレッド | 1.50 秒 (約0.36倍) | 1.96 秒 (約0.47倍) |
| ビタビ 2スレッド | 0.78 秒 (約0.19倍) | 0.96 秒 (約0.23倍) |
| 乱数符号語でのビタビ速度 (1スレッド) | 47〜50 M ステップ/秒 | 41〜44 M ステップ/秒 |

前処理とビタビを別スレッドで並行して処理すると、処理能力は遅い段で決まる。
x86 版でもビタビ1スレッドで実時間の約0.47倍、2スレッドで約0.31倍 (前処理が律速) となる。
OFDM 復調 (2.6 節の処理) の処理時間はこの表に含まない。

### 2.12 Rust のストリーム復調と実機でのリアルタイム受信

OFDM 復調を Rust のストリーム処理として試作し、誤り訂正のストリーム版と組み合わせた。
試作の構成は、WinUSB の取り込みツールが生ブロックを標準出力へ流し、復調プロセスが標準入力から読む2プロセスである。
復調が遅れるとパイプへの書き込みが詰まり、等時転送の再投入が遅れてサンプル番号の欠落として現れるため、
受信中の欠落 0 を実時間処理が間に合っている条件として使った。

| 段 | 試作の内容 |
|---|---|
| 初期同期 | 2.6 節と同じ手順 (約212シンボル、約0.24秒分を使用) |
| 追従 | 32シンボルごとに、SP の4シンボル間位相差から窓の間隔と CFO、伝送路の位相傾きから窓位置を補正 |
| 伝送路推定 | SP を時間方向に線形補間し、3キャリア間隔で周波数方向に補間。出力は3シンボル遅れる |
| 制御キャリア | 最初の256シンボルで、等化後に BPSK 的な2値となる12本を各セグメントで検出 |
| 信頼度 | キャリアごとの判定誤差の指数平均 (係数0.02) と、階層ごとの中央値の比 (0〜2) |
| 誤り訂正 | 時間デインターリーブはリングバッファ、ビタビは 5.1 節の逐次投入版、バイト段は約400ブロックで初期探索した後に逐次処理 |

試作で判明した注意点を次に示す。

- 階層の平均電力を1サンプルの電力で初期化すると、起動直後の正規化が大きく狂い、誤差統計と信頼度の重みが
  数秒間汚れる。時間インターリーブの深い A 階層 (I=4) では、この間のシンボルが RS の訂正不能として現れた
  (13ch で訂正不能172ブロック)。シンボルごとの階層全体の平均電力で初期化し、TMCC の確定後128シンボルは
  誤り訂正へ渡さない形にすると、訂正不能は0になった。
- 窓位置の補正のために意図的に変えた間隔を、間隔の推定値から差し引かないと、
  間隔と位置の2つの補正が互いに打ち消し合う定常状態 (標本化ずれ推定 1.05 ppm、位置誤差 −0.44 サンプル) に落ち着く。
  差し引くと、推定は初期同期の値 (約0.61 ppm) に収束し、位置誤差は0.01サンプル以下になった。
- DC 除去の追従を止めると、中央セグメントの MER が約25 dB から約14 dB に下がる。

録画した13〜17ch の IQ (各4.5秒) では、A・B 両階層とも RS の訂正0・訂正不能0となり、
一括処理の TS と重なる39,973パケットがすべて一致した。処理時間は実時間の0.80〜0.83倍 (初期同期を含む) だった。

実機でのリアルタイム受信 (15ch、x64 版、OFDM 1スレッド、ビタビ2スレッド、既定値は 5.1 節):

| 項目 | 60秒 | 600秒 |
|---|---|---|
| 取り込みの欠落 | 開始直後の 32,856 サンプルのみ | 開始直後の 24,732 サンプルのみ |
| B 階層 RS ブロック | 665,548 (訂正0、訂正不能0) | 6,740,277 (訂正0、訂正不能0) |
| A 階層 RS ブロック | 16,352 (訂正0、訂正不能0) | 166,337 (訂正0、訂正不能0) |
| TEI / CC 不連続 | 0 / 0 | 0 / 0 |
| MER (A / B) | 約26 / 27 dB | 最小 23.0 / 26.8 dB |
| 標本化ずれの推定 | 約 +0.60 ppm | +0.602 ppm |
| 最初の TS までの時間 | 約1.9秒 | — |
| 経過時間と信号時間の差 | — | 最大0.57秒 |
| 復調プロセスの CPU 時間 | — | 30秒あたり約37.7秒 (約1.26コア分) |
| 取り込みプロセスの CPU 時間 | — | 30秒あたり約0.4秒 |
| 作業メモリ (復調 / 取り込み) | — | 約60 MB / 約12 MB |

60秒の受信で保存した TS を TSDuck で解析すると、同期不正と TEI は0、
PCR から推定したビットレートは 16,851,541 b/s で、2.7 節の録画データと同じ構成だった。
検証環境以外の CPU、x86 版、他チャンネルでの長時間受信は未試験である。

### 2.13 不連続と選局し直しでの状態の作り直し

復調プロセスは、ヘッダーのサンプル番号の不連続 (欠落、または選局し直しによる番号の巻き戻り) を検出すると、
OFDM 復調と誤り訂正の状態をすべて捨てて新しい区間として初期同期からやり直す。TS は区間ごとに分けて記録した。
不連続より前の、デインターリーバーとビタビに残っていた分は出力しない。

録画データでの確認:

| 入力 | 結果 |
|---|---|
| 15ch の中央から 1,000 ブロック (384,000 サンプル) を除いた IQ | 欠落を検出して作り直し。後の区間は B 階層 19,103 ブロックで訂正1、訂正不能0。前後とも TSID 0x7C17 |
| 13ch の前半に 15ch をつないだ IQ | 番号の巻き戻りを検出。前の区間は TSID 0x7C11 のみ、後の区間は 0x7C17 のみ。訂正不能0 |

実機での選局し直し: 取り込みツールがストリーミングを止めずに、15秒ごとに 13ch と 14ch のレジスター列
(停止、53回の書き込み、開始) を交互に送った (計9回、135秒)。

| 項目 | 結果 |
|---|---|
| 区間ごとの PAT の TSID | 13ch の区間は 0x7C11 のみ、14ch の区間は 0x7C12 のみ (旧局の混入なし) |
| B 階層 | 各区間 約157,000 ブロック、訂正は区間の開始直後の 0〜1 ブロック、訂正不能0、TEI 0、CC 不連続0 |
| A 階層 | 各区間 約3,800 ブロック、訂正0、訂正不能0 |
| 不連続の検出から最初の TS まで | 1.18〜1.20 秒 |
| 選局し直しの制御転送 | 約110 ms (53回の書き込み) |
| 取り込みの欠落 | 開始直後の 32,856 サンプルのみ |

選局し直しの後は MSi2500 のサンプル番号が巻き戻るため、番号の不連続で区間の切り替えを判定できた。
製品では、選局要求を受けた時点で状態を作り直す形とし、番号の不連続は欠落の検出と安全側の判定に使う。
開始直後の欠落も不連続として扱われ、初期同期前の空の区間ができる。実害はないが、製品では開始直後の欠落を区別する。

USB 抜去: 受信中 (開始から約29秒) にケーブルを抜くと、取り込みツールは等時転送の再投入の失敗
(`ERROR_BAD_COMMAND`) で抜去を検出した。ただし最初の試作では、終了処理で投入済みの転送の完了を
無期限に待ったため、プロセスが終了せず、復調側も入力の終わりを受け取れなかった。
取り込みツールを強制終了すると、復調側は抜去までの約30秒分 (B 階層 326,945 ブロック、A 階層 8,000 ブロック、
いずれも訂正不能0) の TS と統計を書き出して終了した。
抜去後は完了しない転送があるため、完了待ちには期限が要る。製品の helper でも、抜去後の終了処理の
各待機に期限を設ける。挿し直した後に新しく開いた受信は、30秒間、A・B 両階層とも誤りなしだった。
挿し直した直後は周波数ずれが約 +298 Hz、標本化ずれが約 +0.67 ppm と、通電を続けていたとき
(約 +264 Hz、+0.60 ppm) から離れていたが、追従で吸収できた。

完了待ちに1本あたり1秒の期限を付けた版で再度抜去すると、取り込みツールは自ら終了し (完了しない転送が1本残った)、
復調側も続けて終了した。ただしこの回は、開始から抜去までの約27秒間、レジスター設定とストリーミング開始の
制御転送は成功したのに、等時転送のパケットがすべて0バイトで、データが1ブロックも届かなかった。
直後に開き直しを3回続けた試験ではいずれも正常に受信でき、この現象は再現していない。
抜き差しの直後だったことが関係している可能性はあるが、原因は未確定である。
製品の helper では、データの届かない時間に上限を設けて失敗として扱い、
等時転送の失敗が続く場合も同様に扱う (試作の取り込みツールは失敗した転送を投入し直し続けた)。

### 2.14 開き直し後にデータが届かなくなる状態

原因は終了処理の順序だった。データが流れている最中に停止要求 (0x45) を送ってから転送を中止すると、
長めの取り込みの後で、次のストリーミング開始でデータが届かない状態に入ることがあった。
Linux の msi2500 ドライバーと同じく、転送を中止して完了を待ち、20 ms あけてから停止要求を送り、
USB インターフェースと ADC を休止させる (レジスター 0x03 に 0x010000) 順に改めると、
「30秒の取り込み、直後に開き直し」を3回繰り返してすべて正常に受信できた。
C の試作で30秒取り込んだ後は Rust の helper で正常に開き直せ、Rust の helper (改める前) で30秒取り込んだ後は
固まったことから、条件を終了処理に絞り込んだ。

改めた helper (x64) で 15ch を600秒取り込むと、開始区間を除く欠落・不良パケット・転送エラーはいずれも0で、
直後の開き直しも正常だった (M1 の完了条件)。別の600秒の取り込みでは、x86 版のコンパイルを同時に実行した時間帯に、
約0.35秒の間に4回の欠落 (計207,628サンプル) と2回の転送エラーがあった。投入済みの転送は約256 ms 分のため、
取り込みスレッドがそれより長く止まると取りこぼす。TVTest などと同じ PC で動かす製品では、
投入数の増加や取り込みスレッドの優先度を M4 で検討する。x86 版は自動試験に合格したが、実機では未確認である。
以下は切り分けの経過の記録である。

Rust の helper (M1) で取り込みを繰り返すと、上記の「制御転送は成功するのにデータが届かない」状態が再現した。
いったんこの状態に入ると、C の試作ツールでも、全レジスター列の再送でも、alternate setting を 0 から 1 へ
設定し直しても回復せず、USB の抜き差しでだけ回復した。パイプのリセット (`WinUsb_ResetPipe`) は、
転送自体が失敗するようになるため使えなかった。

| 直前の取り込み | 次の開き直し |
|---|---|
| 3〜8秒の取り込みの連続 (Rust 6回、C 3回) | すべて成功 |
| 60秒 (C、終了処理で完了を無期限に待つ版) から約10秒後 | 成功 |
| 30秒 (C、完了待ちを1秒で打ち切る版) の直後 | 失敗 |
| 10秒 (Rust) から約1分後 | 失敗 |
| 30秒 (Rust、欠落なし) の直後 (2回) | 失敗 |

取り込みの長さ、次の開き直しまでの間隔、終了処理の完了待ちの方法のどれが条件かは切り分けていない。
1回の失敗例では、直前の30秒の取り込みの途中でサンプル番号が合計約6,480万 (384 の倍数ではない) 飛んだが、
別の失敗例では直前の取り込みに不連続はなかった。
製品の録画では、この状態に入ると抜き差しまで受信できないため、M1 の完了前に条件と回避方法を確定する。

切り分け1 (終了処理): Rust の helper の終了処理を、C の旧版と同じく全転送の完了を無期限に待つ形に切り替えて
30秒取り込んだ直後に開き直すと、2回続けて正常に受信できた。完了待ちを1秒で打ち切る終了処理が、
この状態に入る条件に関係している可能性が高い。ただし成功は1組だけで、再現性は未確認である。
抜去後は完了しない転送があるため、無期限の待機はそのままでは使えない。
抜去と正常終了を区別して待ち方を変えるなど、両方を満たす終了処理を決める必要がある。

この切り分け1の30秒の取り込みでは、受信中の欠落が53回 (計約281万サンプル、1回あたり等時転送の約1回分) 起きた。
同じ条件の他の30秒の取り込みと、C の試作での600秒の取り込みでは欠落がなかった。原因は未確定である。

切り分け1 を「30秒取り込み、直後に3秒取り込み」の繰り返しで再確認すると、全転送の完了を待つ終了処理でも
1回目の直後にデータが届かない状態に入った。終了処理の待ち方は条件ではなかった。
この時点で、デバイスはシリアル番号なしで列挙されていた (インスタンス ID が `0000000001` から
位置に基づく値へ変わっていた)。何度かの抜き差しの後から、30秒の取り込みごとに転送1回分の欠落が
数十回起きるようにもなった。接続 (ケーブル、コネクター、給電) の不安定さとソフトウェアの問題を、
まず接続の状態を確かめてから切り分ける。

## 3. 構成

| 担当 | 役割 |
|---|---|
| DriverHost_PX4 の機種実装 (Type は仮に `MSI2500`) | 記述子の確認、機器の利用権、helper の起動と停止、TS の配信、USB 抜去の反映 |
| helper `msi_frontend.exe` (Rust、GPL-3.0-or-later) | WinUSB の取り込み、レジスター設定、OFDM 復調、誤り訂正、TS の再多重 |
| helper の通信 | RTL-SDR helper と同じ stdout フレーム形式 (24バイトのヘッダーと payload) |

DriverHost は USB 記述子で USB ID とシリアルを確認した後に WinUSB ハンドルを解放し、
受信中は helper を唯一の USB 所有者とする。この所有権の分け方は RTL-SDR の機種実装と同じである。
helper の通信形式を共通にすると、DriverHost 側の受信、形式検査、品質値の扱いを共用できる。
DSP コードを DriverHost にリンクする構成は、ライセンスと障害の分離の観点から RTL-SDR と同じく対象外とする。

## 4. USB 層 (helper)

- 制御転送は bmRequestType `0x40` で送る。`0x42` は WinUSB に拒否される (2.2 節)。
- 取り込みは alternate 1 の等時転送とし、10 bit 形式 (384) で 8.126984 MS/s に設定する。
  12 bit 形式は帯域の上限を超えるため使えない (2.4 節)。
- 転送の構成は、検証環境で欠落のなかった64パケット×32転送を初期値とする。
  一時的な処理の遅れを吸収できるよう、取り込みスレッドは復調から切り離し、
  リングバッファの容量と満杯時の扱いを RTL-SDR と同様に定義する。
  満杯時にデータを捨てて復調を続ける扱いは、欠落を隠すため対象外とする。
- レジスター設定は、libmirisdr (GPL-2.0-or-later) の計算を Rust へ移植して生成する。
  対象は MSi2500 のレートと形式 (`0x03`、`0x04`、`0x07`)、MSi001 の PLL・フィルター・ゲイン
  (`0x09` 経由の SPI 書き込み)、GPIO (`0x08`)。
  検証環境で記録したチャンネル別・ゲイン別のレジスター列を、移植の期待値として自動試験に使う。
- GPIO の表は `DeviceDefinition` の Config で選ぶ。USB ID から互換機と純正機を区別できないためである (2.5 節)。
- 開始直後の形式切り替え前のブロックは、ヘッダーのサンプル番号の増分で判別して捨てる。
- 受信中にサンプル番号の不連続を検出した場合は、欠落としてログと状態の計数に記録し、OFDM の同期を取り直す。
- USB のエラーと抜去は helper の失敗として DriverHost へ通知する。

## 5. 復調パイプライン (helper)

| 段 | 処理 |
|---|---|
| 取り込み | 384 形式の復号、サンプル番号の検査 |
| OFDM | DC 除去、CP 相関によるシンボル同期と小数部の周波数ずれ、SP の PRBS 相関による整数部の周波数ずれ、8192点 FFT、標本化周波数のずれと残留周波数ずれの追従、SP による伝送路推定 (窓の前倒し分の位相補償を含む)、TMCC の復号 |
| 階層ごとの前処理 | ランダマイズ解除 → ローテーション解除 → セグメント間デインターリーブ → 時間デインターリーブ → 伝送路の信頼度を重みにした軟判定デマップ → ビットデインターリーブ → デパンクチャ |
| ビタビ | B 階層 約16.3 M ステップ/秒、A 階層 約0.51 M ステップ/秒 (ブロック並列の整数実装、5.1 節) |
| TS | バイトデインターリーブ → エネルギー拡散の解除 → RS 復号 → 階層の再多重 |

標本化周波数のずれは検証環境で約 +0.6 ppm あり、1時間で約2.2万サンプルに相当する。
FFT 窓の位置は CP と SP の位相傾きで継続的に追従し、整数サンプルの窓移動と小数部の位相補償に分ける。
窓の移動で、シンボル番号、デインターリーバー、ビタビ、PRBS の状態は作り直さない。
この扱いは `isdbt-dsp` の連続受信時の CP 追跡と同じである。

エネルギー拡散のリセット位置は、試作では1フレーム分の候補を RS の符号語判定で総当たりした。
実装では TMCC のフレーム境界と各段の遅延から決定し、総当たりは初期同期の確認だけに使う。

TMCC の内容が変わった場合 (階層構成の切り替え) は、該当階層の前処理と誤り訂正の状態を作り直す。

### 5.1 ビタビの高速化

ビタビの入出力は「前後に助走を付けたブロックの軟判定値を受け取り、ブロックの出力ビットを返す」形とする。
この境界ならブロック間に状態の依存がなく、スレッド並列も、将来の別実装 (手書き SIMD や GPU) への差し替えも、
同じ入力に対する出力の一致で試験できる。

2.9 節の試作では、16ビット整数メトリックの単純なループを自動ベクトル化しただけで、
1スレッドで B 階層の要求の約3倍の速度が出た。32ビット版でも約2.5倍ある (2.11 節)。
このため、まずこの方式を標準の実装とし、スレッド数は CPU の余裕に応じて設定で変えられるようにする。
AVX2 の明示的な利用と GPU への分担は、複数台の同時受信や性能の低い CPU で処理が足りないことを
実測で確認してから検討する。

既定値は 2.10 節の評価から次のとおりとする。

| 項目 | 既定値 | 根拠 |
|---|---|---|
| ブロック長 | 8,192 ステップ | 助走を伸ばしても処理時間が増えない |
| 助走 | 前後 192 ステップ | 訂正不能が出始める条件まで助走 1,024 ステップと全ビット一致 |
| 量子化 | ±16 にクランプした軟判定値 × 12 を8ビットへ丸める | f32 版と訂正能力がほぼ同じで、飽和がほぼない |
| まとめて復号するブロック数 | スレッド数 × 4 | 4スレッドで 16 ブロック (約13万ステップ、B 階層の約7シンボル、約6.6 ms) の遅延 |

逐次投入では、後ろの助走が届くまでブロックを保留し、まとまった数のブロックを並列に復号する。
ブロック境界を先頭からの固定の区切りとし、助走を入力の範囲で切り詰める規則を一括処理と共通にすると、
投入の単位によらず出力が一括処理と一致する (2.11 節)。
この性質は、逐次版を一括版との比較で試験できるようにするために維持する。

信頼度の重み (0〜2) とクランプ (±16) と倍率 (12) の組み合わせは、64QAM の LLR 近似の振幅が
最大でも約14に収まる前提で決めた。重みの算出方法を変える場合は、2.10 節の評価をやり直す。

## 6. TS の再多重

BonDriver は1本の TS を返す必要がある。B 階層には HD のサービスと PAT・PMT・EIT があり、
A 階層にはワンセグのサービスがある。
ARIB STD-B31 の多重フレームでの TSP の位置に従って A・B 階層を元の順序に戻すと、
PCR の時間関係が保たれる。この方式を第一候補とする。
各階層の復号順に混ぜる方式は実装が容易だが、PCR のジッターが残る。
初期段階で B 階層だけを出力する選択肢も残し、方式は未決定事項とする (12 節)。

### 6.1 実装した再多重 (M4)

helper の `remux` は、モデル受信機の動作を 1 フレーム分模擬して、各階層の k 番目の TSP が置かれるスロットを求める。
モデル受信機は 1 シンボルの復調データを FFT のサンプルクロックでセグメント番号の昇順、キャリヤーの昇順に読み出し、
デパンクチャ後の符号化ビットが 1 TSP 分 (3,264 ビット) に達した時点でその TSP を出力可能にする
(N.O. Pisciotta, "Remultiplexor ISDB-Tb", Memoria Investigaciones en Ingeniería, núm. 12, 2014 の 7 節)。
BTS のクロックは FFT のサンプルクロックの 4 倍のため 1 スロットは 408 クロックで、
Mode 3・ガードインターバル 1/8 の 1 フレームは 4,608 スロットになる。
13〜17ch の構成 (A 階層 QPSK 2/3 1 セグメント、B 階層 64QAM 3/4 12 セグメント) では、
1 フレームの TSP 数は A 階層 64、B 階層 2,592 で、エネルギー拡散のフレームごとの初期化と一致した。
出力はヌル TSP を除いた階層の TSP だけで、モデルの処理遅延とデータの読み出し開始位置の定数は推定を含む。

各 TSP のフレーム内の位置 k は、エネルギー拡散の系列の位相から求まる。
フレーム番号は、OFDM の TMCC の同期語から求めたフレーム先頭のシンボル番号と、階層の遅延から求める。
Mode 3 の時間インターリーブの遅延 (95×I シンボル) と送信側の遅延補正 (I = 1, 2, 4 で 109, 14, 28 シンボル) の
合計はフレームの整数倍で、検証環境の局では B 階層 (I=2) が 1 フレーム、A 階層 (I=4) が 2 フレーム遅れる。
同期の捕捉の直後は数フレーム分のパケットが一度に出るため、各回の最後のパケットを基準にし、
それより前は k の巻き戻りで遡ってフレーム番号を付ける。

再多重化は、TMCC で使われている階層がすべてそのフレームを過ぎてから、スロット順に出力する。
起動直後は B 階層が A 階層より約 1 フレーム早く出力を始めるため、出力のない階層も待つ。
ある階層が同期できない場合に出力が止まり続けないよう、他の階層が 3 フレーム先へ進んだらそのフレームを出す。

13・15・17ch の録画 IQ では、A・B 階層の全パケット (39,489〜39,491) が再多重の出力に含まれ、
フレームの数え方の誤りを示す不完全なフレームは区間の最初と最後の 3 フレームだけだった。
再多重した TS の各 PCR について、PCR の時刻と、パケット番号から求めた時刻 (1 フレーム 2,656 パケット) の差を
PID ごとに平均すると、A 階層のワンセグの PCR と B 階層の PCR の差は 0.3〜1.4 ms だった。
A 階層の割り当てが 1 フレームずれていれば差は約 231 ms になるため、フレームの対応は正しい。
A 階層の PCR の差は全区間で一定で、パケットの位置が規則的であることも確認した。
同じ局をハードウェアの復調器で受信した TS との並びの比較は未実施である。

## 7. 選局と状態の破棄

ロックまでの時間は、試作では受信開始から最初の TS まで約1.9秒だった (2.12 節)。
内訳は初期同期の蓄積約0.24秒、制御キャリアの検出256シンボル、TMCC 2フレーム約0.46秒、
重みの収束待ち128シンボル、時間デインターリーブ、バイト段の初期探索であり、選局切り替え時の時間は未測定である。
`AsyncTune` の扱い (選局受付と TS 到着の分離) は RTL-SDR と同じとする。

選局では、同期、周波数ずれ、デインターリーバー、ビタビ、PRBS、RS の状態と、
TS の continuity counter の監視状態をすべて作り直す。
旧局の TS が混ざらないことは、試験で TSID を使って確認する。

USB 抜去時は `SetAvailability(false)` と配信停止を即座に反映する。
helper の終了待ちを、デバイス一覧のロックの中で行う必要はない。

## 8. 品質指標

RTL-SDR helper の品質値は RS 成功割合による便宜的な指標である。
フルセグでは階層別の MER (dB) を復調の途中で求められるため、BonDriver の信号レベルへの対応付けを検討する。
MER は RF の C/N とは異なり、受信機の雑音と等化の誤差を含む値である。

## 9. ライセンスと配布

helper は GPL-3.0-or-later とする。`isdbt-dsp` は GPL-3.0-or-later、
libmirisdr は GPL-2.0-or-later であり、移植したコードは helper のライセンスと両立する。
USB の制御は WinUSB を直接使うため、SDRplay API と libusb への依存はない (13 節)。
配布物に helper と依存元のソース、ライセンス宣言を含める扱いは
RTL-SDR helper と同じとする。

ドライバーは、SDRplay のドライバーが導入済みの環境ではそのデバイスインターフェース GUID を
`DeviceDefinition` の `DeviceInterfaceGUID` に指定して使える。
独自の INF を同梱する場合は、SDRplay のソフトウェアとドライバーを取り合うことになる (12 節)。

## 10. 試験

自動試験:

- 移植したレジスター計算と、記録したレジスター列の一致
- 送信側と受信側のインターリーバーを往復させた恒等性 (周波数、時間、ビット、バイト)
- SIMD 版と標準版のビタビの出力の一致
- 欠落、形式切り替え前のブロック、サンプル番号の巻き戻りを含む模擬入力での状態遷移
- TMCC の階層構成の変化に対する状態の作り直し

録画 IQ による回帰試験:

- 13〜17ch の各4.5秒の IQ から TS を生成し、SHA-256 と RS の訂正不能 0 を確認する

実機試験:

- 13〜17ch のチャンネル切り替えの反復 (周期ごとの同期エラー、TEI、CC 不連続、空受信、TSID)
- 数時間の連続受信 (サンプル欠落、RS 訂正数、CPU 使用率、メモリ使用量)
- PX 系チューナーとの同時受信と同時録画
- USB ハブ経由の接続。この機器は等時転送で1マイクロフレームあたり3,072バイトを予約するため、
  ハブを他の等時転送機器と共有すると帯域が足りない可能性がある
- USB 抜去と再接続、Close/Open の反復

### 11.1 M3 の処理時間

`msi2500_frontend demod` は OFDM 復調と誤り訂正を1つのスレッドで順に実行し、段ごとの時間を出す。
15ch の録画 IQ (信号 4.06 秒、B 階層のビタビは4スレッド) での値:

| 段 | x64 版 | x86 版 |
|---|---|---|
| OFDM 復調 | 1.08 秒 (実時間の約0.27倍) | 1.99 秒 (約0.49倍) |
| 誤り訂正 (同期の捕捉を含む全体) | 2.67〜2.72 秒 (約0.66倍) | 3.08〜3.14 秒 (約0.77倍) |
| 誤り訂正 (同期の捕捉後の 2.91 秒分) | 1.89〜1.94 秒 (約0.66倍) | 2.27 秒 (約0.78倍) |

試作の live 構成 (OFDM 復調と誤り訂正を別スレッドで実行) でも同じ録画で実時間の0.685倍となり、
誤り訂正が律速だった。helper は試作と同じ処理時間で、2.11 節の値 (前処理 0.19倍、ビタビ 2スレッド 0.19倍) は
一括処理での計測のため、シンボルごとの逐次処理には当てはまらなかった。

x64 版で同期の捕捉までを含めた誤り訂正の内訳を計測した結果 (A・B 階層の合計):

| 項目 | ビタビ 1スレッド | ビタビ 4スレッド |
|---|---|---|
| 前処理 (時間デインターリーブ、デマップ、量子化、デパンクチャ) | 1.0 秒 | 1.0 秒 |
| ビタビ | 2.34 秒 | 0.8 秒 |
| バイト段 (同期の捕捉、バイトデインターリーブ、RS) | 0.89 秒 | 0.88 秒 |

ビタビのスレッド数を 8、16 へ増やしても、同期の捕捉後の誤り訂正は約0.61倍、約0.56倍までしか縮まなかった。
ビタビ 1スレッドの速度は約3,200万ステップ/秒で、乱数符号語での計測 (約5,200万ステップ/秒) より遅い。
リンク時最適化 (`lto = true`、`codegen-units = 1`) を外すと 2.34 秒から 1.71 秒になったが、
誤り訂正全体は約0.62倍にとどまった。
前処理については、量子化の丸めを CRT 呼び出しのない演算へ置き換える変更と、
遅延線の値と信頼度を同じ要素に置く変更を試したが、どちらも処理時間は変わらず、採用しなかった。
前処理の時間の原因は特定できていない。

実時間の受信には各段が実時間の1倍未満であればよく、M4 で OFDM 復調、前処理、ビタビ、バイト段を
別スレッドへ分けると、それぞれの段は上の値の範囲に収まる。
0.5倍以下という完了条件は、受信と同時に動く他の処理への余裕として設けたため、
M4 のスレッド構成で受信全体の CPU 使用率と欠落の有無を計測してから、条件の見直しか最適化の継続かを判断する。

### 11.2 M4 の実機試験と USB の等時転送

`msi2500_frontend live` は、取り込み、OFDM 復調、A 階層と B 階層の誤り訂正、再多重化をそれぞれ別のスレッドで処理する。
15ch の 600 秒の受信では、CPU 使用率は平均約 1.33 コア、最大約 2.0 コア、ワーキングセットは約 70〜83 MB で、
停止時の各キューの残りは 0.01 秒以内に処理し終えた。誤り訂正の処理は実時間に追従している。
試験は、同じ PC で PX 系チューナーの録画 (EpgDataCap_Bon) と他のアプリケーションが動いている状態で行った。

この条件の 600 秒の受信では、数分に 1 回、等時転送の一部のパケットが `USBD_STATUS_ISO_NOT_ACCESSED_LATE`
(投入が間に合わなかった) で失敗した。投入済みの転送を 32 (256 ms 分) から 64 (512 ms 分) に増やしても起きたため、
helper のスレッドの遅れだけでは説明できない。原因は特定できていない。

失敗の後の扱いについて、次の事実を確認した。

- 失敗した転送だけを新しいストリームとして投入し直すと、受信は続く。
  パイプを止めて全転送を投入し直す方法では、以後の転送がすべて `ERROR_BUSY` で失敗し続け、受信が止まった。
- 失敗の後の約 1 秒間、完了した転送の 1 ミリ秒ごとに 1 パケット分、数秒前のデータが新しいデータとして返った。
  記述子の長さと状態を投入前に消しても起きたため、投入前にバッファーへ印を書き、
  長さが返っても印が残るブロックを捨てるようにした。これで、失敗は前後に飛ぶ番号の列ではなく、1 回の欠落として現れる。
- 欠落のたびに OFDM と誤り訂正を作り直すため、1 回の欠落で約 2 秒の TS が失われる。

BonDriver の試験 (`tests/msi2500_bondriver_live.ps1`、x64、DriverHost は試験用の通信名) では、
13ch と 15ch を 30 秒ずつ受信する選局の切り替えで、選局要求の受付が 78〜93 ms、最初の TS まで約 2.0 秒、
同期・TEI・CC の誤りと PAT の不正は 0、PAT の TSID は 13ch が 0x7C11、15ch が 0x7C17 で混入はなかった。
15 秒ずつの Close/Open の反復では、2 回目の受信中に等時転送の遅れが 2 回起き、CC の不連続で試験が失敗した。

録画で欠落が許されない用途には、等時転送の遅れの原因の特定か、遅れの影響を受けない転送方式
(MSi2500 の代替設定 3 のバルク転送) の評価が必要である。

### 11.3 USB の接続先とバルク転送

11.2 節の試験では、RSP1 互換機はチップセット側の xHCI (AMD `DEV_43EE`) のルートハブに接続され、
同じコントローラーの USB ハブの先に PX-MLT8PE (5 チューナー側と 3 チューナー側) があり、録画中だった。
CPU 側の xHCI (AMD `DEV_149C`、PX-MLT5PE がハブ経由で接続) のルートハブへ差し替えると、等時転送の 600 秒の受信で
欠落は約 0.7 秒の 1 か所 (転送の遅れ 3 回と未書き込みのブロック) に集まり、それ以外の約 599 秒は欠落がなかった。
差し替え前の同じ条件では、欠落は 600 秒の中で数回に分かれていた。
欠落はいずれも転送の投入が間に合わなかった失敗で、機器の故障を示す状態 (不良パケット、ヘッダーの不正) はなかった。

`--transfer bulk` (代替設定 3) は、チップセット側の接続では 4 回中 1 回だけ取り込めたが、5 秒間に 3 回の欠落があり、
小さな欠落は機器の FIFO があふれたときの形だった。CPU 側の接続では、パイプのリセットとストリーミング開始の送り直しを
加えても、最初の読み取りが `ERROR_GEN_FAILURE` で失敗して取り込めなかった。
バルク転送は帯域を予約しないため、等時転送の代わりにはならないと判断した。この経路は評価用として残す。

試作に使ったコード (WinUSB の取り込み、OFDM 復調と MER 測定、誤り訂正) は、M1〜M3 で
`winusb/tools/msi2500_frontend` へ移植し、試作との出力の一致を試験で確かめた。試作のコードそのものはリポジトリに含めていない。

## 13. 採用しなかった方式

- SDRplay API: 互換機を受け付けない可能性があり、別途サービスの導入も必要なため採用しなかった。
- libusb 経由の取り込み: 2.3 節のとおり検証環境で取り込めず、WinUSB の直接利用で目的を満たせたため採用しなかった。
  原因の切り分けは見送った。
- 12 bit 形式 (336) の 8.126984 MS/s: 等時転送の帯域を超えて欠落するため採用しなかった。
  12 bit 形式で 8.064 MS/s 以下に下げてから再標本化する方式は、精度と処理量の比較をしていない。
- 記録したレジスター列の再生による設定: 試作では使ったが、任意のチャンネルとゲインに対応できないため、
  製品の設定方法としては対象外とした。
