# PIX-DT295: 追加USB要求なしのSERVICE内計測

## 測定条件

2026-11-07 JST、Windows x64、利用者申告Rev.01 / TC90532XBG、地デジ・BS/CS接続、LNB電源0、WinUSB。mAgicVISION 0.1.1を入力にした診断用派生イメージを使用しました。独立ソース生成ファームウェアやpix-userlandの試験ではありません。

入力SHA256: `0b2147e190afc7626165594fdedbedc6461c0e1f044b17742123b77fc5026fcc`。派生イメージSHA256: `e25db9b657e6db6b800b50d5a765e8e41e23d9f8f7713b7b9491b6298a7c92b7`。build IDは `DTS1.001`。

計測は[前回のホスト側測定](pix-dt295-stream-measurement.md)で問題となった、毎SERVICE後の約18 msの追加読出しを外しています。SERVICEの既存64-byte応答に、機器内で取得した生産・消費位置、試行・成功回数、FIFO not-ready回数を載せました。送出予算64成功・4096試行、復調器設定、TS内容は維持しています。

## 安定区間の結果

各30秒の受信です。カウンターの安定区間は受信開始基準1秒以降かつ最後のSERVICEを除いた範囲です。開始時の残留データと、停止時のBulk中止によりFIFO待ちが増える末尾を分離しています。CCは保存TS全体の独立解析値です。

BSの試行回数が多い理由は、主に入力不足でFIFO詰め込み関数まで到達しない反復です。安定区間の試行回数平均はCS 64.08、GR 64.19、BS 629.53。FIFO not-ready平均はそれぞれ0.076 / 0.194 / 0.296回でした。FIFO関数は入力不足の反復では呼ばれないため、試行数とFIFO呼出し数は区別しています。

SERVICE所要時間平均はCS 12.066 ms、GR 10.050 ms、BS 13.802 ms。SERVICE開始間隔平均は13.309 / 11.258 / 15.034 msです。追加USB読出しによって29～31 msへ伸びた前回とは異なり、通常版で観測した周期・レートの範囲に近い結果となりました。ただしファームウェア内の追加命令にも実行時間があり、無負荷の測定を保証するものではありません。

## 分かったこと

CS・地デジでは、FIFOが空くのを待ち続けて4096試行を消費する動作が主因ではありません。ほぼ待ちなしで64回の補充を終え、次のSERVICEまでの間にリングがほぼ満杯へ戻ります。CSは処理直後も99%以上の占有を保ち、地デジも次のSERVICE開始時には全サンプルで99%以上でした。BSは処理後ほぼ空になり、次の開始時にも余裕があります。

従って、この診断版では「ホストによるSERVICEの呼出し周期と1回の送出枠に対し、CS・地デジの取り出しが入力に追い付いていない」という切り分けができました。復調ICのリビジョン差を先に原因とする説明より、送出経路の処理量・呼出し頻度を優先して調べる根拠があります。

位置の剰余差は、ハードウェアの上書きと入力抑止・入力段での取りこぼしを区別しません。失われたパケット数そのもの、TSエンジンのオーバーラン通知、計測命令を取り除いた通常版での瞬間占有量は未確認です。CC異常を根本修正した結果でもありません。

3本とも同期・TEI・形式・PAT CRC異常は0、要求TSIDとの一致を確認しました。BSのHost入力全区間には開始停止境界を含むCC異常10件があるため、保存区間の0件を全区間無欠落とは表現できません。スクランブルTSを含み、内蔵カードによる復号や映像・音声再生の確認は対象外です。

全区間のCS 2257回中1回、GR 2668回中1回は4096試行に達しています。どちらも最後のSERVICEで、停止時にBulk読出しが中止された境界と重なります。これらを安定区間のFIFO待ちとして集計することは適切ではありません。

## 実装と検証

[診断コードと生成器](../experimental/dt295-telemetry/README.md)は344 bytesのFRコードを、既存ローダーが退避する2 KiBのブート領域の未使用末尾へ追加します。元の1552 bytesと合わせ1896 bytesで、退避・復元範囲を拡大する必要はありません。residentのバッファー・BSS・スタックをコードの配置先に転用していません。

3か所の呼出し先即値、build ID、チェックサムを更新します。カウンター本体は追加ラッパーのスタック上に置き、専用の計測用ポインターを毎コマンド終了時に0へ戻します。応答status・detailと元の戻り値、保存レジスター、FIFOのスタック引数を保持する検査があります。

検証は以下の範囲です。

- 元の送出ループ先頭44 bytesの完全一致、ブート領域容量、入力SHA256、呼出し先の元値、immutableチェックサムの検査。
- FR命令モデル9ケース: 64成功、FIFO待ち後の成功、入力待ち後の成功、4096回のFIFO待ち／入力待ち、負値での終了、他コマンド／他機種テーブルの通過。割り込み・キャッシュのモデルではありません。
- x86/x64 Hostビルド、既存DT295模擬試験とtorne runtime試験、生成した実SBC2を使う模擬USBロード・復元。
- 診断応答の読取り、エラー／別コマンド時の誤採用防止、元スナップショットを持たない採用セッションでの復元拒否。
- Python最適化モードでも未検証入力を拒否し、ファームウェアを生成しない検査。

## 復元と次の対象

測定は冷起動から専用Hostで実施し、終了時は通常のDT295常駐維持経路に代えて、保存した試験前のRAM・ブート領域を書き戻して読戻し検証する経路を使用しました。復元処理は約87.3秒、29074制御転送を行ってエラーなく終了し、測定用Hostも終了しています。PIX-DT295のPnP problem codeは0。既存TVTest・EDCB・DriverHostは同じPIDで継続しています。

次の対照試験は、診断を維持して成功上限64を128、256へ段階的に変え、FIFO待ち、リング占有量、CC、制御要求の応答時間を比較する方法です。試行上限やRF設定まで同時に変えると効果を分離できません。送出量を増やすだけで解消する保証はなく、長期的にはホストの制御往復からFIFO補充を切り離す構成も検討対象です。

通常配布物や開発用TVTestへのデプロイ、コミット、pushは今回の対象外です。

## 送出上限の対照試験

64・128・256回を比較した結果、256回版は各30秒の保存TSで全方式のCC異常が0件でした。応答時間と受信開始境界の詳細は[対照試験結果](pix-dt295-budget-comparison.md)に記録しています。
