# 抜去後の受信機のつなぎ直し

受信中に USB を抜き差しすると、利用側が BonDriver を開き直すまで受信が再開しなかった問題と、その対処の記録です。
BonDriver と DriverHost の間の応答を増やしたため、理由、維持した契約、移行の扱い、試験の範囲を残します。

## 現象

TVTest で PX-W3U4 の受信中に USB を抜いて挿し直すと、挿し直した後も映像が戻りませんでした。
チャンネルを変えても選局は失敗し続け、TVTest を閉じて開き直すまで受信できませんでした。

## 原因

DriverHost_PX4 のデバッグログ（`_DEBUG_MSG` を定義したビルドと `DebugLog=true`）で、次の順序を確認しました。

1. 抜去の直後に受信の転送がすべてエラーになり、`DeviceManager::Remove()` が機器を一覧から外して `SetAvailability(false)` を反映しました。
2. 古い機器のオブジェクトは、開いている受信機と WinSCard のカード接続が参照を持つため、TVTest が閉じるまで破棄されませんでした。
   この待機は通知スレッドを止めず、挿し直した機器は約 7 秒後に新しいオブジェクトとして登録され、受信できる状態になりました。
3. TVTest の制御の接続は、開いたときに割り当てられた古い受信機を指したままでした。チャンネルの変更は古い受信機で I2C の転送に失敗し、
   `FAILED` が返りました。

制御の接続が受信機を選ぶのは `OPEN` のときだけで、BonDriver も DriverHost も、抜去された受信機から新しい受信機へ移る手順を持っていませんでした。
DriverHost の応答は信号なしなどの失敗と抜去を区別しなかったため、BonDriver は開き直すべき状況を判断できませんでした。

挿し直した直後の PX-W3U4 は、約 7 秒の間に接続と切断を 7 回繰り返しました。コネクターの接触によるものか、別の原因があるかは、このログからは区別できていません。

### XIT-SQR100 の場合

XIT-SQR100 では、BonDriver のつなぎ直しを加えた後も受信が再開しませんでした。TVTest を開き直しても受信機を開けない場合があり、
TVTest を閉じた状態で抜き差しし直すまで回復しませんでした。DriverHost のデバッグログで、次の順序を確認しました。

1. 抜去の通知を受けた `DeviceManager::Remove()` が機器の最後の参照を解放し、`XitSqr100Device::Term()` が始まりました。
   受信機のデストラクターは、開いている受信機が閉じるまで待ちます。
2. `Remove()` は機器の到着と抜去の通知を処理するスレッドで呼ばれるため、この待機の間は通知の処理が止まりました。
   挿し直した XIT-SQR100 の到着は、約 40 秒後に TVTest を閉じた時点で初めて処理されました。

PX-W3U4 では、TVTest が内蔵カードリーダーを WinSCard で使っていたため、カードの接続が古い機器の参照を持ち、破棄そのものが後回しになっていました。
そのため通知のスレッドは止まらず、この問題が表に出ていませんでした。カードの接続を持たない機器では、どの機種でも同じ待機が起こりえます。

開き直しても受信機を開けなかった試験では、到着の通知が処理されないまま失われ、挿し直した機器が登録されなかったと推定しています。
Windows が待機中のウィンドウへの通知をどう扱うかは確かめていないため、推定にとどまります。

破棄を別のスレッドへ移した後の試験では、挿し直した XIT-SQR100 は抜去の約 10 秒後に登録されましたが、BonDriver はつなぎ直しませんでした。
古い機器の `Term()` が抜去の直後に受信機を登録から外していたため、抜去の印が残らず、信号レベルの取得の失敗が `FAILED` のまま返っていました。

## 対処

### DriverHost

1. `CtrlStatusCode::DEVICE_REMOVED`（3）を追加しました。
2. `DeviceManager::Remove()` は、`SetAvailability(false)` の後に `ReceiverManager::MarkRemoved(path)` を呼びます。
   `ReceiverManager` は、その時点で同じ機器のパスで登録されている受信機に抜去の印を付けます。挿し直した機器は同じパスで後から登録されるため、印を引き継ぎません。
3. `ReceiverManager::SearchAndOpen()` は、抜去の印がある受信機を検索から外します。古い機器の空いている受信機を開こうとして失敗する手間がなくなり、
   `@id:` と `@serial:` による選択でも、古い機器と新しい機器を重複として扱いません。
4. 制御のサーバーは、受信機に対する要求が `FAILED` になったとき、その受信機に抜去の印があるか、受信機が登録から外れていれば `DEVICE_REMOVED` を返します。
   機器の `Term()` は、開いている受信機が閉じるのを待つ前に `Unregister()` で登録から外すため、破棄が後回しにならない機器では抜去の印が残りません。
   開いている接続が持つ受信機が登録にない状態は、機器の破棄の途中だけで起こります。
5. `DeviceManager::Remove()` は、機器の最後の参照を `std::async` で別のスレッドへ渡して破棄させます。通知のスレッドは破棄を待たずに戻るため、
   開いている受信機が残っていても、挿し直した機器の到着を処理できます。破棄の完了は `DeviceManager` のデストラクターで待ちます。
   DriverHost はサーバーを先に止めて受信機を閉じてから `DeviceManager` を破棄するため、この待ちは終わります。
   スレッドを作れない場合は、従来どおり通知のスレッドで破棄します。

### BonDriver

1. `CtrlCmdClient` は直前のコマンドの応答の状態を保持し、`LastDeviceRemoved()` で抜去による失敗を判定します。パイプの失敗は `FAILED` として扱います。
2. `SetChannel()` で `DEVICE_REMOVED` を受けた場合は、新しい受信機へつなぎ直してから、同じ要求を 1 回だけ選局し直します。
3. 利用側は受信が止まってもチャンネルを変えない限り `SetChannel()` を呼ばないため、定期的に呼ばれる `GetSignalLevel()` でも抜去を検出します。
   つなぎ直しに成功すると、最後に選局に成功したチャンネルを選局し直し、TS をパージします。
4. つなぎ直し（`ReconnectLocked()`）は、新しい制御の接続で受信機を開き、データのパイプを結び付けて受信を開始できたことを確かめてから、
   古い接続の読み出しを止めて閉じ、新しい接続へ差し替えます。新しい受信機を開けない間は古い接続を残すため、`open_` と利用側から見た状態は変わりません。
5. `GetSignalLevel()` からの試行は 2 秒の間隔を空けます。試行ごとに DriverHost への接続と受信機の検索を行うため、機器が戻るまでの間の負荷を抑える目的です。
   `SetChannel()` は利用者の操作による選局のため、この間隔を待たずに試します。
6. つなぎ直した後の LNB 給電は、古い受信機を閉じた時点で解放されるため、選局し直すときに新しい受信機で入れ直します。

## 維持した契約

- コマンドの版（`command::VERSION`）は変えていません。`DEVICE_REMOVED` への対応は応答で判断します。
- 古い BonDriver は `SUCCEEDED` 以外を失敗として扱うため、新しい DriverHost の `DEVICE_REMOVED` を従来の `FAILED` と同じ意味で受け取ります。
- 新しい BonDriver と古い DriverHost の組み合わせでは `DEVICE_REMOVED` が返らないため、従来どおり開き直すまで受信は再開しません。
- 抜去されていない受信機の失敗（信号なし、選局のタイムアウトなど）は従来どおり `FAILED` で返り、BonDriver はつなぎ直しません。
- 古い機器のオブジェクトの寿命と、機器の中での破棄の順序は変えていません。古い受信機は、BonDriver が接続を差し替えて閉じた時点で従来の手順により閉じます。
  変えたのは、最後の参照を解放するスレッドだけです。
- `OPEN` と `CLOSE` の応答には `DEVICE_REMOVED` を返しません。どちらも制御の接続が指す受信機を差し替えるか消すためです。

## 試験

### 自動試験

`tests/device_identity_test.cpp` に `TestRemovedDevice` を加えました（x64 と x86 で成功）。

- 抜去の印を付けた機器の受信機は、開いているものも空いているものも `IsRemoved()` が真になり、空いている受信機も検索で開かれないこと
- 空のパスでは印を付けないこと
- 同じパスで後から登録した受信機は印を引き継がず、機種名による選択と `@id:` による選択の両方で、新しい機器の受信機が選ばれること
- 開いていた接続が閉じた後は、従来どおり古い受信機を登録から外せること

`tests/bondriver_reconnect_test.cpp` で、BonDriver のつなぎ直しを検証します（x64 と x86 で成功）。
制御とストリームのサーバーを `PX4_ISOLATED_TEST_HOST` で分離した IPC 名のまま同じプロセスで動かし、TS を出す模擬の受信機を登録して、実際の BonDriver から接続します。

- 抜去の印を付けて古い受信機を失敗させると、`GetSignalLevel()` で挿し直した受信機へつなぎ直し、同じ周波数で選局し直して、新しい受信機の TS が届くこと。古い受信機は閉じられること
- 抜去でない失敗（信号レベルの取得の失敗）では、空いている別の受信機へつなぎ直さないこと
- `SetChannel()` は試行の間隔を待たずにつなぎ直し、要求したチャンネルを選局すること

抜去した機器の破棄を別のスレッドへ移した変更は、Windows のデバイスの列挙と通知に依存するため、自動試験の対象外です。

### 実機試験

Windows 11 x64、TVTest（64 ビット版）で、このブランチの BonDriver_PX4 と DriverHost_PX4 の x64 版を使って確認しました。
B-CAS カードは PX-W3U4 の内蔵カードリーダーへ挿し、どちらの試験でも TVTest がこのリーダーを使っていました。
PX-W3U4 の試験は抜き差しした機器のカードの接続が古い機器の参照を持つ経路、XIT-SQR100 の試験は古い機器の参照を持つ接続がない経路に当たります。

- PX-W3U4：BS の受信機を 2 つ開いて受信中に USB を抜き、約 10 秒後に挿し直したところ、どちらもチャンネルを変えずに受信が再開しました。
- XIT-SQR100：BS を受信中に USB を抜き、約 10 秒後に挿し直したところ、チャンネルを変えずに受信が再開しました。
  DriverHost のデバッグログでは、抜去から約 10 秒後に挿し直した機器が登録され、ファームウェアの読み込みの約 1 秒後に BonDriver が新しい受信機を開いて選局し直していました。
  挿し直してから受信の再開までは約 4 秒でした。
- 最終の変更（登録から外れた受信機を抜去として扱う変更）を加えた後に、PX-W3U4 の抜き差しをもう一度行い、チャンネルを変えずに受信が再開しました。
- 最終の変更を加えた後に、地上波を受信中の抜き差しと、地上波と BS を同時に受信中の抜き差しを行い、どちらもチャンネルを変えずに受信が再開しました。

次の条件は確認していません。

- 挿し直すまでの時間を長くした場合と、抜き差しを短い間隔で繰り返した場合
- EDCB など TVTest 以外の利用側（`GetSignalLevel()` を定期的に呼ばない利用側では、次の `SetChannel()` までつなぎ直しが起きません）
- PX-W3U4 以外の機種
