# PIX-DT295ファームウェア比較（2026-11-06）

Windows 11 Pro x64（10.0.26300）、PIX-DT295 `06b8:103b`、WinUSB 1.0.0.1、地デジ・BS/CSアンテナ接続済み、アンテナ給電0の構成で比較しました。Hostは `70301a0` を基準とした[実機検証の最小修正版](pix-dt295-validation.md)で、ファームウェア間では同じx64バイナリーを使用しています。通常の受信Hostとの競合を避けるため、専用IPCとDT295だけの機器定義を使用しました。

## mAgicVISION 0.1.0と0.1.1

新版は[mAgicVISION v2](https://github.com/makeding/mAgicVISION/releases/tag/v2)の `magicvision-firmware_0.1.1_all.deb`（2026-11-06公開）から取得しました。旧版は `0.1.0+20261104.160644` です。

| 項目 | 旧版 | 新版 |
|---|---|---|
| firmware.bin サイズ | 289,424 bytes | 289,424 bytes |
| SHA-256 | `d9f549b29d286c2ff1e7daf4237e2205bb8a5a2affbb98362bce137b8b42a33f` | `0b2147e190afc7626165594fdedbedc6461c0e1f044b17742123b77fc5026fcc` |
| build ID | `bd7efbdd5060f36c` | `24d14bb0b741881c` |
| resident ABI | 2 | 2 |

SBC2のヘッダー配置は同じで、195,611バイト位置が異なります。新版を使用したtransport/runtime模擬試験はx86/x64とも合格し、既存Hostから初期化・選局・TS受信が成立しました。上流Hostの変更は取り込んでいないため、この試験は上流v2一式の検証ではありません。

旧版の試験終了後にUSBを物理的に抜き差しして新版へ切り替えました。同じCS ND02（1613MHz、TSID 24608）について、Purgeと初期バッファ破棄後のBonDriver測定結果は次のとおりです。

| ファームウェア / 条件 | 時間 | TSパケット | CC異常 | 結果 |
|---|---:|---:|---:|---|
| 旧版 | 30秒 | 778,240 | 44 | 失敗 |
| 新版・USB抜き差し後の初回 | 30秒 | 780,288 | 0 | 測定区間は合格 |
| 新版・再Open | 180秒 | 3,808,256 | 144,653 | 失敗 |
| 新版・ビルド終了後の再試験 | 30秒 | 631,808 | 24,246 | 失敗 |

いずれも測定区間の同期・TEI・形式エラーは0です。新版180秒試験の初期には比較用ソフトのビルドが重なりましたが、ビルド終了後にもCSの異常が再現しています。同じ再試験のGR13 / BS01・TS0は各30秒で596,992 / 346,112パケット、CC異常0でした。

新版初回30秒の測定が0でも、Hostの開始・終了を含む入力にはCC jumpが28件あり、全区間無欠落ではありません。保存TSの独立解析でも新版180秒のCC異常144,653件とPATのTSID 24608を確認しました。短時間結果には変動があり、新版への交換だけでCSが安定するという根拠は得られていません。原因をファームウェア単独へ限定する比較でもありません。

旧版は比較用に保全しました。安定性の改善が確認できていないため、リポジトリの同梱ファームウェアと既定設定の更新は見送りました。

## pix-userlandの公式ファームウェア経路

[pix-userland](https://github.com/Khronos31/pix-userland)の `42364ad24f4fbcac2a611e0992d6f08a1cbd360f` と、同プロジェクトが指定するdtv-userland-core `ba83577710101f9036f11deffeb97464f4212246` を使用しました。ビルドしたバイナリーのバージョン表示は1.0.0です。

使用した `firmware/dt295.bin` はD295A1形式、1,839,100 bytes、SHA-256 `3cabe15f585a8a7a7d7b9b3db548b677b0732c13926dc3a2b5270acf1bc6ffc8` です。メーカー由来の材料を使用する別経路であり、mAgicVISIONのSBC2ファイルと交換可能な形式ではありません。

上流Windowsビルド手順のLLVM-MinGW 20250910 UCRTとlibusb 1.0.30でx64ビルドが成功しました。Windows OS thread proofとDT295 stream Windows I1/I2 proofも合格しています。ネイティブGCC 16.1での別ビルドはpthread型定義の衝突で失敗しました。

実機は列挙できましたが、公開CLIの `pixd` は受信前に終了コード70（INTERNAL）となりました。Windows制御ワーカーのAF_UNIX接続が `WSAEINVAL=10022` で失敗しており、同じツールチェーンの独立した小規模プログラムでも再現しています。ユーザー専用ACLのruntimeディレクトリーは上流の親ディレクトリー検証を通過しています。原因の確定には至っておらず、Windows全般で利用できないことを示す結果ではありません。

IPCの問題とUSB制御を分けるため、同じ製品コードのReceiverAdapterを直接呼ぶ診断プログラムでも確認しました。mAgicVISIONの常駐コードを残さないよう、切り替え前にUSBを物理的に抜き差ししています。

| 段階 | 結果 |
|---|---|
| 公式ファームウェア起動 | 成功 |
| 制御セッション認証 | 成功 |
| カードインターフェース初期化 | 成功 |
| カード有効化 | 事前条件で停止（raw=0、通知あり） |
| 選局・TS受信 | 未到達 |

B-CASカード装着済みの申告があり、カードを抜いて奥まで挿し直した後も同じ状態でした。既存コードは `raw=0 && 通知あり` を有効化可能と扱わず、ReceiverAdapterはNO_CARDを返します。この結果だけで物理的な未挿入やカード故障を断定することはできません。調査用の追加ログは失敗箇所・状態値だけで、カード状態のガードやプロトコルの変更はありません。

別のB-CASカードへ交換した後も同じ診断を実行し、`raw=0 / 通知あり`、open時のNO_CARDで停止しました。選局・TS受信には未到達で、カード交換による変化は確認できていません。

pix-userlandのTS受信は今回成立していないため、mAgicVISIONとの受信品質比較は未完了です。またpix-userlandは内蔵B-CASとハードウェアPID選別・復号を使う経路で、mAgicVISIONの全多重TS出力とは条件が異なります。今後受信できた場合も、出力PIDとECMの制約を揃えた評価が必要です。

## USB転送時間の追加計測

Hostへ段階別の転送回数・IN/OUT所要時間・delay要求値と実時間の集計を追加しました。転送ごとのファイル出力やペイロード記録はなく、コマンドロック下で集計し、初期化・選局・受信停止・Closeの区切りで出力する診断です。通信失敗後の再送禁止、タイムアウト、キャンセル、Bulk読出し数とサイズは維持しています。

機器はWinUSBの照会でUSB High-Speed（code=3）でした。再Open時の初期化は31.25秒で、10,217回の制御転送に30.70秒、delayに0.48秒を使っています。IN 5,125回に15.35秒、OUT 5,092回に15.35秒で、転送一回の平均は約3msです。約93秒の初回初期化を同じ計測コードで測った結果ではありませんが、少なくとも再Openの約31秒は主に制御転送時間です。

CSの20秒測定では、SERVICEが1,505回、平均間隔13,299µsでした。capture開始・状態確認・停止も含む制御IN 1,525回は計4.57秒（平均約3ms）、OUT 1,525回は計13.88秒（平均約9.1ms）です。独自コマンドはOUTでディスパッチし、続くINで応答を読むため、SERVICE実行を含むOUT側に受信中の増分が集中しています。集計値から、USBホスト側の待ちと機器内部の処理時間をさらに分離することはできません。

別の20秒試験でも地デジのSERVICE間隔は11,249µs、受信量は約2.9MB/秒でした。USB入力量をSERVICE回数で割ると約32KB/回となり、処理頻度に応じて出力レートが頭打ちになる観測と整合します。ただしこれは実測上の対応であり、ファームウェア内部の固定上限や機器内の欠落位置を確定した結果ではありません。

### Bulkキューの比較

[MicrosoftのRAW_IO説明](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/winusb-functions-for-pipe-policy-modification)に基づき、同時投入したBulk読出しがWinUSBのキュー処理で遅れる仮説を比較しました。4本×16KBを維持し、最大パケット512 bytesと最大転送サイズ2,097,152 bytesを確認したうえで、試験用HostだけRAW_IOを有効にしました。全readのキャンセル・回収後に元のポリシーへ復元しています。

| 地デジ20秒 | TSパケット | CC異常 | SERVICE平均間隔 |
|---|---:|---:|---:|
| 通常 | 308,224 | 8,347 | 11,249µs |
| RAW_IO | 308,224 | 8,234 | 11,251µs |

RAW_IOでもCS20秒にCC異常15,824件が残りました。地デジの受信量・処理間隔はほぼ同じで、Bulkキューの変更だけで改善する根拠は得られませんでした。試験用RAW_IOコードは差分から除き、診断用集計だけを残しています。

今回の変更は診断追加であり、受信欠落の修正ではありません。x86/x64のHostビルドとbootstrap / loader / session / USB window / stream input / transport / runtimeの既存模擬試験、およびtorneモードのruntime試験は合格しました。純正環境とのUSB手順比較と、制御OUTの待ち時間をホスト側・機器側に分ける調査が次の対象です。

## 続く切り分け

### USB接続先変更後の追加試験

USBを別の接続先へ移した後も、同じx64 HostとmAgicVISION 0.1.1で確認しました。接続先はWindowsのLocationInfoで `Port_#0006.Hub_#0001`、LocationPath末尾は `USBROOT(0)#USB(6)` です。USB速度や変更前とのコントローラー共有関係は未確認です。

| 放送方式 | 測定時間 | TSパケット | CC異常 | 結果 |
|---|---:|---:|---:|---|
| CS ND02 | 180秒 | 2,772,992 | 143,766 | 失敗 |
| GR13 | 30秒 | 461,824 | 12,290 | 失敗 |
| BS01/TS0 | 30秒 | 346,112 | 0 | 測定区間は合格 |

同期・TEI・形式エラーはいずれも0でした。保存TSの独立解析でも各CC異常数と要求TSIDを確認しています。CSの初回選局は初期化込み94,433ms、次のOpenでのGR13は32,297msでした。CSのSERVICE呼出し間隔は平均11,308µsで、変更前の新版180秒試験の8,233µsより長くなっています。

接続先変更による改善は確認できず、この測定では地デジにもCC異常が出ています。ただし、接続先以外の時間変動や機器状態を固定した反復比較ではないため、ポートだけを原因と断定する根拠にはなりません。

### 純正視聴確認後のWinUSB再試験

利用者から、純正ドライバーと専用視聴ソフトではCSを含めて正常に視聴できるとの報告がありました。これは視聴確認であり、純正経路のTSにCC異常がないことを計測した結果ではありません。

純正パッケージを保存してWinUSB 1.0.0.1へ戻し、USBを物理的に抜き差しした後、同じ接続先とmAgicVISION 0.1.1で地デジ→BS→CSを各30秒測定しました。

| 放送方式 | TSパケット | CC異常 | 結果 |
|---|---:|---:|---|
| GR13 | 391,168 | 14,085 | 失敗 |
| BS01/TS0 | 346,112 | 0 | 測定区間は合格 |
| CS ND02 | 462,848 | 23,224 | 失敗 |

同期・TEI・形式エラーはすべて0で、保存TSの独立解析でもCC異常数と要求TSIDを確認しました。初回選局は初期化込み94,300msでした。BSのHost入力全区間にはCC jumpが17件あり、測定区間の合格を全区間無欠落とは扱えません。純正環境の視聴結果と合わせ、当面は独自制御経路のUSB転送・SERVICE処理を優先して切り分ける必要があります。

### DT295-TVTest-Kit 1.1による追試

後続の調査では、Codexから起動したプロセスが使うAppDataパスがパッケージ専用領域へ仮想化されていることを、通常ファイルの最終パス照会で確認しました。AF_UNIX単独試験はAppData内の7条件すべてでconnect時の10022を再現し、AppData外の専用ディレクトリーでは7条件すべてで接続・1 byte送受信に成功しています。後者はより長い78-byteパスでも成功しました。通信フォルダーは現在ユーザー所有・現在ユーザーのみFullControlとしています。

AppData外へruntime-dirを指定すると、DT295-TVTest-Kit 1.1同梱の元バイナリーのままpixd起動と受信が成立しました。このキットはpix-userland 1d606beとCore cf2aedfを基準とする改造版です。カードraw=0を通知履歴によらず有効化可能とする変更、アイドル中の認証維持、複数ECM経路等の変更が含まれます。最初に試した上流版の結果とは区別する必要があります。

| 放送方式 | CLI指定時間 | 保存TSパケット | CC / 同期 / TEI / 形式 / scramble |
|---|---:|---:|---|
| GR13 | 45秒 | 332,211 | 0 / 0 / 0 / 0 / 0 |
| BS01/TS0 | 45秒 | 374,043 | 0 / 0 / 0 / 0 / 0 |
| CS ND02 | 60秒 | 33,465 | 0 / 0 / 0 / 0 / 0 |
| CS ND08 | 45秒 | 185,104 | 0 / 0 / 0 / 0 / 0 |
| CS ND22 | 45秒 | 256,566 | 0 / 0 / 0 / 0 / 0 |

保存TSの独立解析で要求TSIDとPAT CRC異常0も確認しました。指定時間には番組情報取得・経路準備を含むため、実際の保存区間は短く、CS ND08/ND22のPCR範囲は約33.7/37.4秒です。両方で映像・音声PESを確認しています。CS ND02はPCR・番組情報のみで映像・音声PESがなく、全番組の視聴成功や全多重の受信品質を示す試験ではありません。契約状態・PID経路等の切り分けが残ります。最初の短時間試行の初期制御読出しにUSB timeoutが1件あり、後続試験では再現していません。

今回のIPC停止は、キット本体の修正を要する不具合と断定する結果ではありません。通常のターミナルから同じAppDataパスを使う比較は未実施です。PID選別を行うキットと全多重TSを出すmAgicVISIONの単純なレート・欠落比較もできません。

利用者申告では、この実機はRev.01、復調ICはTC90532XBGです。コードにはTC90532/TC90522やRev.01/02の明示的な切り替えがなく、pix-userlandはDT295用レジスター列を使用し、mAgicVISION HostはDT295用常駐ファームウェアへ委譲します。上記の実機受信成立と、IC型番を明示した設計保証は区別しています。

mAgicVISION側では、SERVICE処理量、USB制御転送とBulkの待ち合わせ、開始・停止境界が引き続き調査対象です。

今回の比較によって、ソースビルドFRファームウェアのDT295用HALや物理I²Cが検証されたわけではありません。映像・音声の再生、内蔵カードによる復号成功、数時間録画についても確認済みの範囲には含まれません。
