# PIX-DT295 の内蔵カードリーダー

PIX-DT295 の内蔵カードリーダーを DriverHost_PX4 から制御し、WinSCard_PX4 の内蔵リーダーとして公開する実装の設計と検証範囲を記録します。
この文書の「検証環境」は、Windows 11 x64、PIX-DT295（`06b8:103b`、利用者申告 Rev.01）1台、B-CAS カード1枚、地上波アンテナ接続の構成を指します。

## 構成

内蔵カードは MB86M01 のカード UART（`0x00fea000`〜`0x00fea03c`）に接続されています。
レジスター配置は Sony torne CECH-ZD1J の MB86H47A と同じですが、カード検出の極性と電源投入の手順が異なるため、`dt295/card_uart.cpp` に機種別の実装として分けています。

| 項目 | PIX-DT295 | 根拠 |
|---|---|---|
| カード検出 | `0xfea01c` の bit 10 が1のとき挿入 | 検証環境で挿入時 `0x400`、抜去時 `0` を観測。torne とは極性が逆 |
| 電源投入 | 19項目の書き込み手順（`0xfea004` は最後に `0x0e`） | 検証環境のブート直後の状態から実行し、13バイトの B-CAS ATR を受信 |
| 電源切断 | 5項目の手順の後、ブート直後の待機値へ戻す | mAgicVISION 0.1.0 がカード電源切断後に残す値と一致 |

電源投入の手順は、mAgicVISION 0.1.0 を検証環境で起動してカード電源を投入した状態のレジスター値と、同 0.2.0 の手順表を照合して決めました。
その手順表の待機値はティック数で、ミリ秒として扱った場合に ATR を受信できることを確認しています。

レジスターへのアクセスは、ブート ROM の BC 制御転送で 24 bit の番地を直接指定します。
SourceFirmware が `0x00f10014` などを読み書きするのと同じ要求で、`0x80000` の窓の付け替えは伴いません。
対象はカード UART の16語に限り、ほかの番地へは転送しません。

## FIFO の一括転送

検証環境の BC 制御転送は1回約 3 ms かかります。
カード UART の FIFO は1バイトごとに1回の転送が必要なため、ECM 1回の送受信で制御経路を数百 ms 使います。
地上波受信中の SERVICE は平均約 45 ms 間隔でほぼ連続しており、試験当時の機器側のリング（192 KiB）は地上波で約 51 ms 分でした。リングはその後 6 MiB に広げています（[TSリング](pix-dt295.md#tsリング)）。
1バイトずつの転送を受信と並行させた試験では、カード通信中の区間に CC 不整合が232件発生しました。

このため、ソース生成ファームウェア（DTP3 / DTP4）の PIF1 に操作5を追加し、FIFO を1往復で最大32バイト移します。
要求の word 4 は bit 8〜15 が方向（1=受信 FIFO の読み出し、2=送信 FIFO への書き込み）、bit 0〜7 がバイト数です。
読み出しは受信 FIFO に溜まった数までに限り、空読みで FIFO を進めません。
送信の開始と制御レジスターの設定は、ホストが BC 制御転送で直接行います。

一括転送は PIF1 の導入後、つまり最初の選局以降に使います。
導入前はファームウェアが動作しておらず TS も受信していないため、1バイトずつの直接アクセスで同じ操作を行います。

操作5の追加で主CPU版の本体が 1,936 バイトから 2,188 バイトになり、従来の上限 `0x000e1800` を超えるため、`resident.ld` の上限を `0x000e2000` へ広げました。
`0x000e1000`〜`0x000e8fff` はブート RAM のコード（`0x000e9000` からの領域）から参照がなく、検証環境の電源投入直後は不定値でした。
既存の `0x000e1000`〜`0x000e17ff` と同じ根拠による範囲で、マスク ROM 側の使用までは確認していません。

## 制御ロック

カードの操作は、受信と同じ個体単位の制御ロックと期限付きの転送路を使います。
1回の保持で行う転送を短く区切り、電源投入手順の待機中はロックを手放して SERVICE を止めません。
1回に移すバイト数は、一括転送では32バイト、直接アクセスでは8バイトです。
Close 時の SourceFirmware の復元も同じロックの下で行い、カードの転送と混ざらないようにしています。

## 検証結果

いずれも検証環境で、IPC 名を分離した試験用ビルド（`PX4_ISOLATED_TEST_HOST`）の x64 版を使いました。
`card_reader_reliability` と `card_stream_stress` は B-CAS の初期応答 APDU（`90 30 00 00 00`）を繰り返し送り、応答の `90 00` を成功と判定します。

| 試験 | 条件 | 結果 |
|---|---|---|
| カード単体（選局前、直接アクセス） | 15秒、200 ms 間隔 | APDU 成功25 / 失敗0、最大 436 ms |
| 受信と並行（一括転送の追加前） | 地上波 13ch、基準20秒 + 並行30秒 | 並行区間 594,944 パケット、CC 不整合232、APDU 成功44 / 失敗0 |
| 受信と並行（一括転送） | 地上波 13ch、基準20秒 + 並行30秒 | 並行区間 598,016 パケット、同期 / TEI / CC 0 / 0 / 0、APDU 成功133 / 失敗0 |
| 受信と並行（一括転送） | 地上波 13ch、基準20秒 + 並行60秒 | 基準 398,336 / 並行 1,195,008 パケット、すべて同期 / TEI / CC 0、APDU 成功270 / 失敗0 |

60秒の試験では、DriverHost が受信全体で計数した CC の飛びも0件で、SERVICE の最大間隔は 79 ms でした。
30秒の試験では、カード通信を行っていない基準区間に CC 不整合36件が記録され、そのときの SERVICE の最大呼び出し時間は 122 ms でした。
カード通信と無関係に起きる既存の受信開始時の条件で、[2026-11-06 の実機検証](pix-dt295-validation.md) に記録された未解決の項目に含まれます。

## 未確認の条件

x86 版、BS / 110度CS の受信と並行した通信、実際の番組の復号（`live_b25_reliability` や TVTest）、カードの抜き差し、USB の抜去、複数アプリケーションからの共有、数時間の録画は未確認です。
19200 bps への切り替えは torne と同じ値を使っており、PIX-DT295 での値の妥当性は APDU の成功以外では確認していません。
受信していない状態の APDU は1回あたり最大約 0.4 秒かかります。
