# WinUSB のハードウェア PID フィルター診断

PX4 系・PX-MLT 系・ISDB2056 系の IT930x に、固定 PID 一覧を設定して USB 転送量と TS 品質を比較するための機能です。
通常の BonDriver 利用では、従来の null パケット設定が適用されます。診断 API を呼んだ受信機だけが設定対象です。
ISDBT2071、PX-S1UD、PX-BCUD、torne、RTL-SDR などの別実装は、この追加 API の対象外です。
PAT/PMT から PID を自動選択する処理と、TVTest・EDCB のサービス選択との連携は今回の範囲に含まれていません。

## 構成

- `DriverHost_PX4` が IT930x の PID スロットを操作します。
- `CtrlCmdClient::SetPidFilter()` は、受信機を Open した制御接続から要求を送ります。
- `pid_filter_probe.exe` は明示指定した1受信機を開き、同一選局で既定・選別・復元を順に計測します。
- BonDriver の通常 API と既存コマンドの配置は従来どおりです。制御プロトコルの版は `0x00040005` です。

## ビルド

Visual Studio 2022 / v143 で `winusb/build.ps1` を実行すると、x86/x64 の模擬試験と診断ツールもビルドされます。
診断ツールは `winusb/build/<x86 または x64>/Release-static/pid_filter_probe.exe` に生成されます。
同じ場所の新しい `DriverHost_PX4.exe` と、既存環境に合う `DriverHost_PX4.ini`・ファームウェアが必要です。
診断ツールは既に起動しているホストへ接続するため、ホストの自動起動や既存ホストの停止は行いません。
実行中の古いホストは版の確認で拒否されます。

## 受信の比較

録画予約や視聴のない時間帯に、利用者が既存ホストを終了して新しいホストを起動してから実行します。
同じ実機を別ホストと取り合うため、独立した名前のホストを同時に起動する方法は使えません。
`--device-guid` は `DriverHost_PX4.ini` の対応する `DeviceDefinition` の `GUID`、`--index` はその `Receiver` 定義の `Index` に合わせます。BonDriver ini の `ReceiverDefinition` も参考になります。GUIDはモデルの定義なので、同じモデルを複数接続している場合は、同じIndexの空き受信機のうち1つが選ばれます。

```powershell
# GUID・周波数・PID は実際の機器と受信サービスの値へ置き換える。
.\pid_filter_probe.exe --device-guid "{機器のGUID}" --index 0 `
  --system J83B --freq 112750 --pids 0,1,16,17,18,20,0x100,0x101 `
  --seconds 30 > pid-filter-result.csv
```

- `--system`: `J83B`、`ISDBT`、`ISDBS`。
- `--freq`: kHz。地上波の例は `557143`。衛星は第1中間周波数で、必要なら `--stream-id` を付けます。
- `--pids`: 0〜8191の数値をカンマ区切り。`0x` 付きの16進表記にも対応し、上限は64個です。
- 既定は通過リストです。`--block` を付けると指定 PID の遮断リストになります。
- `--seconds`: 各区間の計測時間。各区間の先頭2秒は滞留データを読み捨て、計数から除外します。
- 衛星の LNB 給電は診断ツールから設定しないため、外部給電のある環境が対象です。

指定 PID はそのまま設定されるため、PAT、PMT、PCR、映像、音声、字幕、ECM、番組表等の必要な PID を含めます。
上記の例の PID は受信サービスから調べたものではなく、視聴や復号を保証する設定ではありません。
既存の null 除去が有効な場合、baseline は null を除いた既定状態です。

`pid` 行は区間別・PID別のパケット数、`summary` 行はバイト数・Mbps・CC飛び・同一CC内容変化・過剰再送・adaptation CC・TEI・同期・構造異常の計数です。
設定変更中と先頭2秒を含む全受信区間では、選別前後とも通過するPIDだけを別途追跡し、`retained_overall` にCC・TEI・構造異常を出力します。意図的に除いたPIDのCC飛びはこの計数から除外されます。
filtered の `unexpected_pid_packets` は、通過リスト外または遮断リスト内の PID が残った数です。
終了コードは、全区間にデータがあり計測上の異常がない場合0、異常を観測した場合2、設定・通信失敗の場合1です。
2秒を超えて古いデータが滞留している場合は、区間の PID 判定にも影響します。USBバス上の転送量そのものは測定対象外で、表示するMbpsはDriverHostから受け取ったTSのレートです。

## 設定の寿命と失敗

- 明示的な Restore、次の選局、Close で、受信機の既定の null パケット設定へ戻します。
- Close時の復元に失敗した場合はログに残し、次のOpenでも復元に成功するまで受信機を貸し出しません。
- TSMF はパケット位置で多重を扱うため、ISDB-C / TSMF 受信中の明示的PID選別は拒否します。J.83B は対象です。
- 選別の変更は原子的ではありません。モード切替中は一時的に全PIDを通し、同一モードでは共通PIDを維持して変更分だけ更新します。
- 初回やI/O失敗後は、対象ポートの64スロットを再構成します。別ポートを含む設定全体を直列化し、共有のPID書き込みラッチへの割り込みを防ぎます。
- I/O失敗時は可能な範囲で選別解除を試みますが、解除にも失敗し得るため、エラーを成功扱いにしません。
- 固定PIDのままでは放送側のPMT変更に追従できません。実用のサービス選択連携では動的更新が別途必要です。

## IPC

追加コマンド `SET_PID_FILTER = 40`、要求と応答は148バイト固定、x86/x64共通です。
既存の8バイトヘッダーに、32bitのモード、32bitの個数、16bitのPID×64、32bit符号付きの結果が続きます。
モード0はRestore、1はPass、2はBlockです。Restoreの個数は0、Passは1〜64、Blockは0〜64です。
不正な長さ・個数・PID・モードは実機を操作する前に拒否されます。結果は0または負のerrnoで、非対応は `-ENOSYS`、抜去は `-ENODEV`、入力不正は `-EINVAL` です。
接続の所有する受信機だけが対象で、別アプリが開いている受信機への設定APIではありません。

## 参照と検証範囲

差分更新と共有ラッチの直列化は [koreapyj/px4_drv の変更](https://github.com/koreapyj/px4_drv/commit/59bc6d6e788276e0c67ecd4c05e3a13eec47ccdd)を参考にしています。
Linuxのioctlやbitmap実装は移植せず、Windowsホストの所有権・既定フィルターの寿命へ合わせています。
模擬レジスター試験では差分更新、全64スロット、各I/Oへの故障挿入後の再構成、別ポートの並行要求と入力検査を確認します。
実機での選別結果、USB帯域削減、他チューナー・カード通信との同時負荷、J.83Bのドロップ改善、長時間録画は別途の実機検証が必要です。

## 実機確認 (2026-11-01)

Windows x64、PX-MLT8PE の5チューナー側、受信機0、J.83B 327250 kHzで固定PID選別を確認しました。
SI系PID 0/1/16/17/18/20 の30秒ずつの比較は、既定35.533 Mbps、選別0.572 Mbps、復元35.496 Mbpsでした。
同じ一覧に0x1008/0x1048を加えた20秒ずつの比較は、既定35.529 Mbps、選別4.294 Mbps、復元35.523 Mbpsでした。
選別後の対象外PIDは両試験とも0で、各区間の先頭2秒を除く安定区間のCC・TEI・同期・構造異常は0でした。

切替を含む連続計数では、SI試験は受信開始直後のEIT (PID 0x0012) でCC飛び1件でした。
高レートPIDを加えた試験では、開始直後2件と、選別開始・既定復元の直後にPID 0x1008で各1件のCC飛びを検出しました。
どちらも診断ツールの厳密な終了コードは2で、無欠落試験の合格として扱っていません。
選別機能と安定受信区間を確認できた結果であり、設定切替時の無欠落やJ.83Bの既知のドロップ問題の解消を示す結果ではありません。

受信機1では実際のIPCで、不正個数・不正PID・短いメッセージの拒否、接続継続、Closeと再選局での既定復元を確認しました。
配置したBonDriverでもJ.83Bの3回の選局で計92160パケットを観測し、選局失敗・空受信・同期・TEI・CCエラーは0でした。
複数受信機の同時負荷、カード通信との同時負荷、長時間録画、映像表示・復号はこの試験の確認範囲外です。
