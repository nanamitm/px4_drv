# torneの機器側USBフレーム時計

対象はCECH-ZD1J、Windows x64、PAF2診断です。`--torne-i2c --torne-device-clock` はホストの `host_us` 更新を使わず、core1から `0x00fdbc1c` を読んで期限を判定します。

## 根拠と境界

2026-11-05、既存bootstrapで初期化した実機のUSB制御レジスターとTS時計周辺を、少数の固定アドレスに限定して時系列で読み取りました。候補レジスターへの書き込みはありません。`0xfdbc1c` 下位11bitは128点で1,983カウント進み、ホスト実測は1,983.350ms、各差分の誤差は-882.5～878µsでした。1msのUSBフレーム時計として整合しています。このレジスターの意味は公開データシートによる確定ではなく、実測に基づくものです。

`torne_clock.c` は11bit差分を1,000µs単位で積算し、uint32のマイクロ秒時刻へ延長します。2.048秒の折り返しを越えて使うには、FR側で2.048秒未満ごとに読む必要があります。時刻の精度は1ms単位で、マイクロ秒精度ではありません。

同じUSBブロックへのアクセス量を抑えるため、実レジスターを読むのは256回の時計呼び出しに1回です。この回数は読み取り頻度の間引きだけに使い、ループ回数を時間へ換算する用途には使いません。時刻が変わらない場合は、従来と同じ有限poll上限でCLOCK_STALLEDとして打ち切ります。

この時計はアプリケーションの更新には依存しませんが、USBのSOFが継続する必要があります。USBサスペンド・バス停止中も進む独立発振器の時計ではありません。CPUが2.048秒以上停止した場合の複数折り返しは復元できず、停止後にそのまま継続使用する契約もありません。

## PAF2の追加

- features bit2 (`4`) は機器側USB時計。ホスト時計bit1とは排他で、I²C準備後はfeatures=`5`。
- offset160は下位11bitのraw frame、offset164は延長したマイクロ秒時刻。全体192 bytesの配置は維持します。
- operation6=CLOCK_WAITは、機器側時計で指定時間を待つ診断用要求です。最大5秒で、I²Cを発行しません。
- ホスト供給時計の既存ビルドは `--torne-i2c` で生成できます。

```sh
python3 build_auxiliary.py --torne-i2c --torne-device-clock --out build/device-clock
```

最終診断イメージは4,628 bytes、SHA-256 `7332bc75c6242705d49ff59279428fc6a07072baf55417b518129642acf7ffd1`。

## 実機確認

ホストは2.5秒のCLOCK_WAITを公開した後、2.7秒間はUSB要求・時計更新を発行せず待ちました。実測はホスト2,704,236µsに対して機器2,704,000µs、差-236µs。ホスト時計wordが書き換わっていないこと、PAF2要求が完了したこと、11bitの1周を越えて時刻が進んだことを確認しています。

初回の受信試験ではPAF2応答待ちの `WaitForSingleObject(1ms)` がWindowsのtickへ丸められ、復調器初期化に約3.55秒、選局は既存5秒期限で失敗しました。時計読み取りの間引きだけでは改善せず、応答待ちの同じ1msを既存の高精度タイマーで待つと初期化842ms、選局3,501 / 2,523 / 2,573msでロックしました。復調器の待機条件・探索期限は変更していません。

合計918,493パケット。先頭生データと破棄総数を照合し、同期後の破棄がないことを確認しています。全区間無破棄の厳密基準は未達で、診断ツールは `transport_ok=1 / strict_zero_discard=0`、終了コード1です。終了後の16KB RAM読み戻しは保存前像と一致し、旧core1の再開を確認しました。

算術・サービスの模擬試験はWindows ClangとWSL GCCのASan/UBSanで合格しています。11bit/uint32の折り返し、上位bit除外、停止した時計、CLOCK_WAIT完了・バイト数、lease失効を検査しています。物理USBサスペンド・抜去、CPUの長時間停止は別の検証項目です。
