# DT295 I²C・USB静的解析の根拠

対象はmAgicVISIONの固定版v1パッケージから抽出したSBC2（SHA-256 `d9f549b29d286c2ff1e7daf4237e2205bb8a5a2affbb98362bce137b8b42a33f`）です。この文書は静的解析の記録で、実機上の波形・タイミング・受信の検証結果ではありません。アドレスはこのバイナリと既知DT295ブート前像に限った値です。

## 補助CPUコードの展開

常駐処理 `0x80398e20` 以降は、共有RAMの前像保存、圧縮データの展開、チェックサム検査、コード転送、メールボックス準備、補助CPUの起動処理を含みます。

| 項目 | 値 |
|---|---|
| 圧縮データの常駐VA | `0x803b02f0` |
| 圧縮長 | `0x1811` = 6,161 bytes |
| 展開長 | `0x1fe8` = 8,168 bytes |
| 展開処理 | `0x80399030..0x80399106` |
| チェックサム検査 | `0x80399114..0x80399148` |
| 展開後の32bit BE加算値 | `0xc23550a9` |
| 展開後SHA-256 | `7bf697cc4ef4867f6dfe89a2c3c9103bd9a158b950e584e566e2e965131d9f76` |
| 共有RAM転送先 | `0x017a0000` |
| 補助CPUのコード配置・入口 | `0x000a0000` |
| メールボックス | 共有側 `0x017a3900`、補助CPU側 `0x000a3900` |

圧縮形式は、controlの最上位bit=0なら `control+1` bytesのリテラル、1なら長さ `((control>>4)&7)+3`、後方距離 `((control&15)<<8 | next)+1` のコピーです。後方コピーは重なりを許します。`tools/extract_reference_aux.py` が固定版を検査して再現します。展開結果はソースから作った独自ファームウェアではなく、解析対象の参考コードです。

`0x80399162..0x803991ea` は展開したコードを共有RAMへ書き、readbackで照合します。`0x80399206..0x80399212` には `0x017ffffc` へ `0x000a0000` を書く箇所があります。展開コード先頭はFR命令で、割り込みマスク、スタック設定 `0x000a37fc`、`0x000a0518` 呼び出しとなり、同関数にはメールボックス `0x000a3900` へDTI2 magicとABI=2を書く処理があります。CPU側と共有RAM側の配置を別々の証拠で照合できました。

## I²C呼び出しと物理レジスター

常駐側 `0x803993ec` はoperation=4の64-byteパケットを組み立て、内部転送処理へ渡します。これは外部のUSB入口でoperation=4が使えることとは別です。公開USB通常入口ではoperation=4を拒否する経路があり、内部呼び出しと混同できません。

補助CPU側 `0x000a004c` はoperation=4と要求を検査し、I²Cコントローラーのコンテキストを初期化し、`0x000a1ae8` で転送を開始、`0x000a1c44` で進行させます。物理ベース `0x01684000` は `0x000a011e` の即値から渡されます。コンテキスト内の読み書きコールバックは `0x000a0040` / `0x000a0044` で、実際の32bitロード/ストア命令まで追跡できます。

| 物理アドレス | 静的に確認できた使用 | 主な根拠（補助CPU VA） |
|---|---|---|
| `0x01684fe0` | 転送開始・進行時の状態read、bit `0x80` / `0x10` / `0x08` の分岐 | `0x000a1b60`、`0x000a1cb2` 以降 |
| `0x01684fe4` | 状態/control read、bit操作を伴うwrite、bit `0x80` の異常分岐 | `0x000a1b70`、`0x000a19fc` |
| `0x01684fe8` | 終了・異常処理で `0x3c` をwrite | `0x000a19c4..0x000a19cc` |
| `0x01684ff0` | 初回アドレス、TXデータ、読み取りアドレスのwrite、RXデータのread | `0x000a1c0e..0x000a1c1e`、`0x000a1d46..0x000a1d64`、`0x000a1d86..0x000a1d9c`、`0x000a1dfa..0x000a1e18` |

`0x000a1980` / `0x000a1998` は、コンテキストに保存されたbaseとoffsetを加算して各コールバックを呼びます。従って上記のbase+offsetは単なる候補即値ではなく、最下層のロード/ストアにつながるアドレスとして確認できました。

`0x000a1c0e..0x000a1c1e` は要求アドレスを2倍し、読み取りのみならbit 0を立てて `base+0xff0` へ書きます。TX+RXの途中では `0x000a1d86..0x000a1d9c` が同じ相手アドレスの読み取り値を書きます。これにより7bitアドレスからバス上のアドレスbyteを作る箇所が分かりました。START/STOP/repeated STARTの物理波形の確認は別途必要です。

補助CPUの上位要求処理には相手アドレス `0x10..0x11` の検査があります。pix-userlandの公式経路が扱う `0x20` / `0x22` は8bit表現と考えると対応しますが、異なる経路のアドレス値をそのまま新しい7bit ABIへ渡すことはできません。

## 残っている確認

最下層のロード/ストアまで到達したことと、そのレジスターを主CPUから安全に操作できることは同義ではありません。現在見えている動作は補助CPUからのもので、クロック、リセット、アクセス権、キャッシュ/順序、割り込み、他CPUとの所有権の確認が残っています。

また、既存処理のbudgetはループごとのカウントダウンとして使われる箇所があり、その値をマイクロ秒と解釈する根拠はありません。独立ファームウェアで使う実時間タイマーと絶対期限、NACK/バス異常の正確な区別、失敗時のSTOPとバス回復、途中まで進んだ転送の報告は未確定です。実機検証前にI²C能力ビットを有効化できる段階ではありません。

## USBアダプターの根拠

DT295ブート前像は `0x000e9000` から `0x3910` bytes、SHA-256 `0bdf3af8c2d4ab49edd69740bd751e698e337e2df542ac4cedcbe4ba99c3e9b0`。フック対象 `0x000ea6fc` の元8 bytesは `c46d02b0a810e32b` です。

元のBC OUT処理では、r11が指す構造体のoffset 0が転送先、+4から転送データ、offset `0x46` がselector、offset `0x48` がlengthとして読まれます。根拠は元コード `0x000ea6fc..0x000ea7fa` のロード・ループと、既存ホスト実装 `usb/window.c` の制御要求です。新しい診断アダプターはselector `0x7e`、転送先 `0x000c4620`、length=64の組み合わせに限定し、全パケットを明示コピーしてPIF1コアを呼びます。

対象外要求では、元の8 bytesが行うmask/通常の分岐をソースで表現し、`0x000ea704` / `0x000ea75a` へ戻ります。PIF1処理後は既存のEP0完了処理 `0x000ea8c8` へ戻ります。同処理にはUSBレジスターへのwriteと保存レジスター復帰があるため、限定モデルではこの入口を終点とし、実機での完了成功は主張していません。

これらは観察した命令の仕様化であり、バイナリのブートストラップ全体をビルド成果物へコピーする方式ではありません。機器内の既存USBブート処理自体をソースから再生成する範囲には含めていません。

## 転送進行通知とブート直後の実測

参考補助コードの `0x000a0206..0x000a021c` では、`0x01684090` と `0x016840b0` の読み値をANDし、さらにbit 0を検査したときだけ転送進行関数 `0x000a1c44` を呼ぶ。進行関数内で `0x01684fe0` と `0x01684fe4` を読むため、制御レジスターのbitだけで進行させるtorne HALとは通知経路が異なる。参考コードの停止・終了処理は `0x01684fe4` への `0x40`、`0x01684fe8` への `0x3c`、制御値の再設定の順に行う。bit 0のクリア条件と、実際の転送に伴う通知は未測定。

参考初期化処理 `0x000a0954` には、`0x00f10090` のbit 0の確認、条件付きの `0x00f10114` 設定、`0x01684014` / `0x01684fe4` の分岐、続く `0x016840c0` 設定と書き戻し照合がある。オフセット表 `0x000a1f74` と書き込み順序表 `0x000a1f3c` から、後続の書き込み順を `0xfe8, 0xff4, 0xff8, 0xb0, 0xc4, 0x10` と確認した。初期化条件と値の適用は今後の実機検証対象。

Rev.01のブート状態 `0000` で、PAF1の補助CPUから以下を取得した。割り込み保留・マスクとも0で、バス転送の完了通知は発生していない。

| レジスター | アドレス | PAF1実測 |
|---|---|---|
| I²C状態 | `0x01684fe0` | `00000000` |
| I²C制御 | `0x01684fe4` | `00000000` |
| 割り込み保留 | `0x01684090` | `00000000` |
| 割り込みマスク | `0x016840b0` | `00000000` |
| システム側ゲート | `0x00f10090` | `00010000` |
| システム側設定 | `0x00f10114` | `80000000` |

補助CPUの停止後に共有RAMとブート領域の前像一致を確認した。pix-userlandが既存経路で読む地上波復調器レジスター `0x0e` は、7bitアドレス `0x10` への1 byteのレジスター指定と1 byteの読み取りを試す候補。復調器の電源・リセット、I²C初期化、通知の確認が先に必要。

### システム側のアクセス幅と排他

参考コードのコールバック `0x000a0014` / `0x000a003c` はシステム側レジスターへ16bitでアクセスする。以前の32bit値 `00010000` / `80000000` は、上位半wordにある実際の観測値 `0001` / `8000` に対応する。

`0x00f10090` は、参考コードが読み値のbit 0が0のときにソフトウェア側で取得済みと記録し、解放時だけ16bitの0を書く。過去の単純な診断読み取りで排他が残った可能性があるため、診断を修正し、ビジー時は書き込みを避ける。設定 `0x00f10114` は別のレジスターで、参考初期化は16bitの保存値に対して `(値 & 0xffcf) | 0x20` を書き、16bitで照合する。その後、コントローラー側の設定とリセットへ進む。

USB再接続後、修正版の操作4で `gate=0000 / gate_reacquired=1` を2回連続で観測。操作5では `0x00f10114` に `0x8020` を書いたときと `0x8000` に戻したときの両方で読み戻しが一致した。排他の再取得、補助CPUの停止、共有RAM・ブート領域の復元も確認した。これはシステム設定値の検証であり、I²Cクロック出力や転送完了の実測は含まない。

### 固定復調器読み取り試験

`aux_probe.py --read-demod` は実験用操作6を要求する。対象は7bitアドレス `0x10`、レジスター `0x0e` の1 byteに固定。制御器設定後に制御 `0x01684fe4 == 0x42` と割り込みマスク `0x016840b0 == 1` を照合し、どちらかが違えばSTARTを発行しない。成功と判定するには読み取り、STOP、保存設定の復元、排他の再取得、共有RAMとブート状態の照合が必要。

最初の試験は補助CPUの応答が途絶え、停止後にシステム設定 `0x8020` が残ったためUSB再接続で回復した。参考コードに合わせてコントローラー操作前に排他を解放し、診断の待機ループに上限を設けた版では応答と復元が成立した。最新試験では設定照合の段階7で、制御・割り込みマスクとも `0` を観測。STARTを発行せずにシステム設定 `0x8000`、共有RAM、ブート領域、補助CPU停止状態の復元を確認した。上位のクロック・リセット・アクセス許可のどれが不足しているかは未確定で、復調器の応答は未取得。

### 動作する0.1.1との比較

WinUSBを排他で開く単体診断からmAgicVISION 0.1.1を起動し、地上波 473.143 MHz の選局と、終了時の既存ローダーによる復元が成功した。USBメモリー窓で冷間、初期化後、選局後、復元後を比較した結果は次のとおり。値はUSB経由の32bit表示。

| アドレス | 冷間・復元後 | 0.1.1初期化後・選局後 | ソース生成PAF1稼働中 |
|---|---|---|---|
| `0x00f10004` | `8a010000` | `8a010000` | `8a010000` |
| `0x00f1010c` | `00010000` | `00010000` | `00010000` |
| `0x00f10114` | `80000000` | `80200000` | 通常診断で `80000000`。操作6では上位16bitを `8020` に設定 |
| `0x01700000` | `000200ff` | `000000ff` | `000000ff` |
| `0x01700004` | `0d8f7ff3` | `01000000` | `01000000` |
| `0x017000c4` | `00000000` | `00000000` | `00000000` |
| `0x01700404` | `00040000` | `00040000` | `00040000` |

USB窓から読んだI²C制御器の11レジスターは、0.1.1での選局後もすべて0だった。よってUSB窓の読み値だけで制御器の設定状態やクロック停止を判定できない。0.1.1の補助コードを静的に展開してv1と比較したところ、差分は識別値4 bytesだけで、対象のMMIOアドレスと転送処理は同一だった。次の比較点は、既存補助CPUの内部で初期化が書き込み直後に行う読み戻しと、ソース生成コードの同位置の観測値。

### 補助CPU内の読み戻しと先行初期化

0.1.1の診断用SBC2を2方式で再パックした試験は、いずれも初期化・復元が `-2600` になった。USB再接続後、既知のブート前像、ソース生成PAF1の動作、復元を確認した。

再パックを避け、展開済みの参考補助コードに観測処理だけを入れて、既存の診断ローダーから補助CPU単体を起動した。DTI2の操作9で初期化、操作4で終了。両操作が成功し、システム設定、共有RAM、ブート領域、補助CPU停止状態を復元した。補助CPU内の初期化照合は8件すべて一致。特に `0x016840b0=1` と `0x01684fe4=0x42` を確認した。

初期化の保存前像は `0x01684010=0x00000004`、`0x01684014=0x0f3f001b`、`0x016840c0=3`。ソース生成版の保存をシステム設定切り替えの後に移しても、前二者はどちらも0で、START前の照合に失敗した。

別の観測では、参考コードが設定 `0x00f10114=0x8020` を書く前に、`0x00f1010c` への16bit `0x000b`、`0x01684300` と `0x01684320` の各 `0→1`、`0x01684010` と `0x01684014` の事前設定、複数の `0x01687cxx/0x01687dxx` 書き込みを実行した。どの書き込みが制御器の有効化に必要か、各段階での終了・復元条件は未確定。現段階では診断結果として記録する。

### クロック設定の切り分けと最初のアドレス転送

操作6の先行処理に `0x00f1010c` の16bit書き込み `0x0001→0x000b` だけを追加した。制御 `0x42` と割り込みマスク `1` の照合が通り、7bit `0x10` の書き込みアドレス送信後に割り込み保留bit 0が立った。応答は状態 `0x99`、制御 `0x53` で、参考コードの状態bit 4の判定上はアドレスNACK。レジスター番号やデータは送信していない。先行リセット候補 `0x01684300` / `0x01684320` の各 `0→1` を加えた試験でも同じ結果だったため、診断の既定手順には残していない。

参考の補助コードを単体で起動し、DTI2操作9の後に同じ複合読み取りを操作3で要求した場合も `-2602`、状態 `0x99`、制御 `0x53`。操作4による終了は成功した。独自版もSTOP後にバス使用中bitの解除を確認し、制御器設定、システム設定 `0x00f1010c=0x0001` と `0x00f10114=0x8000`、共有RAM、ブート領域を復元した。

通常の常駐コードには、補助コード単体の操作9に含まれない `0x00f10014` / `0x00f10018` の16bit操作がある。地デジ復調器の給電・リセットとの関係は未確定。次は通常の選局経路でこれらの値と順序を採取し、アドレスACKが得られる条件を比較する。

### 主CPU側GPIOを加えた復調器読み取り

Rev.01の通常経路で `0x00f10014 / 0x00f10018` の上位16bitは、ブート時 `0000 / 0000`、初期化後と地デジ選局後 `d082 / 0002`、復元後 `0000 / 0000` だった。命令列 `0x803974ae..0x80397582` に、方向bit 1の設定、出力bit 1のLow→Highと待機がある。

最初に `d082 / 0002` を使って読み取りが成功し、次に方向・出力ともbit 1だけに限定しても同じ結果を得た。WinUSBで既知のコールド前像を照合し、方向を `0002`、出力をLowで20ms保持してからHighとし、さらに5ms待って補助CPU診断を実行した。7bitアドレス `0x10` のレジスター `0x0e` は `0x77`。診断ツールへ統合後、同一USB接続で2回連続で成功し、STOPとバス解放、補助CPU停止、システム設定、GPIOの方向・出力、16KiBの共有RAM、ブート領域の復元を確認した。実測したのはこの固定1 byte読み取りのみ。

### ソース生成コードによる地デジ初期化・選局の診断

操作7で、`0x0e` の1 byte読み取り `77`、同じ値の書き戻し、2 byte読み取り `77 10` が成功。続いてpix-userlandの地上波初期化・選局手順をホスト側の一時スクリプトで実行した。マスク更新は機器の読み取り結果を使って計算した。地上波473.142857 MHzの初期化と選局コマンドが完了し、`0x80` と `0xb0` の値はリポジトリーのTC90522地上波ロック判定条件を満たした。Rev.01のTC90532XBGでは同じビット条件をロックの診断指標として使用した。TS出力・USB受信・映像は測定していない。

GPIO、システム設定、補助CPU制御、共有RAMとブート領域の復元を確認。地上波の初期化・選局スクリプトは診断用で、通常のDriverHostには接続していない。

### 独自選局からTSリングまでの実機試験

Rev.01の地デジ13chをソース生成I²C経路で選局したまま、WinUSBのBC制御転送でTSエンジンのMMIOを設定した。既存経路と照合し、システム側は `0x00f10118=0xffff`、`0x00f1011c=(旧値 & 0xfa1f) | 0x0580`、`0x00f001f0=0x1a000000`。これらを合わせると `0x01900404` のbit 18を設定できた。入口レジスター単独、システム側 `0x00f001f0` 単独、`0x01600404` 単独では設定できなかった。

エンジンの設定は参考コード `0x803998ec` と表 `0x803ae034` を参照した。リングはバスアドレス `0x0138ec00`、USBメモリー窓からの読出し先 `0x8138ec00`、容量 `0x30000`。開始・停止は `0x01902010` に `0x02000000` / `0x04000000`。入力開始側は `0x01901040=0x03000000`。初回の試行ではFRの `lsl2` のシフト量を誤って低いビットに書き込み、開始状態が0のままだった。

修正後は開始状態 `0x02000000`、生産位置 `0x2ff40`（リング満杯時の1レコード手前）を確認した。先頭8192 bytesをBC制御転送で取得し、offset 165から192-byte間隔の同期列を検出。完全な188-byte TSは41パケットで、同期欠落・TEIは0。PIDは `0x0100`、`0x0111`、`0x0140`、`0x0160`、`0x0161`、`0x1fff`。この短いサンプルにPATはなかった。終了時に停止状態、リング192 KiBの前像一致、システム設定、GPIO、補助CPUと共有RAM・ブート領域の復元を確認した。TSエンジン設定は保存値を書き戻したが、全レジスターの最終読み戻しは行っていない。

この試験はリングからの制御転送による取得まで。USB Bulk FIFOの設定・連続補充とBonDriver配信は次の段階。

### TSリングからUSB Bulk INへの連続転送

Rev.01のブートRAM上でソース生成FRコードを動かし、`0x00fdbd84` へ128 wordを書いて、USBのBulk IN `0x81` から512 bytesが一致することを確認した。FIFOの受入れは `0x00fdbd0c` bit 2、コミットはセレクター `0x00fd814c=8` 中に `0x00fdbd0c=4` を書き、セレクターを15に戻す方式。通常のブート時のエンドポイント設定で試験できた。

リングから送る診断版はPIF1操作4を使う。要求ペイロード先頭2 wordはリング内の512-byte境界の位置と最大送出数1～256。応答は次の位置、送出数、生産位置、FIFO状態、診断結果の5 word。送出したデータはリングの192-byteレコードをバイト列として保持する。消費位置は転送済みの完全な192-byte単位まで進める。固定の試行上限を使用する診断で、製品用の時間制御や自動再接続は含まない。

最初の2 MiB試験はリングを先に起動し、1回64送出・ホスト4 KiB読取りで実行した。TS同期エラー・TEIは0、CRC正常PATは5件、連続性エラーは118件。リング開始をFIFO補充の直前へ移し、1回最大256送出・ホスト最大64 KiB読取りへ変更した試験では、4.402秒で16 MiBを受信。機器の送出数とホストの受信サイズが一致した。同期オフセット95から完全なTS 87,380パケットを抽出し、同期エラー、TEI、連続性エラーはいずれも0。CRC正常PATは44件、TSIDは `0x7c11`（31761）、PIDは34種類だった。複数条件を同時に変更したため、初回の連続性エラーの改善を個々の変更へ帰属させていない。

試験終了後はTSエンジン停止、リング192 KiBとブート用RAM、システム設定、GPIO、補助CPU共有RAMの復元を確認した。TSエンジン全レジスターの最終読み戻し、長時間、選局切り替え、BonDriver連携は未検証。リポジトリーの `build.py --bulk` で生成した常駐コードは16 MiB実機試験で使用したものとSHA-256が一致した。

### 同一接続での再選局と30分固定受信

2026-11-07に、Windows x64とPIX-DT295 Rev.01（TC90532XBG）で、コミット `f0b03c3` から生成したPAF1とPIF1 Bulkの診断イメージを使用した。`bulk_validate.py --channels 13:31761 17:31760 13:31761 --seconds 5 --long-seconds 1800` で地デジを再選局し、最後のGR13をそのまま固定受信した。各5秒の短区間は期待TSIDと一致し、同期、TEI、CC、形式の異常は0件だった。

固定受信は1,800.031秒、6,884,032,512 bytes、35,854,335 TSパケット。CRCが正常なPAT 18,001件はすべてTSID 31761だった。同期、TEI、形式異常は0件。受信開始後1秒のCC異常は0件、定常区間は11 PIDで1件ずつの計11件となり、連続性の合格条件を満たさなかった。

11件は受信開始から1,108.924～1,108.946秒に集中した。その直前のUSB読み取り完了間隔は試験中最大の82.129 msだった。平均受信量約3.82 MB/sでは192 KiBのリング容量は約51 ms分に相当する。USB読み取り時刻との相関はあるが、この試験では異常時のリング占有率を記録しておらず、欠落が発生した層は未確定。

TSエンジンの停止、TSリング、システム設定、ブートRAM、補助CPU共有RAMと制御状態、GPIOの復元を確認した。対象はWinUSB診断経路の地デジTS。BonDriver配信、映像復号、衛星の長時間受信、TSエンジン全レジスターの最終読み戻しは測定範囲外。
