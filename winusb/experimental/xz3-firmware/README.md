# GV-MVP/XZ3 FR30 I²C中継ファームウェア

GV-MVP/XZ系のUSBブート経路から、FR30でI²Cコントローラーの初期化と、I²Cの書き込み、読み出し、反復START付き書き込み・読み出しを実行する試作です。給電、ピン設定、チューナー選局、TS転送はホスト側の実装範囲です。I²Cコントローラーの転送手順はPIX-DT295の `direct_pump.c` の構造を参照し、CONTROLへ書く値は公開mAgicVISIONファームウェアのXZ常駐部に合わせています。USB入口はXZのブートコードに合わせています。

## ビルドと検証

FR30 GCCとBinutilsを使用します。インストールせずにビルドツリーの `xgcc` を使う場合は、`--compiler <build>/gcc/xgcc --compiler-arg=-B<build>/gcc` と、Binutilsの `--assembler`、`--linker`、`--objcopy` を指定します。

```sh
python3 build.py --out /tmp/xz3-i2c
cc -std=c11 -Wall -Wextra -Werror test_relay.c -o /tmp/xz3-relay-test
/tmp/xz3-relay-test
```

出力はUSBフック用の `hook.bin`（RAM `0x000e9a10`）と、本体の `relay.bin`（RAM `0x000ea61c`）です。ロード側では、XZの起動状態と書き換え対象の元バイト列を確認し、作業領域とステージングを退避したうえで、本体、フックの順で適用する必要があります。終了時はフックから先に復元し、読み戻して照合します。通常のUSB読み出しは元の処理へ戻ります。

Windows x64のWinUSBを使用し、GV-MVP/XZ3のRAM上で状態取得と未初期化時の転送拒否を確認しました。このときboot0のDIVIDERは `0` で、I²Cコントローラーは初期化されていませんでした。試験後にフック、本体領域、ステージングを復元し、退避内容との一致を確認しています。

同じ環境で操作3を実行すると結果は成功で、CONTROLは `0x40`、DIVIDERは `0xbc` と読めました。書いた `0x3c` にbit 7が加わった値で、bit 7の意味は未確定です。このため、BATCHの前提確認はDIVIDERの下位7ビットだけを比べます。初期化後に7ビットアドレス `0x10` と `0x11` へレジスター指定なしの1バイト読み出しを試すと、両方ともバイト完了を待つ段階でタイムアウトしました。STOP後のSTATUSは `0x20`、CONTROLは `0x42` で、バスの解放待ちは成功しています。boot0のクロック状態ではI²Cコントローラーのシフト動作が進んでいない可能性がありますが、原因は特定できていません。I²Cレジスターの初期化はUSBのRAM復元では戻らず、XZの再起動まで残ります。模擬MMIO試験では初期化の順序と値、複数操作、反復START、不正な操作列、NACK、バスエラー、タイムアウト、STOP後のバス固着を確認できます。

## パケット

ステージング `0x000c4600` に64バイトを末尾のワードから書き、マジックを最後に書きます。同じアドレスから64バイト読み出すと処理が実行されます。先頭6ワードはビッグエンディアンです。

| ワード | 要求 | 応答 |
| --- | --- | --- |
| 0 | マジック `0x585a4931` | 同左 |
| 1 | シーケンス番号 | 同左 |
| 2 | 操作番号 | 操作番号の最上位ビットを設定 |
| 3 | 操作データのバイト数 | 結果コード |
| 4 | 0（操作7では7ビットアドレス） | 完了したI²C操作数 |
| 5 | 0（操作7では読出長） | 応答データのバイト数 |

操作1は状態取得で、STATUS、CONTROL、DIVIDERの3ワードを返します。操作2は残り40バイトに `[7ビットアドレス, 書込長, 読出長, 書込データ...]` を並べます。各操作の書込長と読出長は最大8バイトです。全体を検証してから実行し、失敗時は後続の操作を打ち切ります。完了済みの書き込みには副作用があるため、ホストでバッチ全体を再送するときは個々の操作の再実行可否を考慮してください。

操作3はI²Cコントローラーの初期化で、操作データは取りません。初期化後に操作1と同じ3ワードを返し、初期化後もバスが解放されない場合はタイムアウトとともに同じ3ワードを返します。

操作4はクロック関連レジスターの読み出しで、書き込みは行いません。操作データは1バイトのページ番号です。ページ0は16ビットの `0x00f1010c`、`0x00f10114`、`0x00f10118`、`0x00f1011c`、`0x00f10120`、`0x00f10124`、`0x00f10128`、`0x00f1012c`、`0x00f10014`、`0x00f10018` を2個ずつ1ワードの上位・下位へ詰め、続けて32ビットの `0x00f10004`、`0x00fd8010`、`0x00fd8014` を返します（32バイト）。ページ1は各ブロックの `0x0404`（`0x014d0404`、`0x010d0404`、`0x012d0404`、`0x013d0404`、`0x00e70404`、`0x00c70404`、`0x00d00404`、`0x01600404`、`0x01700404`）を返します（36バイト）。ページ1は、クロックが止まったブロックの読み出しでboot0が応答しなくなる可能性を切り分けるため、ページ0と分けています。

操作6はクロック設定で、操作データは取りません。内容は後述の「状態1のクロック設定」のとおりです。応答は1ワード（4バイト）で、成功時は0、読み戻しが一致しなかった場合はその項目番号+1です。前提条件（`0x00f10004` を16ビットで読んだ値の `& 0x0c00` が `0x0800`）を満たさない場合は、何も書かずに未初期化を返します。

操作7は単一のI²C転送です。ワード3は書込長、ワード4は7ビットアドレス、ワード5は読出長で、書込データはオフセット24から始まります。書込長と読出長の合計は1〜40バイトです。書き込みと読み出しを両方指定すると反復STARTを使います。応答形式は操作2と共通です。38バイトのチューナー設定を途中でSTOPせずに送るために使用します。
結果コードは順に成功、形式不正、タイムアウト、バスエラー、NACK、STOP後のタイムアウト、未初期化、読み戻し不一致です。未初期化の判定には、公開mAgicVISIONファームウェアのXZ初期化データで使用されているDIVIDER値 `0x3c` を使います。この値だけで周辺回路の給電やピン設定を確認できるわけではありません。

## I²Cコントローラーの初期化

XZのUSBウィンドウは `0x000fffff` までのアドレスしか扱えないため、ホストから `0x00fdxxxx` のMMIOへは書き込めません。このため、初期化はホストではなくこのファームウェアが担当します。

書き込む値は、公開mAgicVISIONファームウェア（`magicvision-firmware_0.2.0_all.deb` の `firmware.bin`、オフセット `0x1acc0`〜`0x1ad4f`）のXZ初期化表から、I²Cブロックの項目だけを同じ順序で抜き出したものです。表の各項目は `[アドレス, 値, 保持マスク, 種別]` の16バイトで、常駐ファームウェアの解釈に従うと、保持マスク付きの項目は `(旧値 & 保持マスク) | 値` を書きます。

| 順 | アドレス | 書き込み |
| --- | --- | --- |
| 1 | `0x00fd8010` | 旧値に `0x10` を論理和 |
| 2 | `0x00fd8014` | 旧値から `0x10` を解除 |
| 3 | `0x00fd80c0` | `1` |
| 4 | `0x00fd80c0` | `0` |
| 5 | `0x00fd80c4` | `0` |
| 6 | `0x00fd8ff8` | `6` |
| 7 | `0x00fd8ff4` | `0x10` |
| 8 | `0x00fd8fe8`（DIVIDER） | `0x3c` |
| 9 | `0x00fd8fe4`（CONTROL） | `0x40` |

torne（MB86H47）のホスト側初期化 `Bootstrap::I2cInit()` も同じ手順ですが、`0x00fd8ff4` の値はtorneが `8`、XZの表が `0x10` です。同じ値を共有すると機種差を隠すため、XZではXZの表の値を使います。

表の前半にあるクロック、端子、電源の項目（`0x00f10xxx` と各ブロックの `0x0404`）は、USBが動作しているboot0の状態を変えるため対象外です。実機ではこの範囲の初期化だけではバイト転送が完了しませんでした。

操作4のページ0で読んだGV-MVP/XZ3のboot0の値を、表の値と保持マスクから求めた最終値と比べると次のとおりです（I²C初期化の実行後に取得）。

| レジスター | boot0の値 | 表の最終値 |
| --- | --- | --- |
| `0x00f1010c` | `0x0001` | `0x8201` |
| `0x00f10114` | `0xba00` | `0x8008` |
| `0x00f10118` | `0x6010` | `0xffff` |
| `0x00f1011c` | `0x0006` | `0x0006` |
| `0x00f10120` | `0x0100` | `0x0100` |
| `0x00f10124` | `0x128a` | `0x128a` |
| `0x00f10128` | `0x6010` | `0x6100` |
| `0x00f1012c` | `0x4006` | `0x4007` |
| `0x00f10014` | `0x0000` | `0xd0f4` |
| `0x00f10018` | `0x0000` | `0x00e4`（4段階で設定） |
| `0x00f10004` | `0x8a510000` | 読み出しのみ |
| `0x00fd8010` | `0x00100014` | bit 4を設定 |
| `0x00fd8014` | `0x0f2f000b` | bit 4を解除 |

boot0では `0x00f10014`、`0x00f10018`、`0x00f1010c` が設定されていません（`0x00f10014` と `0x00f10018` の役割は後述の「チューナーの電源投入手順」を参照）。`0x00f10004` のbit 10〜11は0で、常駐ファームウェアはこの値のとき表の `0x00f100f0` の項目を省略します。I²Cのバイト転送が進まない原因の候補として、表が必ず立てる `0x00f1012c` のbit 0を、他のビットを保持して16ビットで立ててから操作3の手順を実行する版を試しました。`0x00f1012c` は `0x4007` になり、USBの応答とRAMの復元に問題はありませんでしたが、`0x10` と `0x11` の読み出しは前と同じくバイト完了待ちでタイムアウトしました。このビットだけでは転送が進まないため、操作3には含めていません。

続けて、`0x00f1012c` のbit 0を立てた状態のまま、表と同じ `0xffff` を `0x00f10118` へ16ビットで書いてから操作3の手順を実行する版も試しました。`0x00f10118` は `0xffff` になり、USBの応答とRAMの復元に問題はありませんでしたが、`0x10` と `0x11` の読み出しは同じくバイト完了待ちでタイムアウトしました。この書き込みも操作3には含めていません。残る表の項目は `0x00f10014`、`0x00f10018`、`0x00f1010c` です。

ページ1はboot0で応答を止めずに読み出せました。表はどのブロックにもbit 18（`0x00040000`）を論理和で立てます。

| レジスター | boot0の値 |
| --- | --- |
| `0x014d0404` | `0x00040000` |
| `0x010d0404` | `0x00040000` |
| `0x012d0404`、`0x013d0404`、`0x00e70404`、`0x00c70404`、`0x00d00404`、`0x01600404`、`0x01700404` | `0x00000000` |

bit 18は `0x014d0000` と `0x010d0000` のブロックだけで立っていて、残る7ブロックでは0です。0は、ビットが立っていない場合と、クロックの止まったブロックが0を返す場合を区別できません。I²Cブロック（`0x00fd8000`）は表のこの範囲に含まれず、各ブロックとI²Cの関係も確認できていません。

## XZ常駐ファームウェアのI²C転送手順との比較

公開mAgicVISIONファームウェアのXZ常駐部（`0x80380000` 基準）には、ベースアドレス `0x00fd8000` を受け取るI²C転送関数 `0x8038eb98`、その待機関数 `0x8038eb0c`、1バイト送信関数 `0x8038eb5c`、初期化関数 `0x8038ef10` があります。初期化は操作3と同じ順序と値です。待機の判定（CONTROLのbit 7でバスエラー、bit 0でバイト完了、STATUSのbit 7でバス使用中、STATUSのbit 4でNACK）もこのファームウェアと同じです。異なるのは、CONTROLへ書く値です。

| 段階 | XZ常駐ファームウェア | 以前のこのファームウェア（DT295の実測手順） |
| --- | --- | --- |
| START＋アドレス | `0x50` | `0x52` |
| 送信データ | バイトごとに `0x50` | 読み戻したCONTROLからbit 0を除いた値 |
| 反復START＋アドレス | `0x70` | 読み戻したCONTROLからbit 0を除き `0x20` を加えた値 |
| 受信（後続あり / 最後） | `0x58` / `0x50` | 読み戻したCONTROLからbit 0とbit 3を除き、後続ありなら `0x08` を加えた値 |
| STOP | `0x40` を書き、STATUSのbit 7の解除を最大 `0x400` 回待つ | `0x42` |

XZ常駐ファームウェアの値にはbit 1（`0x02`）がありません。このファームウェアの転送は、XZで受信実績のある常駐ファームウェアの値に合わせ、START・送信 `0x50`、反復START `0x70`、受信 `0x58` / `0x50`、STOP `0x40` を固定値で書きます。

GV-MVP/XZ3の実機（`0x00f10118 = 0xffff`、`0x00f1012c = 0x4007` を書いた後の状態）でこの値に切り替えて操作3と `0x10`、`0x11` の読み出しを試すと、どちらもバイト完了待ちでタイムアウトしました。STOP後のCONTROLは `0x40`、STATUSは `0x20` で、DT295の値のときと同じくSTATUSのbit 5が立っています。bit 1はタイムアウトの原因ではありません。STATUSのbit 5はSTARTの試行後にだけ現れ、復調器とチューナーへの給電やピン設定がない状態でSCLまたはSDAがLowに保たれている可能性がありますが、確認できていません。

## チューナーの電源投入手順

XZ常駐部では、I²C初期化 `0x8038ef10` を状態機械 `0x80391140` の状態4から呼びます（状態はコンテキストの `+0xa4`）。その前の状態は次のとおりです。

| 状態 | 処理 | 次の状態までの待機 |
| --- | --- | --- |
| 1 | `0x80383a90` を呼び、`0x00f1010c` へ16ビットで `0x8201` を書いて読み戻しを照合 | なし |
| 2 | I²Cの待機確認 `0x8038eeb4` の後、`0x00f10018 = (旧値 & 0xffbe) \| 0x40`、`0x00f10014 \|= 0x41`。`0x00f10014` のbit 0とbit 6を読み戻して照合 | 50ティック |
| 3 | `0x00f10018 \|= 0x41`。bit 0を読み戻して照合 | 10ティック |
| 4 | I²C初期化 | — |

`0x00f10014` のbitを立ててから `0x00f10018` の同じbitを立てる順序と、bit 6を先に立ててから待機してbit 0を立てる順序から、`0x00f10014` は端子の出力許可、`0x00f10018` は出力値と推定しています。bit 6は電源の許可、bit 0は待機後に解除するリセットの可能性がありますが、回路との対応は確認できていません。初期化表の `0x00f10014 |= 0xd0f4` と、待機を挟んで `0x00f10018` を `0x04`、`0x44`、`0xc4`、`0xe4` の順に1bitずつ立てる項目も、同じ端子群を順に駆動する手順と考えられます。表の待機値（`0x000a`、`0x03e8`）とティックの時間単位は確認できていません。

GV-MVP/XZ3のboot0では `0x00f10014` と `0x00f10018` がどちらも0で、この推定に従うと、復調器とチューナーには給電もリセット解除もされていません。### 操作5（端子の駆動）

操作5は、表と状態機械の手順を1回の要求につき1手順ずつ実行します。操作データは1バイトの手順番号（0〜5）で、応答は16ビットで読み戻した `0x00f10014` と `0x00f10018` の2ワード（8バイト）です。手順の間の待機はホストが行います。USB処理の中で長く待つと、制御転送がホスト側のタイムアウトを超えるためです。

| 手順 | 書き込み | 出典 |
| --- | --- | --- |
| 0 | `0x00f10014 \|= 0xd0f4`、`0x00f10018 = (旧値 & 0xff1b) \| 0x04` | 初期化表 |
| 1 | `0x00f10018 = (旧値 & 0xff1b) \| 0x44` | 初期化表（待機 `0x000a`） |
| 2 | `0x00f10018 = (旧値 & 0xff1b) \| 0xc4` | 初期化表（待機 `0x000a`） |
| 3 | `0x00f10018 = (旧値 & 0xff1b) \| 0xe4` | 初期化表（待機 `0x03e8`） |
| 4 | `0x00f10018 = (旧値 & 0xffbe) \| 0x40`、`0x00f10014 \|= 0x41` | 状態機械の状態2 |
| 5 | `0x00f10018 \|= 0x41` | 状態機械の状態3 |

表の待機は、その項目を書いた後、次の項目までの間に入ります。

GV-MVP/XZ3の実機で、手順の間にそれぞれ10、10、1000、10、500、200ミリ秒待ってから操作3と `0x10`、`0x11` の読み出しを試しました。`0x00f10014` は `0xd0f5`、`0x00f10018` は `0x00e5` になり、USBの応答とRAMの復元に問題はありませんでした。しかし読み出しは両方ともバイト完了待ちでタイムアウトし、STATUSのbit 5も立ったままでした。この状態の端子駆動だけではI²C転送が進みません。

続けて、常駐部の状態1と同じく `0x00f1010c` へ16ビットで `0x8201` を書く手順を操作5の前に加えた版も試しました（この書き込みは操作5に含めていません）。`0x00f1010c` は `0x8201` になり、USBの応答とRAMの復元に問題はありませんでしたが、`0x10` と `0x11` の読み出しは同じくバイト完了待ちでタイムアウトし、STATUSのbit 5も立ったままでした。端子が駆動済みの状態で手順0を再実行したため、出力値は一度 `0x0005` まで下がってから表の順序で再び `0x00e5` になっています。

初期化表で値が異なる `0x00f10114`（boot0 `0xba00`、表 `0x8008`）と `0x00f10128`（boot0 `0x6010`、表 `0x6100`）は未適用です。### 状態1のクロック設定（`0x80383840`）

常駐部の状態1は `0x80383a90` から `0x80383840` をモード0、フラグ1で呼び、その後で `0x00f1010c` へ `0x8201` を書きます。`0x80383840` は、`0x803b0024` にある9項目の表（各8バイト: アドレス、保持マスク、値）の現在値を退避してから、項目の順に書き込み、毎回読み戻して照合します。照合が一致しない場合は、その時点で中止します。

前提条件として、`0x00f10004` を16ビットで読んだ値（GV-MVP/XZ3のboot0で `0x8a51`）の `& 0x0c00` が `0x0800` であることを確認します。boot0の値はこの条件を満たします。以前の表で `0x00f10004` のbit 10〜11を0と書いたのは、32ビットで読んだ値で見た場合の話です。

| 順 | アドレス | モード0、フラグ1で書く値 | GV-MVP/XZ3での適用 |
| --- | --- | --- | --- |
| 0 | `0x00f100f0` | `1` | 未適用 |
| 1 | `0x00f1010c` | 旧値 & `1`（状態1がこの後で `0x8201` を書く） | `0x8201` だけ適用 |
| 2 | `0x00f10114` | `0x8008` | 未適用（boot0 `0xba00`） |
| 3 | `0x00f10118` | `0xffff`、続けて `0x803b0000` の9ブロックの `0x0404` にbit 18を論理和 | `0xffff` だけ適用。bit 18は7ブロックで未設定 |
| 4 | `0x00f1011c` | 旧値 & `~0x300` を書いてから `6` | boot0で `6` |
| 5 | `0x00f10120` | (旧値 & `0x1080`) \| `0x100` | boot0で同じ値 |
| 6 | `0x00f10124` | `0x128a` | boot0で同じ値 |
| 7 | `0x00f10128` | (旧値 & `0x0e0e`) \| `0x6100` | 未適用（boot0 `0x6010`） |
| 8 | `0x00f1012c` | (旧値 & `0x21f8`) \| `0x4007` | 適用済み |

`0x803b0000` の9ブロックのうち、先頭6ブロックは16ビットで上位側に `4` を論理和し、残り3ブロックは32ビットで `0x00040000` を論理和します。どちらも32ビットのレジスターではbit 18にあたります。表の10番目（`0x00d00004`）は、このループの対象外です。

### クロック設定後の実機結果

この表の手順をモード0、フラグ1のとおりに、毎回の読み戻し照合つきで実行する版を試しました。実行順は、クロック設定、`0x00f1010c = 0x8201`、操作5の手順0〜5、操作3、`0x10` と `0x11` の読み出しです。この版はリポジトリ外の試作で、クロック設定は操作5に含めていません。

- クロック設定の照合はすべて一致しました。
- 適用後、`0x00f10114` は `0x8008`、`0x00f10128` は `0x6100`、`0x00f1010c` は `0x8201` でした。ページ1の9ブロックは、すべてbit 18（`0x00040000`）が立っていました。
- `0x10` と `0x11` の読み出しは、タイムアウトではなくNACKで終わりました。STOP後のSTATUSは `0x00` で、それまで立っていたbit 5は消えています。
- USBの応答とRAMの復元に問題はありませんでした。

この結果から、I²CコントローラーがSTART、アドレス送信、STOPまで実行できるようになったことを確認しました。転送が進まなかった原因は、クロック設定の未適用分（`0x00f100f0`、`0x00f10114`、`0x00f10128`、7ブロックのbit 18）のいずれかです。どの項目が必要かは切り分けていません。

このクロック設定は、操作6としてこのファームウェアに取り込みました。`0x803b0024` の9項目と状態1の `0x00f1010c = 0x8201` を同じ表で扱い、毎回読み戻して照合します。各ブロックのbit 18は、項目3（`0x00f10118`）の照合後に、常駐部と同じく先頭6ブロックは16ビット、残り3ブロックは32ビットで立てます。

### I²Cアドレス

XZ常駐部のI²C要求の組み立て関数 `0x80390f8c` は、7ビットアドレスを要求パケットへそのまま入れ、転送関数が1ビット左へずらして送ります。呼び出し側が渡すアドレスは `0x09`（8ビット表記 `0x12`）と `0x60`（同 `0xc0`）だけで、振り分け関数 `0x803912cc` もこの2つで分岐します。torneの記録（`winusb/docs/cech-zd1j-design.md`）でも、復調器は8ビット表記 `0x12` です。このため、`0x09` は復調器、`0x60` はチューナーの候補と考えていますが、確認できていません。

GV-MVP/XZ3の実機で、操作6、操作5の手順0〜5、操作3の順に実行してから、`0x09` と `0x60` へレジスター指定なしの1バイト読み出しを試しました。操作6の照合はすべて一致し、USBの応答とRAMの復元にも問題はありませんでした。しかし読み出しは両方ともNACKで、STOP後のSTATUSは `0x00` でした。`0x10` と `0x11` もNACKです。I²Cバスは動作していますが、試した4つのアドレスはどれも応答していません。

応答がない理由として、次の可能性を切り分けていません。

- 操作5の端子の駆動が、実際の電源とリセットの極性に合っていない。操作5は初期化表と状態機械の両方の手順を含み、常駐部がどの経路で端子を駆動しているかは確認できていません。
- 常駐部がI²C初期化の後、最初の転送までに行う処理が足りない。

### 復調器ドライバーの転送

常駐部の初期化関数（`0x80390920` 付近）は、I²C関数 `0x8038fcac` をコンテキストの `+0xb4` へ登録し、復調器ドライバーへ渡します。その後で、状態機械の開始関数 `0x803910f8` を呼びます。

復調器ドライバーの転送関数 `0x8039239c` は、このコールバックへ常にアドレス `0x09` を渡します（`ldi:8 0x9,r5`）。レジスター番号とデータは16ビットで、ビッグエンディアンです。

- 読み出し `0x8039242c`: レジスター番号の2バイトを書き、2バイトを読み出します。
- 書き込み `0x803923ec`: レジスター番号とデータの4バイトを書きます。

`0x09` は復調器のアドレスと確認できました。前述の「`0x09` と `0x60` がXZの復調器とチューナーのアドレスではない」という可能性は、`0x09` については否定されます。

振り分け関数 `0x803912cc` は、`0x60` 宛ての転送の前に、`0x09` へ `0x803a78b0` の4バイトを書きます。このため、`0x60` は復調器のI²Cゲートの先にあるチューナーと考えられます。ゲートを開かずに `0x60` へ送った場合のNACKは、この構成と矛盾しません。

一方、`0x09` のNACKは、復調器がアドレスに応答していないことを示します。給電の不足、リセットの保持、端子の極性の違いが候補ですが、確認できていません。初期化表を解釈する関数 `0x80382970` は主処理の振り分け（`0x803811fe`）から呼ばれます。XZでこの表の端子項目（`0x00f10014`、`0x00f10018`）が実行されるかどうかは、まだ確認できていません。

GV-MVP/XZ3を再接続してboot0の状態（DIVIDER `0`）へ戻し、表の端子手順を使わずに試しました。実行順は、操作6、操作5の手順4と5（状態機械の手順）、操作3です。

- 操作6の照合はすべて一致しました。
- 操作5の後、`0x00f10014` は `0x0041`、`0x00f10018` は `0x0041` でした。
- `0x09` へのアドレスだけの1バイト読み出しも、レジスター `0x0405` の2バイト読み出しも、NACKでした。`0x60` もNACKです。
- STOP後のSTATUSは `0x00` で、USBの応答とRAMの復元に問題はありませんでした。

この結果から、I²Cコントローラーを動かすにはクロック設定だけで足り、表の端子手順は不要であることがわかりました。一方、端子の駆動を状態機械の手順だけにしても、表の手順と合わせても、復調器は応答しませんでした。常駐部は、`0x00fdbc00`〜`0x00fdbdff` と `0x00fd814c` のレジスターも、別の関数（`0x80382d46` 付近）とブートストラップ（`0x000ea9bc` 付近）で操作しています。

これらを追跡した結果は次のとおりで、復調器の給電やリセットとは考えにくい用途でした。

- `0x00fd814c` は、保護されたレジスターへの書き込みを許可する鍵として使われています。`8`、`6` または `2` を書いてから対象のレジスターを書き、最後に `0xf` を書いて閉じます。退避関数 `0x80382e24` は、`0x00fd814c` が `0xf` と読めるときだけ動きます。
- `0x80382e24` は、番号0なら `0x00fdbd08`、番号1なら `0x00fdbd20` をコンテキストへ退避し、復元待ちの印を付けます。`0x80382d18` は、退避した値を鍵の手順で書き戻し、`0x00fdbc14` にも書いてから読み戻して照合します。`0x80382df0` は番号0と1の両方を復元します。
- ブートストラップの該当関数は、`0x00fdbd04` のbit 16〜17と `0x00fdbc08` のbit 9、11、14を、遅延関数 `0x82800000` を挟んで最大100万回待ちます。その後で `0x00fd814c = 8`、`0x00fdbd04 = 0x10`、`0x00fd814c = 0xf` を書きます。

退避と復元の対象が2組あること、ブートストラップがUSBの状態待ちと同じ場所でこれらを扱っていることから、USB側の状態の退避と復元と推定しています。回路との対応は確認できていません。復調器の給電、リセット、クロックの供給元は、まだ特定できていません。

### 常駐部のMMIO書き込みの一覧

常駐部の `ldi:32` 命令に現れる `0x00c00000`〜`0x01ffffff` のアドレスのうち、直後にそのレジスターへの格納があるものを抽出し、用途で分類しました。用途は周辺の処理からの推定で、確認できていません。

| 分類 | アドレス | 推定した用途 |

| I²C | `0x00fd8010`、`0x00fd8014`、`0x00fd80c0`、`0x00fd80c4`、`0x00fd8fxx` | 初期化（操作3）とSTOP。終了処理で `0x00fd80c0 = 3` |
| クロック | `0x00f100f0`、`0x00f1010c`〜`0x00f1012c`、9ブロックの `0x0404` | 状態1のクロック設定（操作6） |
| 端子（状態機械） | `0x00f10014`、`0x00f10018` のbit 0と6 | 投入は状態2と3。終了処理（`0x80391514` 付近）で状態2の退避値を書き戻す |

コードの読解だけでは、操作5と操作6で扱ったもの以外に、復調器の給電、リセット、クロックを担うレジスターは特定できませんでした。次の確認では、常駐部が受信している状態のレジスター値と、このファームウェアで設定した状態のレジスター値を比べます。

### アドレススキャン

GV-MVP/XZ3で、操作6、操作5の手順4と5、操作3を適用した状態のまま、7ビットアドレス `0x08`〜`0x77` へアドレスだけの1バイト読み出しを1要求ずつ送りました。112アドレスすべてがNACKで、ACKを返したアドレスはありませんでした。タイムアウトとバスエラーはなく、STOP後のSTATUSは `0x00` でした。

この結果は、バス上のどの機器も応答していないことを示します。ただし、I²Cコントローラーの端子が外部のバスへ接続されていない場合（端子機能の選択が未設定の場合など）も、全アドレスがNACKになります。この2つは、この試験では区別できません。

### 受信中の常駐部の状態と、表の端子状態でのスキャン

公開mAgicVISIONのDriverHostを改変した試作で、地上波（473.142857 MHz）の選局完了直後に、操作10（常駐領域の読み出し）で `0x803b0000`〜`0x803b3fff` を読みました。書き込みは行っていません。受信は正常で、約20 MBのTSを取得できました。

- 初期化表を解釈する関数のコンテキスト（`0x803b1a24`）は、全36項目を完了していました（項目番号 `0x24`、完了フラグ1、エラー0）。XZの受信では、初期化表の経路が実行されています。
- 同じコンテキストの退避表には29個のレジスターがあり、すべて操作3、5、6で扱っているものでした。退避表の値は解釈器が最初に触れる前の値で、設定後の値ではありません。
- warm状態（常駐部の稼働中）では、ウィンドウ読み出しはmAgicVISIONのフックが処理し、指定したアドレスの内容ではなくステージングのパケットを返しました。このため、warm状態ではウィンドウ経由のRAMの読み書きができず、このファームウェアを重ねて導入することもできません。

表の経路が実行されているとわかったため、GV-MVP/XZ3で、操作6、操作5の手順0〜5（表の端子手順を含む）、操作3の順に適用してから、アドレススキャンをやり直しました。`0x00f10014` は `0xd0f5`、`0x00f10018` は `0x00e5` です。

- 7ビットアドレス `0x18` と `0x19` がACKを返し、1バイトの読み出しは両方とも `0x00` でした。残りの110アドレスはNACKです。
- 同じ手順をもう一度実行しても、同じ結果でした。
- USBの応答とRAMの復元に問題はありませんでした。

この結果から、次のことがわかりました。

- バス上の機器が応答するには、初期化表の端子手順（操作5の手順0〜3）が必要です。状態機械の手順（手順4と5）だけでは、どのアドレスも応答しません。
- GV-MVP/XZ3で応答する機器のアドレスは `0x18` と `0x19` です。常駐部の状態機械と復調器ドライバーが使う `0x09` と `0x60`、DT295の `0x10` と `0x11` は応答しません。`0x09` を使う経路は、常駐部に含まれていてもXZの受信では使われていないと考えられます。
- `0x18` と `0x19` の機器の種類とレジスター構成は、まだ確認できていません。

### デバッグ読み出しの可否

公開mAgicVISIONのデバッグ要求（マジック `0x585a4431`）でMMIOを読めるかを、コードから確認しました。

- ホスト側のソースが実際に送る操作はPING（1）と常駐領域の読み書き（10）だけで、READ（2）とWRITE（3）を送る処理はありません。
- ブートストラップの処理（`0x000ea75a` 以降）は、PING（1）と常駐領域の読み書き（10）を自分で処理します。操作10の範囲は `0x80380000` からのオフセット `0x40000` 未満で、4バイト境界、最大40バイトに限られ、MMIOは対象外です。
- 操作9と操作2〜7は、常駐部の署名（`0x803afffc` が `RSN1`）があるときだけ常駐部へ渡します。常駐部の振り分け（`0x80381ac8` 以降）で確認できたのは、操作9のサブコマンド（`0x20`、`0x25`、`0x2b`、`0x2e`、`0x2f` など）の分岐だけです。READ（2）がMMIOを読めるかは確認できていません。
- 公開mAgicVISIONのDriverHostは、受信中にWinUSBのデバイスを排他的に開き、終了時にデバイスを復元します。このため、別のツールから受信中の状態を読み出すことはできません。

受信中のレジスター値を得るには、公開mAgicVISIONのホスト側を改変し、選局後に読み出し要求を送る方法が考えられます。操作10で常駐部のRAMを読めば、状態2で退避した端子の値（コンテキストの `+0x98`、`+0x9a`）や、クロック設定で退避した値は確認できます。ただし、これはMMIOの現在値ではありません。

### 地デジ13chのI²C記録とrelayでの再現

Windows x64のWinUSBで、地上波とBS/CSのアンテナ線を接続したGV-MVP/XZ3を使用しました。mAgicVISION v2-0.2.0の試験用RAMイメージでI²C転送関数 `0x8038eb98` の要求と応答を記録し、選局に成功した経路を確認しました。最初の試行は初期化ログ採取後のログカウンター消去が失敗したため終了し、再試行ではカウンターを消去せず、初期化時点と選局後の記録を比較しました。

| 段階 | `0x18` 宛て | `0x19` 宛て | 内容 |
| --- | ---: | ---: | --- |
| 初期化 | 28 | 30 | 全58件が書き込み。最長38バイト |
| 地デジ13ch（473.142857 MHz） | 20 | 0 | 書き込み17件、レジスター指定付き読み出し3件 |

すべてI²Cコントローラー `0x00fd8000` を使い、転送エラーと記録のオーバーフローは0件でした。両方のアドレスで見られた `FE C0 …` は、LinuxのTC90522ドライバーが使う `0xfe` のI²C中継形式と一致し、下流アドレスは7ビット表記で `0x60` です。地デジ選局では `0x18` の `0x96`、`0x80`、`0xb2` を読み出し、`0x96` は `0xc2` でした。このロック判定と地デジ選局時の使用アドレスから、`0x18` はTC90522系の地デジ側、`0x19` は同系の衛星側と推定しています。部品の型番と衛星選局時の転送経路は未確認です。

- [Linux TC90522ドライバー](https://github.com/torvalds/linux/blob/master/drivers/media/dvb-frontends/tc90522.c)

試験用mAgicVISIONでの地デジ受信は10秒間で109,376パケットでした。PATのTSIDは `31761`、同期エラーとTEIは0件、CC不整合は653件でした。

続いて、boot0（DIVIDER `0`）からrelayで操作6、操作5の手順0〜5、操作3を実行し、操作7で記録と同じ初期化58件と選局20件を順番に再現しました。78件すべてが成功しました。選局前は `0x18` の `0x96=0x04`、`0x80=0xef` で未ロックでした。選局直後のポーリングで `0x96` が `0x02` から `0x40` に変わり、TC90522系の判定で地デジロックを確認しました。試験後はUSBフック、本体RAM、ステージングを読み戻して復元を照合しました。relay経由のTS取得はTS経路の実装が必要です。

### XZ3のTSリングとEP81の単発取得

mAgicVISIONのFIFO書き込み関数を試験用RAMイメージで計測しました。Windows x64のWinUSBで地デジ13chを10秒受信したとき、USB向けのフレーム化経路が54,377回呼ばれ、別の生TS送信経路は0回でした。この試験の取得結果は108,735パケット、同期エラー0件、TEI 0件、CC不整合738件です。

| 項目 | GV-MVP/XZ3の地デジ13chで確認した値 |
| --- | --- |
| DMA設定 | `0x00d02000 = 0x03020300` |
| DMA開始・停止 | `0x00d02010` へ `0x02000000`・`0x04000000` |
| DMAリング | DMAアドレス `0x00a90000`、FR30の読み出しアドレス `0x80a90000`、サイズ `0x3fe00` |
| 生成位置・消費位置 | `0x00d02028`・`0x00d0202c` |
| リングのレコード | 192バイト。先頭4バイトに続いて188バイトのTS |
| Bulk IN | EP81。512バイト単位。FIFO `0x00fdbd84`、状態 `0x00fdbd0c` |

TS診断用のビルドは `python3 build.py --ts-probe --out /tmp/xz3-ts` です。I²C中継版で地デジをロックした後、USBフックと本体RAMを復元し、給電を保ったままTS診断版を同じ手順でロードします。TS診断版は同じマジックを使用し、引数なしの操作8でリング先頭3レコードの先頭8バイトを返します。引数なしの操作9では、先にホストでEP81に196,608バイトの非同期読み出しを発行します。操作9はリングに1,024レコードを取り込み、DMAを停止してから、USB列挙時のEP81設定を使って生の192バイトレコードを送ります。

- 操作8の応答データは10ワードです。先頭4ワードは起動前のDMA状態、起動中の状態、生成バイト数、停止後の状態で、残り6ワードは3レコードの先頭8バイトです。
- 操作9も先頭4ワードは同じです。残り6ワードは試験前のEPモード、EP制御、EPバッファ、FIFOへ送ったバイト数、最後のFIFO待ちの結果、FIFO状態です。
- 最初の試作では送信直後にFIFOをリセットし、最後の512バイトがホストへ届きませんでした。列挙時のEP81設定をそのまま使用した版で196,608バイトを取得できました。
- 4バイトの前置データを除いた結果は1,024パケット、同期エラー0件、TEI 0件、CC不整合0件でした。CRCが有効なPATのTSIDは `31761` でした。試験後にDMAの停止と、USBフック、本体RAM、ステージングの復元を確認しました。

### DMAを止めずに行う連続取得

引数なしの操作11でDMAを開始し、操作12を繰り返すと1回あたり3 MiBの192バイトレコードをEP81へ転送します。操作12の間もDMAは動作し、FR30はUSB FIFOへ512バイトを渡すたびにDMAの消費位置を更新します。応答のオフセット40、44、48、52には、消費前に観測した最大の未処理バイト数、次の消費位置、最後に観測した生成位置、EP81へ投入したバイト数が入ります。操作11でEP81のFIFOを初期化します。ホストは操作11の応答後、最初の操作12より前にEP81読み出しを発行し、成功時も転送異常時も操作13で停止してからUSBフックと本体RAMを復元します。単独の操作10は開始から停止までを1要求で行う3 MiBの診断です。

XZのTSブロックがリセット前の状態にある場合は、操作10または11でDMA開始前にブロックをリセットします。長いデータを1回の制御要求で送った試験では、Windows側で約5秒後に制御転送がタイムアウトしました。操作11〜13で制御要求を分割すると、リングの消費位置を引き継いで受信を続けられます。

Windows x64のWinUSBで地デジ13ch（473.142857 MHz）を測定しました。初回の分割転送では、直前に中断した転送の1,024バイトが先頭に残り、TSの境界がずれました。操作11にFIFOの初期化を追加してから測定し直した結果は次のとおりです。

| 項目 | 実測値 |
| --- | ---: |
| ホストの連続受信時間 | 57.141秒 |
| EP81から取得したデータ | 125,829,120バイト（3 MiB × 40回） |
| 188バイトTSパケット | 655,360 |
| 同期エラー / TEI / CC不整合 | 0 / 0 / 0 |
| CRCが有効なPAT | 571件、TSID 31761 |
| リングの観測最大未処理量 | 113,856バイト（全体261,632バイト） |

40回すべてでDMAが動作中のまま規定量を転送し、最後に操作13で停止状態 `0` を確認しました。USBフックと本体RAM、ステージングも退避内容と一致しました。受信中の再選局、BS/CS、長時間運転は、この試験の対象外です。
